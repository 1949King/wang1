1结论先行：五条判断

不讲场面话。以下是我读完代码后的真实判断，正确性由后面的证据支撑。

判断 1 这不是一个剪辑软件，是一条「AI 漫剧制片线」的垂直切片

市面上没有第二个人在做「3D 素模摆姿势 → 分镜 → 生图 → 入轨精剪」这条连续链路。 剪辑功能只是它的出口，不是它的本体。这个认知一旦错位，所有优先级都会做错 —— 你会忍不住去补剪映已经做好的东西（磁吸、转场库、模板），而丢掉唯一性。

判断 2 真正的瓶颈不是功能缺失，是「写回时间线」的通道太窄

34 个 capability、58 个 action 已经注册，但能真正写回 _clips 且可撤销的只有 5–6 个。 项目自己在 06-roadmap.md:100 立的硬门槛是「≥8 个」，至今未勾选达标。 这意味着：AI 能"看懂"片子，但改不动片子。整个 AI 剪辑叙事卡在这一步。

判断 3 插件体系是全仓最乱的地方，也是投入产出比最高的地方

3 套在用 + 1 套死代码：plugin_manager.PluginManager、 plugin_loader 的接口族、plugins_module+plugin_store 的拓展中心、 以及已经死掉的 plugin_hotloader.py——后者里还藏着一个与前者同名的 class PluginManager，是个定时炸弹。 同时插件注册靠 plugin_store.py:503-517 硬编码路径，manifest.json 写了却没用。

判断 4 「诚实失败」是这个项目最值钱的产品哲学，应该升格成对外主张

我核对了全部生成路径：无 Key 时返回 ok:False、口型成片明确 TALKING_HEAD_UNAVAILABLE、生视频失败不写假片。 在一个 AI 工具普遍"假装成功"的时代，这是信任资产，也是天然的内容选题。 现在的做法是对的，但只做在了代码里，没做成品牌。

判断 5 拆分方向正确，但拆到一半留了个「漏拆」

editor_module.py 从 13,321 行降到 9,079 行，抽出 8 个 mixin， 成绩真实。但 Agent 调度代码（L7637–8300，含 _agent_dispatch、_cut_at_timeline_time） 还留在主文件里——旁边就躺着 EditorAgentRuntimeMixin。 同族代码分居两处，属于拆到一半停手，约 660 行可以直接搬家。

3我读懂了什么：三张关键结构图

项目的真实形状，比文档描述的更清楚。

3.1 时间线真相源：只有一个，但有两个镜像在跟着它跑

EditorModule._clips（editor_module.py:511）是唯一真相源，字段包含 path / name / start_time / duration / in_point / out_point / track / type / effects / transitions / speed / volume / keyframes。 这是好设计——没有出现双真相源（不存在的 AppState 是文档幻觉，virtual_timeline.py 是死代码）。

但有两个"影子副本"，目前是单向写入，属于可接受的暂时状态，但必须加守卫：

→

改进方向：把两个镜像改成 只读代理（property 转发到宿主）， 或在写入点加断言守卫。成本极低，收益是彻底断掉"漂移类 bug"的根。

3.2 Agent 权限金字塔：设计得比实现好

这是我在这个项目里最意外的发现。agent_policy.py 实现了一套三模式权限裁决， 而且细节相当老练：未登记工具默认按 file_write 保守处理（:149）； 预算限制 12 轮 / 24 工具 / 3 次只读重试（:38-41）； 写操作和付费操作永不自动重试（:214）；日志脱敏剔除密钥与绝对路径（:255, :278）。

结论：权限层没问题，问题在权限层下面没有足够多的"手"。 白名单 26 条对话 action 里，能落到 _clips 的寥寥无几。 就像一个保安系统很完善的仓库，但货架上没货。

3.3 剪辑 ↔ 画布 round-trip：通了，但用的是轮询

canvas_bridge.py:702 的 emit_canvas_to_editor() 与 :787 的 push_editor_to_canvas() 已经把双向通道建起来了， 身份字段走 editor_canvas_link.py:11 的 LINK_KEYS （canvas_node_id / kind / title），而且刻意不换 _clips 真相源——这个克制值得表扬。

但前端 useEditorCanvasLink.ts:46 用的是 每 4 秒拉 outbox、每 6 秒拉 timeline-snapshot。 服务端明明已经有 SSE（canvas_server.py:356-368 的 text/event-stream）， 却让它闲置。这是"能用但浪费"的典型。

↓ 正在贬值 · 别投
  • 一键成片 / 自动混剪：模型每 3 个月就更强一次，你的实现会被碾过

  • 工作流锁定：越垂直、越长的链路越难被替换
  • 角色/场景一致性：这是 AI 生成内容最大的痛，也是短剧的刚需（项目已有 @角色 注入与三视图，方向对）

5百万编程 UP 主视角：什么能被拍成视频

我关心的不是代码好不好，是"能不能让观众看完说一句'卧槽'"。

5.1 先说坏消息：这个项目现在很难拍

因为它的差异化全都藏在流程里，而流程最不上镜。 你没法拍一段"我修了一个静默吞异常"的视频。你也没法拍"我把 _clips 镜像改成了只读代理"。 观众看不到 119 处 except: pass 为什么是问题。

同理，"我做了一个 AI 剪辑软件"这个标题已经被拍烂了——同质化严重到观众划走。 你必须找到别人没拍的切口。

5.2 五个真正能出片的切口

选题爆点为什么它成立（基于代码事实）
① 3D 素模摆姿势 → 分镜 → 成片 极强 Stage3D.tsx 4426 行纯 three.js，15 关节 21 旋转角，5 种群像模板（双人对峙/三人弧形/四人一字/五人围圆），还能导出 BVH。画面冲击力天然极强：观众看着一个火柴人被你摆出"下跪求饶"的姿势，然后它变成了分镜图。这个"丑到美"的转变过程就是视频本身。
② 我让 AI 剪片，但它每改一刀都要我点头 强 反向蹭当前最热的"AI 万能"叙事。agent_policy.py 的三模式权限 + CleanupChecklistDialog 的勾选确认是现成素材。人设是"我故意不让 AI 全自动"——这在 2026 年是个有思辨性的立场，评论区会吵起来。
③ AI 骗了我一次，我就把它所有的"假成功"都删了 强 这是最有共鸣的技术价值观内容。你有真实素材：口型功能标着 TALKING_HEAD_UNAVAILABLE、生图无 Key 返回 ok:False、而构建日志里躺着一个真的静默失败：AutoClip初始化失败: No module named 'bs4'。这个反差本身就是剧本。
④ Ctrl+Z 能不能撤销 AI 的修改？ 中强 技术上你有真货：edit_commands.py 薄指令执行器、_apply_action 的 undo/redo 分支、v4.10.2 刚修完"AI 入轨片段不可撤销"的 bug。可以拍成"我为什么花三天让一个按钮生效"——从 bug 讲到架构，这是硬核向观众最爱看的。
⑤ 1.9 GB 的安装包，我一个一个文件删到 300MB 中 包装优化的性价比之王。ai_video_editor_local.spec 里已经排除了 torch/transformers/onnxruntime/easyocr/librosa 和整个 video_processing（起因是打包触发 0xC0000005 访问违例——这个 bug 故事本身就很上镜）。观众爱看"数字从大变小"。

一个模式值得注意：真正能用的 AI 能力（去水词 / 字幕 / 无损裁 / 高光 / 节拍）都是"确定性的、可验证的体力活"； 而做不出来的（智能重构画幅 / 语义搜素材 / 一键成片）都是"需要判断力的脑力活"。 这不是巧合，这是当前技术边界的真实投影。产品叙事应该顺着这个规律走： "AI 干体力活，人干判断"——既诚实，又刚好是你能做的那部分。

7三阶段路线图

8红线与风险提示

8.1 我建议继续保持的做法（别动）

保持「诚实失败」不动摇

我逐个核对了生成路径，全项目没有一处返回假数据冒充成功。 在 AI 工具普遍注水的环境里，这是一种竞争力。哪怕商业压力上来，也不要为了演示效果做假成功。

保持 _clips 单一真相源

已抽出 editor_export.py、clip_transform.py 等副路径，但它们都只读宿主的 _clips。 画布桥接也刻意不换真相源。这个克制是整个项目最正确的架构决策，别为了"画布更强"而破坏它。

保持冻结区机制

52 个锁 + stability_gate 430 项固化。这是防止"修好又坏"的唯一保险， 而且每次拆分后都用 --update 重写基线，流程是活的。继续保持。

保持「不做」清单

不重写时间线、不换壳（Wails / Tauri / tldraw）、不嵌商业画布、不默认一键成片。 能列出一份"主动不做"清单的项目，通常比功能列表长得多的项目活得更久。

8.2 三个真实风险

①

定位漂移风险（最高）。 文档里"四轨收口"写得清清楚楚，但代码里 app/modules/lego/ 仍堆着 account_widgets / account_analyzer / drama_crawler / viral_optimization_engine / stealth_browser 等一大批"已宣布卸空"的残留。 产品决定说卸载，代码里还留着，下一步人就会忍不住去修它。 建议做一次物理清理，或者在文件头明确标注"接口壳·勿扩展"。

②

静默失败风险。 119 处 except Exception: pass + 打包日志里那条 No module named 'bs4'， 说明"功能悄悄不工作"是这个项目的系统性风险。 用户不会报 bug，他只会觉得"这个软件不太行"。 建议：所有 AI 功能入口加一个"健康自检"按钮，一键列出哪些能力当前可用、哪些缺依赖、哪些缺 Key。 这个功能本身也是极好的内容素材。

③

单人维护的规模风险。 164,754 行代码 + 378 个文件 + 1.9 GB 产物，已经远超一人可长期维护的舒适区。 继续加功能的边际收益在快速衰减，而维护成本在指数上升。 出路只有两条：收缩（删掉非核心模块，把代码量压到 10 万行以内），或者开源（把维护成本分摊出去）。 两条路都通向同一个动作：先让代码少一点。

8.3 一句话收尾

这个项目的问题从来不是"做得不够多"，而是"做出来的东西有一半还没被接上、被看见、被验证"。
下一刀不该加功能，该把已有的 6 个写回能力变成 20 个，然后录一条 90 秒的片子给别人看。
