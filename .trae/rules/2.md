# TRAE AI 编程能力提升总规范

本文件用于补充 `0.md`、`1.md` 的项目硬约束，目标是让 Trae 在本项目中更像可靠的资深工程师：先理解、再动手、少改动、可验证、能回退。

## 一、规则来源

本规范综合以下本地规则与技能原则：

1. `.trae/rules/0.md`、`.trae/rules/1.md`：项目级强制编码铁律。
2. `karpathy-skills`：Think Before Coding、Simplicity First、Surgical Changes、Goal-Driven Execution。
3. `tdd`：红绿重构、行为测试、异常路径测试。
4. `diagnose`：复现、最小化、假设、插桩、修复、回归验证。
5. Qt UI 审查原则：父子窗口、信号槽、主线程 UI 更新、分层隔离。
6. `improve-codebase-architecture`、`cto-agent`：架构边界、技术债、渲染管线和性能决策。

## 二、最高执行原则

1. 未读结构不编码：先确认 `app/core/`、`app/modules/lego/`、`app/ui/`、入口文件和相关调用链。
2. 未懂业务不新增：先理解启动流程、窗口跳转、事件总线、权限状态、信号槽绑定。
3. 最小改动优先：每一行改动都必须服务当前需求，不顺手重构、不顺手格式化、不清理无关代码。
4. 简洁优先：不添加未要求的功能，不为单次使用创建抽象层，不制造过度配置。
5. 目标驱动：所有任务必须有可验证结果，不能用“应该可以”作为结论。
6. 可回退：新增能力必须保留旧路径或明确 fallback，尤其是渲染、导出、AI 调用、登录权限、文件操作。

## 三、开发前标准流程

任何功能开发、修复或性能优化前，必须完成：

1. 定位入口：找到用户操作进入的 UI 方法、核心调度方法、数据流向。
2. 定位最小修改点：优先修改现有扩展点，禁止新建无关文件和绕过现有架构。
3. 明确风险：判断是否影响启动、导出、登录、权限、项目保存、视频处理。
4. 给出成功标准：例如编译通过、启动通过、导出成功、单元测试通过、日志无异常。
5. 不确定就询问：需求含糊、方案代价不同、会影响数据或架构时，必须先确认。

## 四、代码修改铁律

1. 命名：类名大驼峰，函数和方法下划线，变量语义清晰，禁止 `aaa`、`temp`、`test` 等无意义命名。
2. 导入：标准库、第三方库、本地模块分组；本项目优先 `from app.xxx`，必要时兼容 `from xxx` 回退。
3. 日志：核心层使用 `logger`，禁止新增裸 `print()` 作为长期日志。
4. 异常：禁止裸 `except: pass`；异常必须记录日志或给用户清晰提示。
5. 注释：类和核心方法必须说明职责；复杂逻辑补充关键注释；不写解释废话。
6. 文件：不私自调整目录结构，不新增无用文件，不删除原注释和无关代码。
7. 状态：登录、权限、版本、用户信息统一归集到权限/auth相关模块，禁止 UI 层乱放全局状态。
8. 验证：改 Python 文件后至少运行 `py_compile` 或对应测试；改导出/渲染后验证 C++/FFmpeg fallback。

## 五、PySide6 / Qt6 专项规则

1. 弹窗必须绑定父窗口：`QDialog(self)`、`QMessageBox(self)`，禁止无主窗口弹窗。
2. UI 更新必须在主线程，后台线程通过信号槽回到主线程更新界面。
3. `QTimer`、后台 worker、动态窗口必须保存为实例属性，避免被垃圾回收。
4. 信号定义要带类型，复杂槽函数优先使用独立方法，避免 lambda 捕获循环变量错误。
5. UI 层只负责展示、交互和事件分发；耗时处理、文件处理、AI 调用、渲染导出放到 core 或现有引擎层。
6. 按钮点击必须防重复触发，耗时任务要禁用按钮或显示进度。
7. 用户可见错误必须用界面提示，后台细节写日志，不能静默失败。

## 六、架构边界

1. `app/core/`：业务逻辑、状态管理、渲染调度、AI 调用、性能优化。
2. `app/modules/lego/`：界面模块、用户交互、事件总线调度，不写复杂业务算法。
3. `app/ui/`：纯界面资源和样式，不承载核心业务状态。
4. 渲染导出统一优先走 `RenderManager`，遵循 C++ 引擎 -> FFmpeg CLI -> CPU fallback。
5. GPU 检测统一走现有 `GPUDetector` / `HardwareDetector`，禁止重复写硬件检测逻辑。
6. FFmpeg 路径统一复用已有工具层，禁止在 UI 模块里直接拼复杂 FFmpeg 命令。
7. 新能力优先接入事件总线、现有服务、现有管理器，避免跨模块硬编码调用。

## 七、TDD 与验证规则

1. Bug 修复：先复现，再修复，再加回归验证；不能只凭猜测改代码。
2. 新功能：优先写行为测试；UI 像素和样式类改动可跳过 TDD，但必须人工启动验证。
3. 测试关注行为，不绑定内部实现细节。
4. 异常路径必须测：空输入、文件不存在、权限不足、网络失败、模型不可用、导出失败。
5. 每次交付说明必须包含：改了什么、验证了什么、还有什么风险。

## 八、调试和性能规则

1. 先测量后优化：性能问题必须先定位瓶颈，禁止凭感觉重写。
2. PySide6 性能优先检查：主线程阻塞、重复创建控件、paintEvent 过重、信号重复绑定、定时器泄漏。
3. 视频导出优先检查：是否走 `RenderManager`，是否启用 C++ 引擎，是否检测到 NVENC/QSV/AMF，是否 fallback 到慢路径。
4. 大文件处理必须流式或分块，禁止一次性读入超大视频、音频、图片序列。
5. 耗时任务必须有进度、取消或至少不会卡死主界面。
6. 优化必须保留兼容回退：C++、GPU、第三方模型失败时，用户仍能完成基础任务。

## 九、安全和数据规则

1. API Key、Token、用户账号、模型密钥不得写入代码和日志。
2. 文件路径必须校验存在性、扩展名、读写权限，避免覆盖用户重要文件。
3. 网络请求必须有超时、异常处理和用户提示。
4. 插件、脚本、MCP、外部命令必须限定输入，禁止拼接未校验的用户输入执行系统命令。
5. 删除、覆盖、批量移动文件前必须确认范围，不能使用破坏性命令清理工作区。

## 十、AI Agent 工作方式

1. Think Before Coding：先说清楚已知事实、假设和不确定点。
2. Simplicity First：优先小修、小补、小验证，不追求炫技。
3. Surgical Changes：只碰任务相关代码，发现旁边问题先记录，不擅自扩大范围。
4. Goal-Driven Execution：每一步都围绕用户目标和可验证结果推进。
5. 遇到冲突：用户最新要求优先；发现用户改动时不覆盖、不回滚，先协调。
6. 遇到失败：读完整错误栈，复现问题，定位根因，再动代码。
7. 长任务：阶段性反馈进度，说明正在看什么、发现什么、下一步做什么。

## 十一、交付检查清单

提交最终结果前，Trae 必须自检：

1. 是否只修改了需求相关文件。
2. 是否保持 PySide6 分层和现有命名风格。
3. 是否保留旧逻辑或 fallback。
4. 是否处理空值、异常、重复点击、文件不存在。
5. 是否运行了合适的验证命令。
6. 是否说明了验证结果和残余风险。
7. 是否没有泄露密钥、没有执行破坏性命令、没有覆盖用户改动。

## 十二、本项目优先级规则

当不同规范冲突时，按以下顺序执行：

1. 用户当前明确要求。
2. `.trae/rules/0.md`、`.trae/rules/1.md` 的硬约束。
3. 本文件的 AI 编程能力规范。
4. 具体技能文件的专项流程。
5. 通用工程经验。

## 十三、证据优先与防漂移（2026-11-16 补：代码是唯一事实源）

针对 AI 总结架构时"大概说法与代码对不上"的漂移问题，强制以下纪律：

1. **总结必须锚定代码**：架构结论须附 `文件:行号` 引用；无引用的判断标记 `[INFERRED]`（推断）或 `[UNKNOWN]`（未核实），禁止用"大概/应该/通常"替代证据。
2. **先盘点后构建**：生成新架构总结或代码前，先产出差距清单——新需求逐项映射到现有代码最近对应物，标记 ✅直接复用 / ⚠️需改造 / ❌缺失 / 🗑️废弃；未出清单不写码。
3. **文档与代码冲突时先回正**：发现文档描述与真实代码不一致，以代码为准先回正文档再继续开发，不沿错误文档施工。
4. **交付必须附可验证证据**：声称"已完成"时给出改动文件清单、实际运行的验证命令与真实输出（py_compile / 门禁 / 冒烟日志）；给不出证据视为未完成。
5. **新鲜度自检**：开工前核对 `git status` 与目标文件真实内容，不直接引用旧会话或旧文档结论；防漂移复用现有门禁（`stability_gate` / `frozen_zone_guard` / `run_all_checks` + pre-commit），**不引入外部索引数据库、不新增常驻文件监视器**。
