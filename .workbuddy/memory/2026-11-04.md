## 第 2 条：拉取前先另存 + 拉完自动认领（画布 0.3.47，提交 e12e9b15）

**真问题**：拉取是覆盖式，`loadProjectBundle()` 换掉内存画布、几秒后自动保存把同一个工程 id 的本机
存档也写成新内容 ⇒ 用户那一版**从此不存在任何地方**。二次确认只能拦手滑，拦不住「我以为我上传过了」。

**做法**：新文件 `teamBackup.ts::backupBeforePull()` —— 把**内存里**的画布复制成新 id 的本地工程
（名字「X（覆盖前 11-04 15:20）」），写进 localStorage 工程索引 ⇒ 直接出现在「我的画布」里。
🔴 **不自造快照格式、不做恢复面板**：本地工程本来就是 bundle，另存＝复制新 id + 改名，走现成链路。
🔴 不能用「上次自动保存的存档」当备份（有延迟，少存最后几秒，而那几秒正是用户心疼的部分）。
🔴 配额顶满必须 `ok:false` 并再问一次，**不许假装存好了**。

**拉完自动认领**：`claimNote()` 返回一句说明而不是自己 `say`（`say` 只有一行，连续 say 会互相覆盖）。
锁被别人占着不抢、不算失败，只提示「锁在 X 手上，上传时可能撞」。

**测试教训**：`backupBeforePull` 少一个 `canvases`/`activeCanvasId`，用户在「我的画布」打开备份就是
空画布，而这条路径平时没人走。所以测试必须**往返**（写进去 → `readProjectBundle` 读回来断言节点还在），
不能只测名字。vitest 无 jsdom ⇒ 自造最小 localStorage 桩 + `useCanvasStore.setState` 灌状态。

## 第 3 条：历史版本 + 回滚（画布 0.3.48，提交 57898d91）

**发现的两个真空洞**：① 服务端 `GET /team/projects/{id}/versions` 一直存在、`version.message` 一直在存，

**回滚语义（想清楚再写）**：历史**只增不删** —— 回滚＝又提交一版旧内容（rev+1，备注「回滚到 rev N（谁）」），
**不是**删掉后面的版本把指针退回去（那会把同事这之后的工作直接抹掉）。`push`/`rollback` 共用 `_publish()`。
`base_rev` 不符 ⇒ Conflict（防止「看着 rev 3 的旧界面」把 rev 4 盖掉）。

**顺手补的静默覆盖洞**：`pushTo` 原来用项目列表里的 `p.rev` 当 `base_rev`，而那是刷新那一刻的值，
中间别人提交过它不变 ⇒ 闷着盖掉别人的版本。改成优先 `localRevOf(projectId)`。

**验证**：pytest 39 passed（+4）；真 HTTP 端到端脚本 `.workbuddy/tmp/rollback_e2e.py`

## 配对收窄为两条路（画布 0.3.51 · 提交 0eef7ef）

**用户问的**：「目前是靠 6 位数配对码，还是还有一个网络链接的配对方式？二维码取消掉，只保留这两种。」

**答的现状**（核实过，不是印象）：加入有 **3 条路**（6 位码 / 扫局域网 / 手填地址），

同一个东西的第三种壳。`pair_url` 落地页 `/pair?code=` 只做「复制地址 + 看名额」，不假装手机能加入。

**发现的真缺口**：链接**只在发出端存在** —— 卡片上有「复制邀请链接」，但同事收到 URL 后
软件里没地方粘（`teamJoin` 会把 `...?code=` 拼成非法路径）。所以「保留链接方式」= 必须补接收端。

**做法**：
- 后端 `_pairing_payload` 去掉 `qr` + `_qr_cached` + import；删 `team_qr.py` 与其测试（-2 文件）
- `/pair?code=` 落地页**保留**（是链接的落地页，不是二维码的）；文案「重新扫一次」→「把完整链接再发一次」
- 新文件 `teamInvite.ts::parseInvite()` 纯函数：6 位码 / 带码链接 / 光地址，三种粘贴形态一次认出，
  不联网不猜；`kind:none` 必须给 `why`
- `TeamPanel`：② 段输入框改「6 位配对码，或粘贴邀请链接」；新增 `joinByLink()`——**链接里带地址就直接换令牌，
  不发 UDP 广播**（跨网段/对方禁广播时这一跳是唯一能通的）；`join()` 也先 parseInvite 再分派
- 顺手清两处旧账（HEAD 就有的 ruff F401/F841）

**验证**：pytest 43 passed；vitest 782 passed（+13 teamInvite）；tsc 37；棘轮 10-10-5；稳定性 clean；
冻结区 106 锁；19 道门禁全绿；dist 重建后「二维码」0 命中。

## 产品战略三问 + 试玩版α原型（21:20-21:35）

**背景**：用户问「往后几年还有优势吗 / 能做什么 / 订阅制怎么运营」，随后追问
「买断一次用户群小利润不够」「本地部署没法收回，测试用户多了怎么办」。

**答出的三个判断（要记住结论，后续别推翻）**：
1. 优势不在模型层（Sora 已两次关停：2026-04 网页版、2026-09 API）⇒ 钉在单一模型上是负资产。
   真正站得住的是：① `app/core/neural/kernel/adapters/` 四族（sd15/sdxl/svd/wan）的**调度层**
   （换模型不改上层，越换代越值钱）② 画布→分镜→3D 机位→时间线→成片的**闭环**（别人各占一段）
   ③ **本地可控**（素材不出内网 / 成本可预算 / 离线）—— 代价是背显存兼容的锅。
2. 能做什么分三档：现在可交付（图生图 GGUF、svd、wan 适配器、图像编辑 5 件套、110 条 capability、
   精剪、3D 导演台、团队协作）/ 能用但标边界（跨镜头一致性、长时段要分段、3D 角色非可雕刻 mesh）/
   宣传口径禁说（「AI 导演」自动出片、「22 万行」）。
3. **成本结构反转**：竞品边际成本=GPU 时长 ⇒ 必须卖额度（Descript $35 含 800 积分、剪映 199 元含 22100 点）。
   你跑客户自己的卡，边际成本≈0 ⇒ **绝不该卖额度**，卖席位 / 能力包 / 维护年付。
   `viewer` 免费是杀手卖点（甲方零成本进来提意见）。

**买断制的正解（用户顾虑的解法）**：
- 小用户群的病不是「买断」，是「单价低 × 客户数少」。三条路线算过：走量 B2C 89 万一次性 /
  小群高单价 31.8 万 / 混合漏斗 22.6 万首年 + 15 万次年。天花板都不高，但对比他现在 6-10 万/年已够。
- 结构 = **永久授权（获客门槛最低）+ 年度能力包自愿续费（补复购，不做强制校验）
  + 服务包（前期现金流）**。关键：能力包不写授权系统，靠新适配器的实际价值驱动。
- 高单价的敌人不是客户数，是**服务成本** ⇒ 把 `device_profile.py`/`accel_status.py`/
  `capability_manifest.py` 做成「启动前体检报告」，把 80% 的「我跑不动」变成用户自己能读懂的一行字。

**本地部署收不回的解法（核心结论）**：
🔴 **不要纠结「能不能收回」，要设计「给出去的是什么版本」。**
- 你手里比远程锁更强的武器 = **更新通道**：模型三月一换代，试玩版停更一季就自动掉队。
  这不侵犯用户，只是「不再投资源」⇒ 软收回。
- 阈值规则：1-30 人 = 元老终身授权（名额提前定死并公开）；31-100 人 = 正式版 5 折；100+ = 只给 beta。
- **铁律：绝不扣作品**。限的是「继续生成的能力」，不是「已经生成的东西」。
- 50 人以内免费送完全划算：损失 ≈ 50×3980 ≈ 20 万，换回的是显存兼容数据，能救掉几十万的开发弯路。

- 游戏内测三要素落地：**有限边界（4 关到底）+ 强制引导（每关一个任务 + 完成判定）+ 数据回收（右侧实时埋点）**。

  → 2 三镜成段（时间线/转场）→ 3 3D 机位（4 预设）→ 结束页（埋点汇总 + 3 题问卷 + **试玩版 vs 正式版差异表**）。
