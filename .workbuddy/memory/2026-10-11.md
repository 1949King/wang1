## 磁吸/ComfyUI 生态对比分析（纯分析，无代码改动）

- **本质区别定位**：ComfyUI = **显式图**（拓扑即程序，边携带类型语义，可分享/复现/交易）；
  拾光小白 = **意图编译**（拓扑是编译产物，关系从几何邻近推断）。这是产品品类差异，
  不是功能多少的差异 —— 不能用 ComfyUI 的「节点多」标准去套。
- 关键机制证据：`bonds.ts:24-26` 咬合判据（边距 0 + 投影重叠 ≥40px，纯几何不落盘）、
  `SoftConnection.ts:4-8`（磁吸到 strong 自动生成「潜在血缘」虚线，点固化才转正式 edge）、
  `types.ts:57-63`（**方向语义已被剥离**，left/right 不带业务含义，属 2026-09-18 方案 A）。
  ⇒ 空间只表达几何形态，语义由卡片类型 + 节点数据承载，这是「意图编译」的地基。
- 五档磁吸（types.ts:9）+ 让位 reflow 三条红线（reflow.ts:26-30）= 手感资产，
  ComfyUI 完全没有这一层（它不需要「让位」，图是显式连出来的）。
- **生态现状**：插件机制已存在（`src/plugins/`：types.ts 定义 CanvasPlugin 契约
  {id,name,version,minAppVersion,nodes[],css?,setup?}、plugin-loader 从 URL fetch→
  Blob→import()、node-registry 统一注册 + ownerByType 追踪 + unregister 按 pluginId 清）。
  但 examples/ 只有 1 个 sticky-note.tsx，且**无 market/registry/版本冲突处理**。
- 结论方向：要达到 ComfyUI 生态量级，**不是加节点**，是补三件套 ——
  ① 节点包市场（manifest + 版本约束 + 一键安装）② 工作流/配方分享（图 + 模型 + 参数打包）
  ③ 稳定的节点契约（当前 CanvasPlugin 已具备雏形，缺「输入输出端口类型声明」，
  这是与 ComfyUI 生态对接的最大缺口 —— 现在的节点只是「卡片外观」，没有 wire 契约）。

## 小白模式优化方案（意图编译范式 2.0）

## ⚠️ 原型 v2 被用户否掉 —— 教训记牢

用户原话：「设计很一般，而且小白模式里面的卡片的所有卡片类型你放哪去了？」

**我做错的事**：v2 只在左栏放了 8-10 个「意图入口」，把 13 种卡片（config/prompt/text/markdown/
note/group/shotlist/storyboard/panorama/digitalHuman/animation/script/source等）**藏进"更多"**，
理由是「小白认知负荷」。这是**越权**——用户明确要求「包含小白模式已有的所有功能」，
我却用自己的产品判断替换了他的判断。

**正确做法（v3 已改）**：21 种卡片**一种不少全部放回左栏**，改用「按创作阶段分 7 组」组织：
开始创作 / 做画面 / 做声音 / 摆位与实拍 / 批量与设定 / 素材与笔记 / 整理。
分组是**组织方式**的改变，不是**可见性**的减少 —— 这是分界线。

**通用纪律（写进 MEMORY 级）**：优化「降低门槛」类需求时，
**不得替用户决定「他不需要这个功能」**。正确做法是「让全部功能可达，但改变呈现方式」。
把「减少可见性」和「改善组织方式」搞混，是产品越权。

### 根因
**PyQt6 的 `QColor` 没有 `(name: str, alpha: int)` 重载**。合法只有 `QColor(name)` 单参
（alpha 默认 255）或 `QColor(r,g,b,alpha)` 四整数。V4.43.4 误写 `QColor("#fff", 80)`。
修法 = 用本文件已有的 `_rgb(hexv, alpha)`（内部 `QColor(name)` + `setAlpha()`）。

### 为什么 11 道门禁 + 4 次 offscreen 全没抓到
| 检查 | 为什么漏 |
|---|---|
| ruff 棘轮 | 不做类型检查 |
| AST scope（SCOPE） | 扫「未定义名字」，`QColor` 是已导入的合法名字 |
| 单测 | 零覆盖 `paintEvent` 运行时绘制 |
| tsc / vitest | TS 侧，与 PyQt 无关 |
| **offscreen ×4** | **设置对话框没打开 ⇒ `_PresetPreview.paintEvent` 压根不触发** |

### 永久纪律（已写入 CHANGELOG V4.43.5 + version.py description）
1. **静态门禁全绿 ≠ 运行时没崩**。自绘控件（QPainter/QColor/QPen）改动的交付标准 =
   **真机启动（不带 offscreen）+ 打开该界面让 paintEvent 真跑一遍**。
2. **不要再把 `QT_QPA_PLATFORM=offscreen` 当成"启动验证"** —— 它掩盖一切绘制类崩溃。
   offscreen 只适合验证「进程能不能起到事件循环」，不能替代视觉/绘制回归。

## V4.43.7 主题切换不生效根治 + 预设卡点击穿透（HEAD `07a7f16`）

### ① 主题切换不生效 → 根因（重要，通用 Qt 坑）
- `ThemeManager._apply_theme_property()` **只 setProperty 不 repolish**，注释称
  「依靠 setStyleSheet 自动生效」—— **错的**。
- 决定性实测（offscreen，QPushButton + `[theme]` 属性选择器）：
  ```
  初始 dark          → #000000
  只 setProperty     → #000000   ← 期望 #ffffff，没变！
  unpolish+polish 后 → #ffffff   ← 正确
  ```
- 迷惑点：`_do_apply_theme` 先 setStyleSheet 后改属性 ⇒ 界面停在旧主题；但 ThemeManager
  内部状态**正确交替**（日志 light→dark→light… 看着全对），所以「日志正常但界面没变」。
- 修复：`_apply_theme_property` 内补 `unpolish/polish`（+ 属性未变则跳过省开销）。
- **教训**：Qt 里改**动态属性**后必须 repolish，`[prop="x"]` 选择器不会自动重算。
  这是「内联/属性样式不生效」类问题的通用病根。

### ② 点预设卡没反应 → 根因
- `_PresetPreview`（自绘 QWidget，覆盖卡片绝大部分面积）**吞掉 mousePressEvent**，

- **教训**：自绘子控件盖在可点父控件上时，**必须**设鼠标穿透，否则父控件永远收不到点击。

### 本轮最有价值的三个「实测发现」（可复用）

**① PyQt6 + opentimelineio = 段错误 ⇒ OTIO 必须进程隔离。**
`import PyQt6.QtCore, opentimelineio` → access violation；**反序**（`import opentimelineio, PyQt6.QtCore`）→ 正常。
结论：opentimelineio 的 C 扩展在 Qt 之后加载会崩，而 GUI 进程必然先加载 Qt ⇒ OTIO 读写全部丢进
`_otio_worker.py`（`python -m app.core.interchange._otio_worker`）这一**无 Qt 子进程**，主进程只经临时 JSON 文件交换数据。
这与项目一贯的 `wmic` / `ffmpeg` 隔离是同一个范式。**验证标志 = 在 PyQt6 已加载的进程里跑完导出+回读且 `SURVIVED`（无段错误）。**

**② 噪声会伪装成「清晰」。** 五维评分器原有的常量 70 基线之外，我加的真像素测量里，
未处理时**噪声图的 composite 85.8 反而压过真清晰图的 61.6**，且所有图 sharpness_score≈0。
根因：Laplacian 方差对噪声极敏感。修法两步：先 `medianBlur(3)` 压噪，再**经验标定**减去噪声贡献 ——
实测该系数在 σ=5..40 区间稳定在 **2.29**（实测 2.397/2.328/2.302/2.300/2.293/2.287/2.276，±2.6%），
即 `sharpness = max(0, lap.var() − 2.29·noise²)`。修后：清晰 composite 83.4/sharpness 96.3 ＞ 强噪声 79.6/90.7。
（噪声本身要在**原分辨率**上测算，不能在缩放后 —— 缩放会把噪声抹平。）

**③ 官方 `ruff_gate.py` 对「未跟踪新文件」不强制 0 违规 —— 有盲区。**

### ⚠️ 行尾坑（冻结文件尤其致命）

### 关键技术突破：SSH over 443 是唯一可用推路
- **`gh-proxy.com` 是死路**（决定性反例）：它对 GitHub 的 `/user` 会**无视请求方 `Authorization`**、
  用**自己的服务端凭据**去访问 ⇒ 同一个 token 在不同时刻返回 `aeroheaven1` / `HHPLow`（都是中继方账号），
  用**假 token** `ghp_0000...` 也照样返回 `HHPLow`。⇒ **匿名只读中继，无法认证成用户本人，永远推不上去。**
  （曾据此误判"用户 token 不是本人的"，实为误判，已向用户更正。）
- **正解 = `ssh.github.com:443`**：`~/.ssh` 空、22 端口 refused，但 **443 端口 SSH 握手完全正常**
  （`Permission denied (publickey)` = 链路通）。加公钥后 `ssh -T` 回 `Hi 1949King!`，push 成功。
- **推送命令范式**：
  ```bash
  export GIT_SSH_COMMAND="ssh -i /path/key -o StrictHostKeyChecking=no -o IdentitiesOnly=yes -p 443"
  git remote add origin git@ssh.github.com:<user>/<repo>.git   # 注意不是 git@github.com
  ```

### filter-repo 关键坑（本轮踩到）
1. **每次 filter-repo 执行都会删掉 remote**（防误推回原仓库）⇒ 推之前必须 `git remote add` 补回。
2. **`--invert-paths` 是纯排除**，想中途"加回某些文件"**做不到** ⇒ 正解 = `git archive HEAD <paths> | tar -x -C <目标>` 导出到工作区，再 `git add` + 普通 commit 推送（保留原有提交，只多一个新提交）。
3. **`--prune-empty never` 也挡不住"整个提交内容被剔光"** 时提交被删 ⇒ 152 → 149。

## GitHub CI 整改（方案 C · 已完成，commit `ad3ee92`）

### 现象
