## 1. 架构总览

### 1.1 一句话定位

**这不是"一个引擎"，是"一套可替换的执行栈 + 一本跨模态显存账"。**
栈可以换（diffusers / diffsynth / 将来的自建实现），账不能乱（谁占了多少 GB、为什么被赶走，必须可查）。

### 1.2 目标形态（T）与当前形态（T0）

| 层 | 目标（T） | 现状（T0，2026-10-28 实测） | 差距 |
|---|---|---|---|
| 入口 | 一行三元切换，新老路径互斥 | `diffusers_image.generate()` / `video_gen.generate()` 直调 `pipe(...)` | 无切换点 |
| 执行 | **自研循环**（唯一 `for t in timesteps`） | 循环在 `diffusers/pipelines/*/pipeline_*.py` 内 | 全仓 `scheduler.step` 命中 **0** |
| 适配 | 族语义集中在 adapter | 语义散在 3 个引擎文件（1205 + 927 + 1289 行） | 未拆 |
| 组件 | `ComponentBag` 只取零件，不调 `pipe()` | 直接持有整条 pipe | 未拆 |
| 资源 | 跨模态统一账本 + 仲裁 | 只有 `memory_policy` 决策 + 视频 LRU 让位，LLM 侧无让位能力 | 部分 |
| 治理 | 66 条引擎全部声明能力 | `EngineSpec` **14 字段**（9 观测 + 5 能力；quant/offload_tiers/step_cache/verified/loop_owner 全部带诚实默认值） | ✅ 2026-10-28 P0 |
| 证据 | 每次优化有实测台账 | 有 `quant_descriptor`（量化）、无时延/显存台账 | 部分 |

**结论**：T0 → T 的距离不是"写多少代码"，而是**把控制权从 3 个 1200 行文件里一点点拆出来**。所以本架构的第一原则是「不动业务、只拆边界」。

## 2. 运行时：一次生图请求的 12 步

这条链是架构的"体检表"——哪一步缺，架构就缺一块。

| # | 动作 | 归属层 | 现状 |
|---|---|---|---|
| 1 | 画布发 `/host/generate-image` | 画布 | ✅ |
| 2 | 路由 mixin 分发（`canvas_route_registry` 表 → 老 if 链） | 入口 | ✅ |
| 3 | `execution_planner.plan()` 选栈：diffusers / diffsynth / cloud | 决策 | ✅ |
| 4 | `quant_descriptor.is_admissible(precision)` 挡掉已否决精度 | 决策 | ✅ 新增 |
| 5 | **`ResourceBroker.claim()` 申请显存 → 必要时让位** | 资源 | 🟡 MVP 已验证，未入项目 |
| 6 | `memory_policy.pick_memory_policy()` 决定装载档（whole/model/sequential/layer） | 决策 | ✅ |
| 7 | `load()` 取组件袋（不调 `pipe()`） | 后端 | ❌ 仍 `pipe(...)` |
| 8 | `cache_gate` 决定步缓存/编码缓存是否启用，attach | 内核 | ✅ 但靠 hook 数步 |
| 9 | **denoise loop**（encode → init → N×step → decode） | 内核 | ❌ 在 diffusers 内 |
| 10 | `vram_ledger` 记账 5 分项 | 资源 | 🟡 模块已落地（P0），尚未接进 generate 路径 |
| 11 | 落箱 / data URL 兜底 / 遥测 | 入口 | ✅ |
| 12 | `claim.release()` + 让位记录归档 | 资源 | 🟡 MVP 有 |

**读法**：第 5、7、9、10 步是本次架构要补的，其余是既有能力（不要重写）。

## 4. 七条关键设计决策（含被否决方案）

### D1 · 拿循环，不拿算子

- **决策**：自研 `for t in timesteps`；UNet/DiT 前向、scheduler 数学、VAE 解码全部用上游。
- **理由**：Python 层重写收益 <5%（设计稿 §5 实测）、CUDA Graph 0.33×（`accel_status.py:36-37`）；收益来自**结构**（跳步/预取/合并前向），而结构必须在循环里改。
- **被否决**：自写 UNet 前向、自写 CUDA kernel（L4）——ABI 连锁 + 8GB 卡无实验空间。
- **代价**：要吃透每族的循环语义（SD1.5 15 条 / SDXL 9 条 / SVD 13 条 / Wan 10 条隐性项）。

### D2 · 契约归我，语义归适配器

- **决策**：`GenRequest / AdapterCaps / ParityContract / DenoiseResult` 由本仓库定义并版本化；族差异全部落 adapter。
- **理由**：这是 C2（契约所有权）与 C3（上游可替换）的唯一实现方式。上游改名只改 adapter。
- **被否决**：契约层也管条件编码——会把契约变成条件仓库（SD1.5 单 TE / SDXL 双 TE+pooled+time_ids / Wan T5+seq_len 差异过大）。
- **代价**：每个族要填 `AdapterCaps` + `ParityContract`，接入成本从"写一个函数"变成"填两张表"。

### D3 · 双栈不合并，只统一契约

- **决策**：diffusers 为主体（唯一自研循环对象）；diffsynth 走契约兼容 + **有触发条件的接管预案**；两栈不合并代码。
- **理由（实测）**：diffusers 0.42.1（2026-10-27 发版，间隔 4 天）活跃；diffsynth 正式版停 0.7.0、dev 流 2026-05-27 后无新版 ⇒ **风险性质不同**（漂移 vs 停更）。diffsynth 的循环本体只有 3 行（`sdxl_image.py:448/469/492`），接管收益极低、前置逻辑要复刻约 75 行。
- **被否决**：把 diffsynth 也纳入自研循环（收益≈0、风险高）；只做 diffusers 完全不管 diffsynth（它真停更就没退路）。
- **代价**：跨栈结果**不可比**（采样器不同）⇒ 验收只能同栈对照，跨栈只做人眼。

### D4 · 资源层跨模态统一，执行层按模态分离

- **决策**：显存仲裁/账本/请求取消跨模态统一；去噪循环与自回归循环**各自独立**。
- **理由（MVP 实测，2026-10-28）**：8GB 卡实际可用 6.94GB；声明 LLM 常驻 5.2GB 后只剩 1.74GB，申请 SDXL 5.2GB 缺口 3.46GB ⇒ 必须仲裁才有"生图+对话共存"。而三类模型的步语义根本不同（时间步 vs token 位置），同一份 `for` 必然扭曲。
- **被否决**：一个循环跑所有模型（抽象泄漏）；LLM 侧自研执行内核（vLLM/llama.cpp 已做到极致，纯亏）。
- **代价**：LLM 侧只能整模型让位（Ollama 无部分卸载），缺口 3.46GB 要让 5.2GB，**多让 1.74GB**。

### D5 · 钉版 + 快照守卫，不跟版

- **决策**：diffusers 钉 0.40.0 / torchao 钉 0.16.0 / torch 2.6.0+cu124；季度评估一次。
- **理由**：全部标定基线（SDXL 5.21GB/27.9s、SVD 40s、四档显存）都在 0.40 上测得，跟版 = 基线全废。torchao 更硬：0.17+ 要 `torch ≥ 2.11`，而 Windows 上 ≥2.11 只有 cu130 轮子。
- **被否决**：跟随最新（基线天天失效、快照天天红）。
- **代价**：吃不到新特性。~~`requirements.txt` 现在连 diffusers/torch 都没写，要先把"钉"落地成文字。~~
  **2026-10-28 已落地**：pin 写进两份清单 + 守卫 ⑰ 守住（见 §8 P0 落地说明「钉版」）。

### D6 · 证据先行，负收益也登记

- **决策**：任何优化进主路径前必须有：对照实验（同 prompt/seed）+ 质量判据 + n≥5 + 反例验证 + 回退路径；不合格写 `rejected` 并留原因。
- **理由**：`int8` 就是活案例——显存省 43.4%（SDXL 4.78→2.71GB）看起来很香，实测 PSNR 5.29、整张全黑。没有台账就会再试一次、再崩一次。
- **被否决**：先上再测（本项目最反感的"静默降级"温床）。
- **代价**：每项优化多花 0.5~1 轮做对照。

### D7 · 自研引擎先并列备用，不切主路径（2026-10-28 定稿）

- **决策**：现有画布推理引擎（`diffusers` 主选 + `diffsynth` 兼容）**保持不动、继续担任主路径**。
  自研引擎以「**并列备用通道**」形态存在——不替换、不改写任何现有生成代码，通过开关启用，可与现路径同批对照。
- **理由**：自研路径尚未验证。直接切主路径 = 拿用户真实生成任务做实验，这违反 D6（证据先行）。
- **从「备用」升为「可选主选」的判据（四条全满足才允许）**：
  1. 同批 prompt/seed 与现路径 A/B 对照，**质量保持率 ≥ 85%**（口径见 `推理引擎设计规范.md` §11）
  2. 显存峰值不高于现路径
  3. 全量门禁通过，且不触冻结区
  4. 有明确回退开关，可一键退回现路径
- **关于「两个合成一块」**：维持 D3 现状，**不合并**。理由已在 D3 写明——两栈循环本体差异使合并收益≈0、风险高。
  若后续确有合并需求，再单独立项评估，不在本轮范围。
- **代价**：两套路径并存，维护成本上升。但二者运行在同一契约下（`GenRequest` / `AdapterCaps`），
  差异收敛在 adapter 层，不产生分叉逻辑——这正是 D2/D3 铺好的地基。
- **被否决**：立刻替换主路径（未验证就上，风险不可控）；两栈代码级合并（D3 已否决）。

## 5. 跨模态资源层（ResourceBroker，MVP 已验证）

### 5.1 结构

```
claim(owner, modal, gb, priority)
  → effective_free()                     # 原始读数 − 未体现的声明值（扣减只在唯一一处）
  → plan_eviction(claims, need, free)    # 纯函数，可单测，输出 候选+让出量+reasons
  → _evict(claim)                        # 可插拔执行器：llm / diffusion / video
  → 重新读数 → 准入 or 诚实失败
  → ledger（claims + evicted + reasons）
```

### 5.2 优先级与让位序

| 优先级 | 值 | 适用 |
|---|---|---|
| 前台交互 | 100 | 用户正在等的对话/预览 |
| 交互 | 60 | 用户主动点的生图 |
| 批量 | 20 | 抽卡/批量任务 |

同优先级时让位序：`batch > video > image > text`（视频重建成本最高但可中断性最好；对话是"随时可用"的心智，最后动）。

### 5.3 三个必须写进代码的事实

1. **`load()` 不等于占显存**：SD1.5 `load()` 后 `memory_allocated()` = 0.00GB（offload 档惰性上卡）。⇒ 仲裁必须用**标定过的申请值**（`vram_budget.required_gb`），不能用"load 后差值"。
2. **扣减只允许发生在一处**（MVP 第一版踩坑：`mem()` 和 `effective_free()` 都扣 ⇒ 可用算出 0GB）。
3. **差值测量必须同口径**（MVP 第二坑：前用扣过的值、后用未扣的值 ⇒ 算出 0.00GB）。

### 5.4 缺口（诚实）

- LLM 侧只能整模型卸载 ⇒ 粒度粗，平均浪费 = 让出量 − 缺口（实测 1.74GB）。
- 本机 Ollama 不可达 ⇒ 真实卸载路径**未验证**，MVP 里是 `simulated=True` 的声明值。
- 抢占式仲裁（正在跑的任务被更高优先级打断）**未设计**——现在只做"准入前让位"。

| 包 | pin | 说明 |
|---|---|---|
| `diffusers` | `==0.40.0` | 主栈 |
| `transformers` | `==5.14.1` | |
| `accelerate` | `==1.15.0` | |

三条纪律：

1. **AI 推理栈一律 `==`，`>=` 不算钉版**。`>=` 只能保证不更老，不能保证不漂。
2. **两份清单不许各自为政**：`requirements.txt`（文件自称与 app 对齐）与 `app/requirements.txt` 的 pin 必须逐条相等，

3. **torch 与标定档案联动**：`calibration.make_key` 含 torch major.minor ⇒ 升 torch 即档案失效、必须重标。
   所以升 torch 不是改一行 pin 的事，是「升级 → 重跑标定验收 → 改 pin 一起提交」。

守卫 ⑰ 把这三条变成可执行的：文件间一致 + 与实际安装一致，任一不符当场红灯。
**合法升级路径是「升级 → 重跑验收 → 改 pin 一起提交」，不是静默漂移。**
补它要先把本机实测版本钉对（torch 2.6.0+cu124 / diffusers 0.42.1），属独立小任务，
不在本轮硬塞 —— 钉错版本比不钉更坏。

**三条口径（都是实测逼出来的，不是设计洁癖）**

1. **「腾出多少」一律实测 delta，不信自报**。Ollama `/api/ps` 自报 `size_vram=2.92GB`，
   nvidia-smi 实测占用 **3.66GB** ⇒ **低估 0.74GB**（CUDA 上下文不自报）。
   故 `release()` 前后各测一次池子，差值才进账；源自报的值只写 note。
   实测校验：估算 3.62 vs 实占 3.65，**偏差 +0.03GB（0.8%）**。
2. **判「够不够」取两读数里更保守的**。同机 `torch.cuda.mem_get_info()` 比 nvidia-smi
   **稳定高 0.54GB**（空载）；更关键的是 **LLM 占了 3.66GB 时 torch 仍报 6.94GB 不变**
   —— 它对本进程之外占用基本无感。偏乐观正是危险方向（以为够 ⇒ 不让人让位 ⇒ 挤爆）。
   故取 `min(torch, smi)`；nvidia-smi 不可用（非 NVIDIA/MUSA）时退回 torch 并如实记 `smi=None`。
3. **让位是优化不是前提**。任何失败只让 `ok=False` + note，绝不抛给正在加载权重的调用方。

**真机验收读数**（`python scripts/verify_broker.py`，RTX 4060 Laptop 8GB / qwen3.5:4b）

`diffusers_image.load('sd15-t2i')` 先让 LLM 让位再加载，**`ok=True`，LLM 列表清空**。

   但它让的是**内存**（offload 权重在 CPU），不是显存；而视频生成自己就是那个缓存的主人，
   叫自己让位没意义。故它作为 broker 的 `pool=ram` 来源登记（`cost_s=40`，比 LLM 的 5.5 贵 ⇒ 后让位）。

### P1.5 · `probe_vram` 对别的进程占显存无感（**已修** · 方案 A）

`memory_policy.probe_vram()` 用 `torch.cuda.mem_get_info()`。实测：**Ollama 占 3.66GB 时它仍报 6.94GB**
（与空载一模一样），而 nvidia-smi 报 2.74GB。

影响是具体的：`memory_policy.py` 的标定档案安全闸判据是 `peak > free_gb`。
`free_gb` 虚高 ⇒ 闸门放行一个实际装不下的方案 ⇒ 在这台机器上的失败方式**不是 OOM，而是 WDDM 换页**
（2026-10-25 实测 68.9s/步、可用 327MB）。不报错、只慢 50 倍，比 OOM 更难发现。

**2026-10-28 已按方案 A 修**（全链一次性变保守）：

- `memory_policy.nvidia_smi_free_gb()` 新增：起 subprocess 查 nvidia-smi，**1s TTL 缓存**
  （每次决策起进程 ~150ms 太贵；显存格局不会在 1s 内反复重塑决策）。
- `probe_vram()` 的 `free_gb` 改为 `min(torch, nvidia-smi)`，同时保留
  `torch_free_gb` / `smi_free_gb` 两个原始读数供诊断。
- nvidia-smi 不可用（非 NVIDIA / MUSA）⇒ 退回 torch 单读数，`smi_free_gb=None` **如实标注**。
- `resource_broker._smi_free_gb()` 改为委托同一实现，**不复制第二份 subprocess 逻辑**。
- 测试 `test_probe_vram_conservative.py`（17 项）：取小值 / 两读数都保留 / 四条降级路径 /
  缓存命中与 `force` 绕过 —— 全部用假 torch 注入，不依赖本机显卡。

**A/B 实证（同一台机器，broker 关闭，只让 LLM 占显存）**

| 场景 | 修复前（只看 torch） | 修复后（取 min） | 安全闸结论 |
|---|---|---|---|
| 空载 | 6.94GB | 6.55GB | 放行档案 `whole_gpu`（3.19GB 装得下）**正确** |
| LLM 占 3.66GB | **6.94GB（一点没变）** | **2.89GB** | 「档案需 3.19GB，当前空闲仅 2.89GB ⇒ **降级走规则决策**」 |

修复前第二行会放行 `whole_gpu`（3.19 < 6.94），实际只剩 2.89GB ⇒ 撞 WDDM 换页。
修复后闸门如实拦下并降级到 `model_offload`。**这就是这次改动的全部意义。**

**为什么选 A 而不是 B（只改安全闸那一处）**：B 会让同一文件里两处口径并存
（`probe_vram` 给策略、`read_pool` 给闸门），将来必然漂移；而偏乐观的影响面
不只在安全闸——任何 `pick_memory_policy` 的调用方都吃这个数。一处修好，全链受益。

**代价**：决策链上多一次 subprocess（有缓存摊薄）。**回退**：`SHIGUANG_BROKER=off` 不影响本修法
（它改的是 `probe_vram` 本身）；真要退回旧行为需改代码，故已用 17 项测试把语义钉死。

**落地过程中被实测抓出的四个缺陷**（都是"不报错、只出错结果"那类，已各配单测）：

1. **`bind()` 与 `validate()` 顺序死锁**：`validate()` 头一条就查"未 bind 组件袋"，
   而引擎是先体检后绑定 ⇒ 内核**永远拒绝**。拆成 `validate_caps()`（绑定前）/`validate()`（绑定后）。
2. **漏了推理态**：上游 `pipe.__call__` 挂着 `@torch.no_grad()`，自写循环里没有它。

   里的 `numpy()` 直接抛 `Can't call numpy() on Tensor that requires grad`。
   统一收进 `kernel/grad_mode.py`（用 `no_grad` 而非 `inference_mode`：后者产出的推理张量
   出了作用域再被原地改会抛异常）。
3. **执行设备判据取错地方**：`next(model.parameters()).device` 在 `offload=model` 下是 **cpu**
   （权重常驻 CPU、靠 accelerate 钩子在 forward 时搬），于是 latents 造在 CPU、
   UNet 输出在 CUDA，错误在 `scheduler.step` 的一行减法里炸。
   改问上游 `_execution_device`（`pipeline_utils.py:1152`，专为 offload 提供）。
   **只跑 SD1.5 时这个坑完全不显形**（它走 `whole_gpu`）—— 这就是"只测一族也算假绿"。
4. **空负向提示词被改成 `None`**：SDXL 的 `negative_prompt=""` 与 `None` 编出的负向条件
   实测差 `max|Δ|≈854` ⇒ 每步偏 2.5、PSNR 掉到 23dB。stock 路径是**逐字透传**，
   内核必须一致（两族都不许写 `or None`）。

## 8. 度量体系（六个 KPI，全部可自动采集）

| KPI | 定义 | 采集点 | 目标 |
|---|---|---|---|
| K1 张量一致性 | 逐 step `max|Δ|` vs stock | `kernel/instrument.py` | ≤1e-3 |

| K3 时延比 | kernel_median / pipe_median（n≥5，交错） | 同上 | ≤1.00（≤1.03 记"持平"） |
