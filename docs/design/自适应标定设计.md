# 自适应标定设计（Calibration · v1.0）

> 状态：设计稿 · 2026-10-28
> 上游文档：`推理引擎架构设计.md`（§5 资源层 / §7 演进路线）、`推理引擎设计规范.md`（C1–C4）
> 本文解决的问题：**引擎装到我们没有的卡上，怎么自己找到最优配置。**

---

## 1. 问题定义

### 1.1 一句话

我们只有一台 4060 8GB。别人会装到 3090、4090、A10、Mac M 系列、AMD 卡上。
**不可能给每一张卡提前写一份配置。** 引擎必须在部署后自己把参数找对。

### 1.2 准入门槛：显存 ≥ 8GB（2026-10-28 定稿）

**规则：显存 < 8GB 不做适配，直接拒绝；≥ 8GB 一律进适配流程。**

这个门槛有实测依据，不是拍的：

| 模型 | 实测显存峰值 | 8GB 卡可用（实测 6.94GB）够不够 |
|---|---|---|
| SD1.5 512² | 3.0GB | 富余 |
| SDXL 1024² | 5.21GB | 够，但吃紧（余量 1.7GB） |
| SVD（视频） | 见架构文档基线 | 需 offload 档 |

7GB 卡可用约 6.0GB，跑 SDXL 只剩 0.8GB 余量——OOM 概率高、体验差，**判为不做适配是合理的**。

### 1.3 但「显存够」只是必要条件，不是充分条件

准入必须过**三个维度**，缺一不可：

| 维度 | 判据 | 不过会怎样 |
|---|---|---|
| **① 显存** | ≥ 8GB | 直接拒绝（本节规则） |
| **② 操作系统** | 该厂商驱动 + torch 后端在该 OS 上可用 | 装了也跑不起来 |
| **③ 后端存在** | `device_profile` 能识别并分派到该后端 | 探测不到 = 无从适配 |

**②这条最容易被忽略，且我们踩在 Windows 上。** 例如 AMD ROCm 官方对消费卡的 Windows 支持长期缺位（主要在 Linux），显存 16GB 的 7800XT 在 Windows 上并不等于能跑。

### 1.4 五种「不适配」情况，处理方式不同

| 类型 | 例子 | 能否自动适配 | 手段 |
|---|---|---|---|
| **A. 同后端、不同硬件** | 3090 / 4090 / A100 | ✅ **完全能** | 运行时标定 |
| **B. 不同后端、生态成熟** | 摩尔线程（MUSA） | ✅ **能**，需补探测分支 | 标定 + 后端适配 |
| **C. 不同后端、生态建设期** | 砺算（TrueGPU） | ⚠️ **先标 unverified，不承诺** | 探测到就试，试不通诚实报错 |
| **D. 后端在但有 OS 限制** | AMD ROCm on Windows | ⚠️ **按 OS 分档** | 立项时判定，不运行时猜 |
| **E. 显存不足** | 显存 < 8GB | ❌ **直接拒绝** | 给出需要多少显存的明确提示 |

**E 类必须拒绝。** 勉强跑出一张糊图比直接说「这台机器跑不了 SDXL，至少需要 8GB 显存」更糟——这违反本项目一贯的「拒绝静默降级」原则。判据沿用 `quant_descriptor` 同款三态：`verified / unverified / rejected`。

> **C 类的态度要特别说清**：砺算显存达标（12GB / 24GB），但 PyTorch 后端成熟度无公开证据。**不能因为"它是国产、该支持"就标 verified。** 正确做法是探测到就试一次，通了标 `verified`，不通标 `rejected` 并写明原因。台账的诚实性比覆盖面重要。

### 2.2 **缺的只有一环**

```
现在：probe() 查静态属性 → estimate_floor_gb() 估 → pick_memory_policy() 规则选档 → 直接用
                                              ↑
                                        这里是「估」，不是「量」
```

- `probe()` 只问「你这卡叫什么、多大显存」，**不问「你这卡跑这个模型实际吃多少」**
- `pick_memory_policy()` 是**规则推出来的**，规则来自 4060 上的标定，换卡就未必成立

**补的就是这一环：真跑一次，量出实际峰值，把结果写回去。**

## 3. 设计决策

### D-A1 · 标定只测「能不能跑 + 多快」，不测「好不好」

- **决策**：标定期间判断标准是「不 OOM、峰值不超水位线、耗时」；**质量不进在线判据**。
- **理由**：质量判定需要参考图 + PSNR，一次至少几秒到几十秒，塞进标定会让用户等太久。质量是**离线台账**的职责（`quant_descriptor.py`，`DEFAULT_MIN_PSNR_DB = 35.0`）。
- **代价**：标定选出的档位只保证「快且不崩」，不保证画质。画质由量化/缓存的准入裁决独立把关。

### D-A2 · 阶梯爬升，不做网格搜索

- **决策**：从最保守档起步，一次只升一档，第一个失败的**上一档**就是答案。
- **理由**：`whole_gpu → model_offload → sequential_offload → layer_cpu_offload` 是**单调**的（越激进越省时间、越费显存）。单调空间线性爬最经济：最多 4 次试跑。若做网格（4 档 × 3 chunk × 3 interval = 36 次）用户等不了。
- **代价**：找到的是「第一个能跑的档」，不是「全局最优」。接受——省下来的时间比那点差距值钱。

### D-A3 · 失败必须零成本回退

- **决策**：每次试跑前留存当前档位；失败即释放显存、退回上一档、继续可用。
- **理由**：标定是**增强**，不是**前置依赖**。标定失败绝不能导致引擎不可用。
- **落实**：试跑失败 → `torch.cuda.empty_cache()` → 恢复上一档 → 记 `calibration_failed` 事件，**不抛异常给用户**。

### D-A4 · 档案必须可失效

- **决策**：key 含 `vendor / arch / vram_class / torch_major_minor / model_id / res_class`；任一变化即自然失效。另提供 `invalidate()` 手动清空。
- **理由**：驱动升级、torch 升级、模型换版本都会让旧标定失效。沿用 `device_profile.probe()` 已有的缓存失效设计，不另造一套。
- **细化**：`torch` 只取 `major.minor`（`2.6`），patch 不参与——否则每次小版本更新全部重标，成本过高。

### D-A5 · 后台标定，不阻塞首次使用 ★ 最关键

- **决策**：
  - **首次安装**：直接用最保守档（`layer_cpu_offload`）让用户**立刻能用**；
  - **空闲时**（无任务或任务间隔 > 30s）在后台线程跑标定；
  - **下次启动**读档案，跳过试跑。
- **理由**：用户不想等 5 分钟才能出第一张图。**先能用，再好用。**
- **代价**：第一次会话可能偏慢。这在预期内，且应该在 UI 上说明「正在学习你的设备」。

### D-A6 · 图像标定结果外推给视频，不重复标定

- **决策**：视频只标定一次「帧数-显存」的边际斜率，档位选择复用图像的结论。
- **理由**：`memory_policy` 的档位逻辑与模态无关，差异只在帧数。SVD 一次试跑 40s（见架构文档基线），4 档就是 160s，用户等不了；SD1.5 512² 8 步一次只要几秒，4 档约 20s，可接受。
- **落实**：`calibration.json` 里图像与视频分开存，但视频条目允许 `derived_from: image:<key>`。

## 4. 四步闭环

```
┌─ 第 0 步：静态画像（已有）
│    device_profile.probe() → {vendor, arch, vram_total, vram_free, caps}
│
├─ 第 0.5 步：预热（丢弃结果，2026-10-28 新增）
│    用 model_offload 跑一次完整 load+generate，把冷启动成本先付掉
│    结果不进 tried、不参与裁决，只记 warmup_seconds（见 §11.6）
│
├─ 第 1 步：保守起步
│    用 layer_cpu_offload + 最小分辨率 + 最低步数 试跑一次
│    跑通 → 有了基线，用户可以开始用
│    跑不通 → 判 C 类，诚实拒绝（见 §8）
│
├─ 第 2 步：单维爬升（后台）
│    for mode in [sequential_offload, model_offload, whole_gpu]:
│        试跑 → 量 peak_vram / elapsed
│        peak > water_line 或 OOM → 回退，锁定上一档，break
│        否则 → 记录，继续升
│
├─ 第 3 步：写档案
│    key = (vendor, arch, vram_class, torch_mm, model_id, res_class)
│    value = {mode, chunk, interval, peak_gb, seconds, measured_at, source}
│
└─ 第 4 步：命中复用
     下次同 key → 直接读档案，跳过试跑（秒开）
     未命中 → 回第 1 步
```

### 4.1 试跑规格（为什么用小分辨率）

| 用途 | 分辨率 | 步数 | 单次耗时（4060 估算） |
|---|---|---|---|
| 标定探针 | 512² (SD1.5) | 4 | **实测 2.0~19.4s**（受冷启动影响，见 §12.2） |
| 正式生成 | 1024² (SDXL) | 按质量档 | 27.9s（实测基线） |

**关键**：探针用小规格，但**峰值显存要按比例外推到大规格**再判水位线。

外推系数**已实测校正为 `1.46`**（§12.1），不再用猜的 1.6。优先走线性模型
（传 `base_gb`），幂律仅作兜底。

### 4.2 档案格式

```jsonc
{
  "version": 1,
  "entries": {
    "nvidia|sm89|8|2.6|sdxl-base|1024": {
      "mode": "model_offload",
      "chunk": 1,
      "interval": 3,
      "peak_gb": 5.21,
      "seconds": 27.9,
      "measured_at": "2026-10-28T02:20:00",
      "source": "measured",
      "tried": ["layer_cpu_offload", "sequential_offload", "model_offload"],
      "rejected": ["whole_gpu: OOM at 6.58GB"]
    }
  }
}
```

`source` 三态：`measured`（本机实测）/ `derived`（外推）/ `default`（内置保守值）。**必须区分**，否则会把外推值当实测值用——这是最危险的静默降级。

### 4.3 第 4 步落地：档案怎么接进决策链（2026-10-28 已接通）

标定算得再准，不接进 `pick_memory_policy()` 就等于白算。接线位置与优先级如下。

**位置**：`app/core/neural/memory_policy.py` 的 `pick_memory_policy()` **分支 -1**，
排在一切规则分支之前（`vram` 探测之后、调优表 `prefer_mode` 之前）。

**优先级排序（为什么档案在最前）**

| 顺序 | 依据 | 可信度来源 |
|---|---|---|
| -1 | 标定档案 | 这台机器真跑、真记账 |
| 0 | 调优表 `prefer_mode` | 人工写死的四档对比结论 |
| 1–2 | 水位线规则 | 通用设计意图（0.85 / 0.95 / 0.60） |

机器换了、驱动换了、别的进程占了显存，档案会被下面两道闸拦下并**自动降级回规则**，
所以「实测优先」不会变成「实测盲目」。

**两道安全闸**

1. **放得进当前空闲**：`entry.peak_gb > free_gb` ⇒ 拒绝。历史实测只证明「当时跑得动」，
   不证明「现在还跑得动」。
2. **whole_gpu 复验 15% 余量**：`peak > total_gb × 0.85` ⇒ 拒绝。这条跟分支 1 同一条线。
   历史峰值只说明「当时刚好没炸」，而 WDDM 分页的代价是 >600s 卡死（SVD 10 帧实测），
   所以 `whole_gpu` 永不接受「勉强塞得下」。总显存未知时同样拒绝（没法复验就不猜）。

**五条边界（宁可不用，不许猜）**

| 情况 | 处理 | 理由 |
|---|---|---|
| `frames > 0`（视频） | 不用档案 | 档案没有帧数维度；SVD ≈0.31GB/帧，拿 25 帧套 5 帧的档案必翻车 |
| 档位不在 `ACTIVE_MODES` | 忽略 | `layer_disk_offload` 仍是预告 |
| 档位不在 `supported_modes` | 忽略 | 引擎没实现这档 ⇒ 决策与执行漂移 |
| `peak_gb <= 0` | 忽略 | 不拿 0 当「不占显存」 |
| 模块缺失 / 查询异常 | 降级走规则 | 标定是增强，不是前置依赖（D-A3） |

**关闭开关**：`pick_memory_policy(..., use_calibration=False)` —— bench、四档对比、
排障时用；也保证「关掉增强照样跑」这条纪律可被测试验证。

**分辨率换算（2026-10-28 补）**：档案里的 `peak_gb` 是**探针尺寸**（512²）的实测值。
传了 `width/height` 时，`calibration.peak_for_resolution()` 会按 `EXTRAPOLATE_COEF_4X = 1.46`
把它换算到本次尺寸**再判闸**（3.19GB @512² → 4.65GB @1024²），`floor_gb` 也用换算后的值。
不换算就会拿「512² 的占用」判「1024² 的水位」，而低估正是 OOM 的来源。
`res_class` 是 `1536plus`（非数字分桶）或目标尺寸未知时**原样返回**，不编比例。

**调用方现状**：`diffusers_image.load()` 传 `frames=0` 但**不传 width/height** ——
`load()` 阶段还不知道本次出图尺寸（尺寸是 `generate()` 才定的），而 offload 必须在
load 时装好。所以档案走 `calibration.lookup()` 的**宽松匹配**：先试精确 `res_class`，
不中则取同设备同模型下 `peak_gb` **最大**那条 —— 用最坏情况决策。
换算机制已就绪，等 `generate()` 阶段的重复核接上才算闭环（见 §10 第 13 条）。

**测试**：`app/tests/test_memory_policy_calibration.py`（23 项）专测接线、两道闸与分辨率换算；
`test_memory_policy.py` / `test_memory_policy_matrix.py` / `test_vram_budget.py` 用
autouse fixture 把档案**钉死为空** —— 它们测的是规则语义，档案存在与否（开发机有、CI 没有）
不该改变结论。

## 5. 失败处理矩阵

| 失败点 | 现象 | 处理 |
|---|---|---|
| 第 1 步就跑不通 | 最小规格也 OOM | 判 C 类 → 报「此设备无法运行 <model>，需要约 X GB」→ 不启用该模型 |
| 爬到第 N 档 OOM | 峰值超水位线 | 回退到第 N-1 档，锁定，记 `rejected` |
| 标定超时 | 单次试跑 > 3× 预期 | 中止标定，保留保守档，下次再试 |
| 档案损坏 | JSON 解析失败 | 删档重建，走第 1 步 |
| 显存被其他进程占用 | 可用显存 << 总量 | 用 `effective_free()` 而非 `total` 判定（见架构文档 §5.3 第 1 条） |

> 最后一条是踩过的坑：`load()` 不等于占显存（SD1.5 `load()` 后 `memory_allocated()` = 0.00GB，offload 档惰性上卡）。标定必须用**真跑一次**的峰值为准，不能用「load 后差值」。

## 6. 五厂商支持矩阵（2026-10-28 核实）

### 6.1 现状对账

| 厂商 | 后端 | 显存档位 | OS | 判定 | 依据 |
|---|---|---|---|---|---|
| **NVIDIA** | CUDA | 全系（3060 12G 起） | Win/Linux | ✅ **verified** | 本机 4060 已实测 |
| **摩尔线程** | MUSA `torch_musa` + `torchada` | S80 16G / E300 16~64G / S5000 80G | Win/Linux | ✅ **可支持** | 见 §6.2 |
| **AMD** | ROCm / HIP | 7800XT 16G 等 | **Linux 为主** | ⚠️ **按 OS 分档** | `device_profile.py:122` 已有 `_probe_rocm()` |
| **Intel** | XPU（`torch.xpu`） | Arc A770 16G / B580 12G | Windows 较好 | ⚠️ **需补分支** | `_caps_from()` 无 intel 分支 |
| **砺算** | TrueGPU 自研 | 7G100/7G106 12G、ULTRA 24G | Win/Linux | ⚠️ **unverified** | 见 §6.3 |

### 6.2 摩尔线程：比预期好，且改动量可控

核实到的软件栈现状：

- **MUSA SDK 5.1.0** 对标 CUDA 12.8，兼容接口 761 个，官方称完整支持 PyTorch 全部 3194 个算子
- **`torchada`**（2026-02-25 发布）：代码顶部加一行 `import torchada`，所有 `torch.cuda.*` 自动重定向到 `torch.musa.*`。明确支持：显存管理（`memory_allocated` / `empty_cache`）、`synchronize`、Stream/Event、amp autocast、**CUDA Graphs**、**`torch.compile` 全后端**、C++ 扩展
- vLLM 官方后端、SGLang 主线原生支持；FlashAttention3 在 MUSA 上达 95% 效率

**对我们意味着什么（`verify_torchada_coverage.py` 实测，非推测）：**

| 项 | 实测 |
|---|---|
| `torch.cuda.*` 调用 | **30 处** |
| 文档清单可覆盖 | **20 处（66.7%）** |
| 未明列、必须真机验证 | **10 处** |
| `"cuda"` 字符串字面量 | 23 处，其中**只有 2 处**是字符串比较 |

未明列清单（MUSA 适配前必须逐个验）：

| API | 次数 | 位置 | 不支持的后果 |
|---|---|---|---|
| `get_device_properties` | 4 | `accel_status.py:64`、`device_profile.py:79/128`、`diffusers_image.py:968` | 读不到卡名/显存 ⇒ 标定基数据全错 |
| `get_device_capability` | 2 | `accel_status.py:65`、`device_profile.py:80` | 读不到 sm ⇒ `_caps_from()` 全部返回 False |
| **`mem_get_info`** | 2 | `diffusers_image.py:976`、`memory_policy.py:145` | **★ 最关键**：torchada 文档的「显存管理」一栏只写了 `memory_allocated` / `empty_cache`，**没有它**。它不重定向 ⇒ 显存读数全错 ⇒ 整个标定建在假数据上 |
| `ipc_collect` | 1 | `inference_cache.py:1000` | 显存回收失效，长跑会累积 |
| `OutOfMemoryError` | 1 | `video_gen.py:787` | ★ 异常类，见下 |

**★ `OutOfMemoryError` 是这批里最危险的一个，因为它是异常类而不是函数。**

`video_gen.py:787` 用 `except torch.cuda.OutOfMemoryError` 接 OOM。如果 MUSA 抛的是另一个异常类，这个 `except` **抓不到**，异常直接穿透 → 进程崩溃，而不是我们设计的优雅降级（回退档位）。必须验这一条：
`torch.cuda.OutOfMemoryError is torch.musa.OutOfMemoryError`

**字符串那一项要纠正我此前的判断。** 之前我按 grep 说「24 处 `"cuda"` 都要改」，实测下来**只有 2 处是真的字符串比较**：

- `style_transfer.py:82` `if self._device == "cuda":`
- `style_transfer.py:134` `if self._device == "cuda":`

其余 21 处都是 API 实参（`device="cuda"`、`pipe.to("cuda")`、`torch.randn(..., device="cuda")`），torchada 会自动重定向。**改动量比原先估计小一个量级。**

**三个代码改动点：**

1. `device_profile.py` 新增 `_probe_musa()`：检测 `torch.musa.is_available()` 或 `import torch_musa`
2. `_caps_from():47` 加 musa 分支：`fp16` / `bf16` = True；`fp8` 待实测，先 False
3. `_libs():61` 加 `torchada` / `torch_musa` 检测位

**顺带一个技术债**：`_VENDOR_BY_ARCH:31` 这个名字有歧义——它映射的是 NVIDIA `sm89 → ada`（架构→**代际**），不是厂商。加 MUSA 后会更混乱，建议改名 `_GEN_BY_SM`。改名是纯符号重命名，不涉行为，可放进 P0。

### 6.3 砺算：显存达标，但后端成熟度无公开证据

- 硬件：LX 7G100 / 7G106 12GB GDDR6、LX ULTRA 24GB，自研 TrueGPU「天图」架构
- 官方口径：「支持 Qwen3、DeepSeek 等大模型本地化部署」
- **但**：没有公开的 PyTorch 后端名称；官方招聘页正在招「AI 框架适配工程师，负责 PyTorch/vLLM 在自研 GPU 上的适配」——**这说明生态还在建设期**
- 有第三方提到「CUDA 兼容层已能跑 PyTorch 主流模型，精度和速度还有优化空间」，属传闻级别，不可作为准入依据

**判定：标 `unverified`。** 探测到设备就试一次，通了升级为 `verified`，不通记 `rejected` 并写明原因。

> ⚠️ 有一条必须写死：**不能因为"它是国产、该支持"就标 verified。** 台账的诚实性比覆盖面重要。这是 `quant_descriptor` 的 int8 教训换来的规矩。

### 6.4 不能覆盖，且必须在 UI 说清

- ❌ **显存 < 8GB**：按 §1.2 直接拒绝
- ❌ **多卡张量并行**：所有档位都是单卡逻辑，跨卡切分未设计
- ❌ **统一内存设备的部分档位**：`device_profile.py:7` 已注明「offload 概念假设权重能从 CPU 搬到 GPU ⇒ 统一内存设备上无意义」
- ❌ **后端根本没实现的特性**：如 MPS 无 fp8，那是后端问题，不是调参能解决的
- ❌ **DirectML 路线**：与 `torch.xpu` 是两条不同的路，未评估

### 6.5 与千问那个「AI 自主适配」的区别（避免误解）

云栖大会披露的是 Qwen3.8-Max 在**一张全新平头哥 GPU** 上自主改推理代码、33 轮迭代拿到 +96% 吞吐。那是**开发期的一次性攻关**，人定目标、人验收。

本设计做的是 **部署期的参数标定**：搜索空间是有限的枚举（档位 × chunk × interval），不做代码生成。**不要把它宣传成「AI 自己进化」**——它是工程标定，成熟、可解释、可回退，这才是当前该有的形态。

## 10. 已知缺口

1. ~~**1.6× 外推系数是猜的**~~ → **2026-10-28 已实测校正为 `1.46`**（见 §11.1）。原值偏高 9.8%。
2. **Intel XPU 分支未写**，`_caps_from()` 需先补。
3. **AMD 在 Windows 上的 ROCm 消费卡支持未核实**——直接决定 ②操作系统维度怎么分档。
4. **MUSA 的 fp8 / bf16 实测未做**，`_caps_from()` 里先保守填 False，待实测再放开。
5. **砺算无设备可测**，只能等真机。
6. **多卡场景完全未设计**，所有假设都是单卡。
7. **Mac 统一内存**下的档位语义待验证。
8. ~~**标定耗时未真机测量**~~ → **已实测**，单档 2.0~19.4s（见 §11.2）。
   ~~**冷启动偏差尚未消除**~~ → **2026-10-28 已消除**（阶梯前插丢弃式预热，
   第一档加载 19.31s → 3.94s，整轮反而从 37.1s 降到 33.4s，见 §11.6）。
9. **`torchada` 对 10 处调用的重定向行为未验证**——已用 `verify_torchada_coverage.py` 静态定位，
   但静态分析只能证明「我们用了什么」，不能证明「它认不认」。**必须在真实 MUSA 设备上跑一次 `--run`。**
   其中 `mem_get_info` 与 `OutOfMemoryError` 两个最关键：前者决定显存读数，后者决定 OOM 能否被捕获。
10. **本机无摩尔线程硬件**，脚本的运行时分支只验证了 NVIDIA 路径（`mem_get_info` = 6.94/8.0GB，与 MVP 实测一致）。
11. **`derive_for_video` 的「1.2%/帧」仍未实测**——视频探针一次 40s，四档 160s，本轮未跑。
12. **档案没有「帧数」维度**（2026-10-28 接线时明确的边界）：`Entry` 只有 `peak_gb`，
    没有「这条是在几帧下测的」。视频显存随帧数线性增长（SVD ≈0.31GB/帧），
    拿一次 5 帧的档案去决策 25 帧会严重低估 ⇒ `pick_memory_policy()` 在 `frames > 0` 时
    **明确不用档案**，并写进 reasons。补法有两条：① `Entry` 加 `frames` 字段（要升 `CALIB_VERSION`）；
    ② 档案只存 `base_gb`，按帧数现算。**P3 视频内核落地时二选一，现在不猜。**
13. **档案命中后的分辨率复核只做了「换算」，没做「二次确认」**：传了 `width/height` 时
    峰值会按 `EXTRAPOLATE_COEF_4X` 换算后再判闸（`peak_for_resolution`），但
    `diffusers_image.load()` 在 load 阶段拿不到出图尺寸 ⇒ 那条路径仍走「取最坏情况那条」的
    宽松兜底。严格做法是 `generate()` 阶段拿真实尺寸**再复核一次**，超线就降档重载 ——
    **尚未实现**（代价是一次重载，收益是长宽比极端时不会撞 OOM）。

## 11. 首次真机实测（2026-10-28 · RTX 4060 Laptop 8GB）

代码：`app/core/neural/calibration.py` + `calibration_probe.py`，测试 42 项全绿。

### 11.1 外推系数校正

同一模型（SD1.5）、同一档位（`model_offload`）、仅改分辨率的对照：

| 规格 | allocated | reserved | 加载 | 生成 |
|---|---|---|---|---|
| 512² | 1.75GB | 2.00GB | 16.14s | 3.41s |
| 1024² | 2.55GB | 4.36GB | 15.72s | 6.69s |

- 峰值比 **2.55 / 1.75 = 1.457** ⇒ 系数取 **1.46**（原猜 1.6，偏高 9.8%）
- 反解线性模型：`base ≈ 1.48GB`、`k ≈ 0.267GB/单位`，代回 1024² 得 2.55GB **完全吻合**
  ⇒ 线性模型（传 `base_gb`）比幂律准，已设为优先路径。
- 幂律指数 `ln(1.457)/ln(4) = 0.272`，仅在拿不到 `base_gb` 时兜底。

### 11.2 四档端到端标定（第二次运行，缓存已热）

| 档位 | allocated | reserved | 加载 | 生成 | 总 | 判定 |
|---|---|---|---|---|---|---|
| `layer_cpu_offload` | 2.01 | 2.93 | 15.02s | 4.35s | 19.43s | 最慢（逐层钩子开销） |
| `sequential_offload` | **0.61** | **0.65** | 4.01s | 4.71s | 8.72s | 最省显存，但慢 |
| `model_offload` | 1.75 | 2.00 | 1.07s | 1.60s | 2.67s | 均衡 |
| **`whole_gpu`** | 2.61 | 3.19 | 1.28s | **0.73s** | **2.01s** | **选中** |

档案：`data/calibration.json`
key = `nvidia|sm89|8|2.6|sd15-t2i|512` → `whole_gpu` / 3.19GB / 2.01s / `measured` / `verified`

**结论：`decide()` 按实测耗时选档是对的。** `whole_gpu` 生成 0.73s，是 `layer_cpu_offload`
（4.35s）的 1/6 —— 若按「取最激进」的旧规则会选到它，恰好也是对的；但若按「取最保守」就错了。
真正起作用的不是顺序，是实测。

### 11.3 新发现一：冷启动偏差（**2026-10-28 已消除**，见 §11.6）

同一台机器、同一配置，两次完整标定的加载耗时：

| 档位 | 第一次 | 第二次 |
|---|---|---|
| `layer_cpu_offload` | 16.62s | 15.02s |
| `sequential_offload` | 6.90s | 4.01s |
| `model_offload` | 2.73s | 1.07s |
| `whole_gpu` | 2.52s | 1.28s |

**加载时间随执行顺序单调下降** —— OS 文件缓存 + cuDNN 句柄初始化 + 分配器首次扩张。

因为阶梯固定「从保守到激进」，**第一档总是承担冷启动成本，被系统性高估**。
当时结论不受影响（`whole_gpu` 优势太大），但**两档接近时偏差可能翻转结论**。

**处理**：阶梯之前插一次「丢弃式预热」（§11.6 有对照实验与实测数据）。

### 11.4 新发现二：`reserved` 涨幅远大于 `allocated`

| 规格 | allocated | reserved | 差值 |
|---|---|---|---|
| 512² | 1.75 | 2.00 | 0.25 |
| 1024² | 2.55 | **4.36** | **1.81（+70%）** |

**只按 allocated 判水位线会系统性低估真实占用**，8GB 卡上这正是 OOM 的典型路径。

已落地：`Trial` 增 `reserved_gb` 字段，`effective_peak_gb()` 取二者较大值记账。
`test_decide_uses_reserved_when_allocated_looks_safe` 复现了这个陷阱形状。

### 11.5 顺带修掉一个真 bug：缓存把「探测失败」固化了

`data/device_profile.json` 里曾存着：

```json
{"name": "CUDA 探测失败", "vram_gb": 0.0, "arch": "unknown",
 "reason": ["CUDA 探测异常 ModuleNotFoundError: No module named 'torch'"]}
```

原因：在无 torch 的环境（managed python）里跑过一次 `probe()`，而它**无条件写缓存**。
后果：之后所有调用读到 0GB ⇒ `calibration.admit()` 永久拒绝、`memory_policy` 档位决策全错；
且 `force=True` 不会自动修复（force 分支本身不写缓存）。

**修法**（`device_profile.py`）：只有 `vram_gb > 0` 才写缓存。CPU 机与探测失败每次重探，
代价只是几次 import 检查，不必缓存。

### 11.6 冷启动偏差：对照实验与消除（2026-10-28 · 同机同配置）

**做法**：阶梯之前跑一次**丢弃式预热**（默认 `model_offload@512px`，结果不进 `tried`、
不参与 `decide`，只记 `warmup_seconds`）。两次运行都是全新进程，对照公平。

| 档位 | 对照组加载 | 实验组加载 | 降幅 | 对照组总 | 实验组总 |
|---|---|---|---|---|---|
| （预热） | — | **13.83s** | — | — | 16.76s |
| `layer_cpu_offload` | **19.31s** | **3.94s** | −79.6% | 23.75s | 7.42s |
| `sequential_offload` | 4.63s | 0.98s | −78.8% | 8.80s | 4.75s |
| `model_offload` | 0.90s | 0.89s | −1.1% | 2.44s | 2.40s |
| `whole_gpu` | 1.38s | 1.32s | −4.3% | 2.10s | 2.05s |
| **整轮合计** | ~37.1s | **~33.4s** | — | | |

三个结论：

1. **冷启动不止影响第一档**。`sequential_offload` 的加载从 4.63s 掉到 0.98s
   —— 说明冷启动成本是被**摊在两档里**付的（第一档付大头，第二档付尾巴）。
   所以「每档前预热」是过度设计，「阶梯前预热一次」刚好够。
2. **预热不是成本，是节省**。整轮从 37.1s 降到 33.4s：预热只付一次 16.76s，
   而对照组把同一笔冷启动成本付了两次（19.31 里的约 15s + 4.63 里的约 3.7s）。
3. **显存测量没被污染**。四档 `peak_gb` 对照 2.01→2.02 / 0.61→0.61 / 1.75→1.75 /
   2.61→2.61，零漂移 —— 预热后的 `unload() + empty_cache() + reset_peak_memory_stats()`
   生效了。**预热只修时间口径，不动显存口径**，这点必须保持。

**剔除冷启动后的真实档位成本**（实验组加载列）：`layer_cpu 3.94` ≫ `whole_gpu 1.32`
≳ `sequential 0.98` ≈ `model 0.89`。`layer_cpu` 依然最慢，但**差距从 19.31s vs 0.90s
（21 倍，荒谬）收敛到 3.94s vs 0.89s（4.4 倍，可解释）** —— 那个 3.94s 是挂 12 个
block 组 hook 的真实开销，不是噪声。

**实现**：`Calibrator(..., warmup_run=...)`，注入式（`calibration.py` 保持零 torch）；
执行层的 `make_image_warmup()` 负责造这个动作，`--no-warmup` 可关（只给对照实验用）。
预热失败**不阻断**标定，但会在档案 `note` 里留「未预热 ⇒ 首档耗时可能含冷启动」。

**为什么预热选 `model_offload` 而不是 `whole_gpu`**：whole_gpu 在窄显存卡上可能直接 OOM，
而预热失败虽不阻断，却会留下没暖透的状态；`model_offload` 是所有已登记模型的定稿档，
过了 8GB 准入的卡几乎必然成功。

## 12. 一页速查

- **准入门槛**：显存 ≥ 8GB 才适配，< 8GB 直接拒绝并说明需要多少。
- **但显存不是唯一条件**：还要过「② 操作系统」和「③ 后端存在」两维。
