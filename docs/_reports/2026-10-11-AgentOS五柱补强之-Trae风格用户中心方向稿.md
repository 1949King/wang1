### 3.4 数据共享 & 状态机

**PyQt6 主程序内**（单进程同对象）：
- **数据真源**：`auth_service`（`auth.py:838`）单例
- **状态变化事件**：通过现有 `EventBus`（`main_window.py:21`）广播
- **通知事件源**：`alert_system.py` 的 `SYSTEM` 渠道直接写入 `NotificationCenterPanel` 模型

**画布侧（vendor/shiguang-canvas）**：
- **不出现 UserCenterPanel**（本稿核心定位已明确）
- **画布只做状态镜像** —— 主程序通过 localStorage `shiguang-canvas:user-state:v1` 写入，画布启动时一次性读取
- **跨进程通知**：主程序状态变化时通过新增 `/host/auth/state` 端点推送到画布
- 触发场景：仅需同步的少数事件
  - 用户登录/退出 → 画布更新 nav bar 上的状态图标
  - 主题切换 → 画布同步 CSS 主题（之前 V4.41.18 已实现部分）
  - 大版本更新广播 → 画布显示 toast（V4.41.x 系列已有 `needs_log` 落地）

### 3.5 跨主程序调用（**主程序主导，画布被同步**）

**主程序 → 画布**：
- **新端点**：`POST /host/auth/state-changed`（事件化）+ **`POST /host/auth/broadcast`**
- 已有端点不动；只新增广播路径

**画布 → 主程序**：
- **不应该发起** —— 头像、消息、设置都在主程序入口；画布上是「只读镜像」
- 例外：画布内执行的任务需要通知到主程序通知栏（**P1 任务** —— S2 任务完成 → 弹通知）

## 6. 风险 & 纪律

### 6.1 风险

| # | 风险 | 缓解 |
|---|---|---|
| ① | 主程序有 8 个旧 UI 模块被菜单入口绑死，迁到面板会破坏既有用户流 | **先做主程序 UserCenterPanel**（保留旧菜单入口），等用户验证后再迁移 |
| ② | alert_system 7 渠道敏感（Slack/Discord）需用户配置 | 默认仅用 system channel；其它渠道不在 P0 |
| ③ | 画布侧需镜像主程序登录态 / 主题 / 更新状态 | 已通过 `POST /host/auth/state-changed` 端点；画布订阅后**只读**，不发起动作 |
| ④ | 退出登录逻辑需清理画布 token（避免画布侧残留过期态） | P1 端点 `POST /host/auth/logout` 双删主程序 + 画布 localStorage |
| ⑤ | 主题切换：主程序 QSS 与画布 CSS 主题不一致 | 主程序主导、画布订阅（VelaRocket 单一来源）|
| ⑥ | 用户积分 / 升级权益等业务字段未来扩展 | UserInfo schema 后续字段预留 `points / vip / extra` |

### 6.2 纪律

| 律 | 内容 |
|---|---|
| **收口不替换** | PyQt6 的旧菜单入口保留；UserCenterPanel 是「**新增入口**」而非「迁移入口」 |
| **同一份数据** | 主程序 User 数据是单一真相源；画布只读 |
| **不引入新理念** | 与整合稿 + 可行性报告 8+2 铁律全兼容 |
| **特权操作不暴露 UI** | 注销 / 删除账号等危险操作仍由主程序完成 |
| **离线可用** | localStorage 缓存 UserInfo · 离线时仅显示本地状态 |
