## 第 0 章 总判定：一句话 + 一张表

**一句话：零件已达准一流，整机差「通电」——项目的系统性问题不是造不出零件，而是建成的零件没装进整机；同时剪辑底座的三条铁律各有具体的洞，内容生产的前半链（策划/编剧/美术资产）是三颗硬缺牙。**

五路侦察的独立结论互相印证出同一个模式（「建成未通电」清单）：

| 已建成的准一流零件 | 现状 | 证据 |
|---|---|---|
| 自研+主选双图像引擎（M1 双 PASS） | **生产调用方为 0**：无路由、无 capability、无 backend | diffsynth_image.py / diffusers_image.py 仅被各自 test import |
| 图执行三件套（runner + 增量缓存 + 增强） | **孤岛**：全库只有 _verify 脚本在调 | canvas_workflow_runner.py:6-9 自述「连线不参与执行」 |
| 抽卡闭环（seed/账本/代理分/局部重绘全通电） | **差 ~80 行编排**：全库 best_of 0 命中，多张靠人眼挑 | draw_book.py / gen_critic.py / draw_ledger.py 均在 |

## 第 1 章 发展方向（三战役，与既有优先级对齐）

既定总序不变：**先剪辑体验 → 再画布体验 → 再 AI 剪辑/智能体 → 再数字人**。三战役是这个总序在当前代码现状下的具体化：

### 战役一 · 通电（把已付成本的零件接进主链路）—— 最先打
理由：引擎、抽卡、图执行、账本都是已付开发成本，接线的改动量都在「几十行~一个路由」量级，ROI 全场最高；且通电后 M1~M5 才从「实验室成绩」变「产品能力」，自研引擎切回（刀4 终局）才有意义。

### 战役二 · 铁律（剪辑底座三铁律补洞 + 诚实性清剿）—— 并行打
理由：剪辑是北极星主战场（自评 8.0→8.5 的涨分队列），三铁律（一切皆可撤销 / 预览即导出 / 操作即数据）各有具体的洞；诚实性违规（假超分/假风格迁移）直接违反项目第一原则，是口碑级风险。

### 战役三 · 前半链（内容生产三颗牙）—— 接续打
理由：对标 LibTV 1.5 / 动漫公司制作链，消费端已接近甚至局部超越（ABCD 高光、账本/抽检/冻结纪律比同行严谨），差距集中在生产侧：编剧大脑、美术资产本体、审美真值。这是差异化竞争力的来源，但工程量最大，排在通电变现之后。

## 第 2 章 需要优化的架构设计（6 项，按依赖序）

### A1 · 引擎选路统一（补「主备制裂缝」）
- 现状：`memory_policy` 名义上是显存单一决策点，主选 `diffsynth_image.load` 却硬编码 `offload_mode="cpu_offload"`（diffsynth_image.py:244,255）；`execution_decider.resolve_execution_engine()` 的选路结论只写进 reasons 字符串，不改变任何执行路径（execution_decider.py:307）。
- 设计：① diffsynth_image.load 改为读 `pick_memory_policy`（至少对齐观测、打出 reasons）；② `execution_decider` 从「写日志」变「真分派」——云端渠道 / 本地引擎按 engine 字段路由；③ 给 SDXL 20s/180s 双态加 RAM/换页遥测（cpu_offload ~7GB 权重常驻 RAM 是最可疑嫌疑）。
- 收益：单一决策点名至实归；M2 未决与 M5 稳定性同源问题获得观测手段。

### A2 · 图像引擎生产化（通电战役主力）
- 现状：两个图像引擎契约已逐键对齐、守卫锁定，但零生产接线。
- 设计：照 `/host/local-video-generate`（canvas_routes_post.py:1439，models/pull/generate 三态）新增 `/host/local-image-generate`；canvas_aigc 注册 `LocalImageInferBackend`（现仅视频+语音，canvas_aigc.py:239-240）；能力目录加 `canvas.local_generate_image` 一行（唯一入口纪律）。
- 配套：修 SDXL provisioning 断点——`sd_xl_base.yaml` 目前是手工 jsdelivr 落盘，pull 的 allow_patterns 拉不到 ⇒ 换新机器永远报「未落盘完整」（diffusers_image.py:279-281）。把第二来源编码进 pull。

### A3 · 图执行进主链路（与 ComfyUI 最本质的差距）
- 现状：`canvas_workflow_runner`（端口模型、collect_inputs、拓扑执行）+ `canvas_node_cache`（上游指纹/TTL/LRU/原子写）质量达标，但只有测试在用；画布主链路仍是「人逐节点点生成」，前端 `collectUpstreamContext`（bridge.ts:1388）只拼文本上游，图/视频/音频参考不参与。
- 设计：前端加「运行到此处」入口 → `POST /host/canvas-run`（dry_run 出计划→确认→执行）→ 进度回显走既有 generationQueue 轮询。立刻获得两大 ComfyUI 级能力：**同参数增量缓存（不重抽）+ 上游产物注入（图/视频参考）**。
- 边界：22 种节点仅 6 种可执行是诚实现状（_NOT_RUNNABLE 如实报告），先接可执行子集，不硬撑全图。

### A4 · 契约派生化（消灭手工副本）
- 现状三处手工同步：① `agentPolicy.ts:14-47` 是后端 `_CANVAS_ACTION_ROWS` 的手工抄写副本（dangerous 级别已丢失：deleteNode 后端标 dangerous，前端无此维度）；② 双 prompt 库当前字节一致但同步机制=手工复制；③ storyNodes.tsx 双库分叉是**此刻的活伤口**（check_canvas_dual_repo FAIL，1,578 行整体替换）。
- 设计：① agentPolicy.ts 改为运行时 GET 下发（/host/agent-policy 端点）或构建期生成，deleteNode 的 dangerous 同步进前端确认流；② storyNodes 立即收敛（确认主库为真源→同步→--update 基线）；③ 长期解 = P0-1 抽 `@shiguang/libtv` 单包（未启动，工程量大，攒着）。
- 配套守卫：check_canvas_routes.py 比对从 path 改 (method, path) 二元组——`/host/model-preload` 的 GET/POST 错配 latent 404 就是从这条缝漏的（canvas_routes_get.py:620 vs bridge.ts:340）。

### A5 · 撤销系统与渲染缓存（剪辑底座两项结构性升级）
- 撤销：手动 dict 栈已 6 种 type + compound，每加一种操作就在 `_apply_action`（editor_module.py:3653-3790）加分支，越来越脆；且 _apply_action 自己多步改 `_clips` 不持锁（违反本文件 L473-479 自写纪律）。先补洞（转场/贴纸入栈 + 整段持锁，RLock 可重入风险低），再评估升级命令对象模式。
- 渲染缓存：当前只有同帧 GL uniform 缓存（L641），scrub/播放每帧重解码+逐帧 numpy 合成（L6350-6498）——这是流畅度的最大杠杆。设计：预览帧 LRU（解码帧+特效参数哈希做 key），先内存盘后评估磁盘层。

### A6 · 工具协议升级（Agent 体感的 Cursor 差距）
- 现状：AgentLoop 靠正则从文本里抠 JSON（agent_loop.py:49-50）；生成进度靠前端轮询而非 SSE 直推节点；AgentBrain 完备但只接 1 个决策点。
- 设计（分两步，不一口吃胖）：① SSE 事件直推节点进度（SSE 桥已存在，server:430-490，只差事件源接 generation 状态机）；② AgentBrain 触点扩展——把 suggest_next 从 1 个岔路口推广到「能力选择/参数建议」两类高频决策（每个触点独立可关，学 SG_BRAIN_ROUTE 开关模式）。原生工具调用（function calling）依赖云端模型能力，列为观察项不承诺。
