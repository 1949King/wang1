## 第一部分 ★★「异构动态协作引擎是否被应用在这里面？」—— **答案：没有**

### 1.1 先厘清这套引擎是什么

它源自用户提供的《异构动态协作引擎 — 完整开发规格说明书》**v4.3**，
在本项目以 **12 个切片**落地（见 `docs/_reports/2026-09-23-拾光剪影-架构与算法规格说明书.md` §35）。

**核心思想**（§35 引言，原文）：
> 不是「先决定本地/云端/双路、再执行、再补救」，而是**把质量、成本、延迟、资源放进同一个实时目标函数，
> 动态选路，并用执行结果持续修正下一次决策**。

**关键性质：它本身就是「选路层」** —— 决定「这一次用云端还是本地、用哪个 provider」。
所以它与「执行引擎（L2）」的关系是**上下层**：**异构引擎管选谁，执行引擎管怎么算。**

**落地切片**（§35 统计：11 个已实接主链路，3 个实现完整但未接线）：

| 切片 | 职责 | 接线状态 |
|---|---|---|
| `budget_pacer.py` | PI 影子价格控制器（λ 随预算消耗连续调节） | ✅ `video_generation_client.py:466-468, 622-629` |
| `execution_modes.py` | 执行模式（§10/11/12） | ✅ `:484, 508` |
| `divergence_probe.py` | 发散探测 | ✅ |
| `fusion.py` | 多维融合 | ⚠️ 仅视频算子接线，文本/音频未接 |
| `global_price.py` | 全局价格层 + 配额拍卖 | ⚠️ λ 已接，`auction()` 未接生产 |
| `sampling_review.py` | 抽样审查 | ✅ |
| `quality_prior.py` | 质量先验 | ✅ |
| `degradation.py` | 降级 | ✅ |
| `provider_pool.py` / `provider_caps.py` / `score_book.py` | 渠道池 / 渠道能力 / 评分账本 | ✅ |
| `module_scheduler.py` / `engine_api.py` / `simulator.py` | 模块调度 / 引擎门面 / 模拟器 | ❌ **未接生产** |

### 1.2 ★ 核查方法：看画布链路有没有 import 这些切片

对画布生成链路的 5 个关键文件，逐个搜全部 12 个切片的模块名：

| 文件 | 命中 |
|---|---|
| `app/core/canvas_aigc.py` | **0** |
| `app/core/canvas_routes_post.py` | **0** |
| `app/core/local_video_infer.py` | **0** |
| `app/core/neural/video_gen.py`（我新加的） | **0** |
| `app/core/ai/comfy_provider.py` | **0** |

再核 `canvas_aigc.py` 的全部 `from app.core` 导入，实际只用到：
`canvas_gen_jobs` · `canvas_bridge` · `local_video_infer` · `voice_generator` ·
`ai.canvas_aspect` · **`ai.draw_ledger`** · `generation_postprocess` · `canvas_agent_runtime` ·
`ai_engine` · `ffmpeg_utils` · `ai_editing_assistant`

**⇒ 结论：画布生成链路对异构引擎的消费是「零」。**

### 1.3 真正的接线位置：**只在 Agent 侧**

异构引擎挂在**另一条链**上：

```
agent_pipeline_orchestrator.execute(:365-366)          ← Agent 侧入口
  或 capability_handlers.py(:980-993)                  ← 能力调用入口
    → ai_video_generation_pipeline.execute()
        → ai/video_generation_client.generate()        ← ★ 11 个切片在这里被消费
```

而画布走的是：

```
canvas_aigc.generate_video_via_host(:1328)
    → _resolve_aigc_channel(:996)          ← 静态渠道解析
    → local_generation_registry            ← 取「第一个可用」本地后端
```

**⇒ 两条生成链是平行的、互不相通。**
**画布生成目前是「静态选路」**（按 channel_id 直查），
**异构引擎是「动态选路」**（按目标函数实时决策）—— **两者没有打通。**

### 1.4 这个缺口意味着什么（值得记）

1. 异构引擎的三大能力（**PI 影子价格控成本** / **渠道池与能力探测** / **质量先验与降级**）
   在**画布生成上完全不生效** ⇒ 画布消耗云端额度**不经过预算与价格控制**。
2. 我在 V4.40.17-20 加的 `video_gen` / `local-video-generate` **同样绕过了**这套引擎 ⇒
   它与 `provider_caps`（渠道能力声明）等既有治理机制**天然脱节**（这是我第二次在同一个盲区上撞车：
   上一次是没发现 `local_video_infer`，这次是没发现治理层）。
3. **这正是一个高价值改造点**：把画布的 `_resolve_aigc_channel` 升级为「问异构引擎要决策」，
   即可让画布生成也享受动态选路。但**改动面大、要动主链路**，须专门评估。

## 第二部分 对用户提供文案的逐条核实

### 2.1 diffusers（首选）—— ✅ **准确**

| 文案说法 | 核实 |
|---|---|
| pip 装、进程内 `pipe()` | ✅ |
| Apache 2.0 | ✅ |
| 已有 WanPipeline / MiniMaxH3ModularPipeline / CogVideoX / HunyuanVideo / LTX-Video | ✅ 与项目 `local_video_infer.py` 的 `PIPELINE_CLASS_MAP` 一致 |
| 短板：跨 runs 缓存、节点级重跑、显存调度要自己写 | ✅ 完全成立（本项目的 `TUNED` 表正属于「自己写的显存调度」） |

**评价**：这就是项目**已经在用**的层，评价中肯。

### 2.2 DiffSynth-Studio（魔搭）—— ⚠️ **基本准确，但漏了一个关键项目**

| 文案说法 | 核实 |
|---|---|
| 魔搭出品、pip/源码引入、纯 Python API + 可选 Gradio | ✅（配套 `DiffSynth-WebUI` 提供图形界面） |
| Apache 2.0 | ✅（社区通行，最终以仓库 LICENSE 为准） |
| 重构 TextEncoder/UNet/VAE，支持 Wan/HunyuanVideo/CogVideoX | ✅（并含 LTX-2、Mochi、StepVideo、ACE-Step 等） |
| **内置 FP8 量化** | ✅ `computation_dtype: torch.float8_e4m3fn`，另支持 **FP8 训练** |
| **磁盘卸载** | ✅ 且是**逐层（Layer 级）Disk Offload**，四态状态机（offload→onload→preparing→computation） |
| **序列并行** | ✅ 多卡序列并行 |
| **低显存** | ✅ **官方称 Wan2.1-T2V-1.3B 最低 8G 显存**；HunyuanVideo 在 6GB 下可出 129×512×384 |
| 短板：社区体量小于 diffusers、新模型适配慢半拍 | ✅（README 自述「开发人员有限，进展较慢」） |

**★ 文案漏掉的关键点（建议补上）**：DiffSynth 其实是**两个项目**——
- `DiffSynth-Studio`：**面向学术界**，激进技术探索
- **`DiffSynth-Engine`：面向工业界，聚焦稳定模型部署，提供更高的计算性能与更稳定的功能** ← 2025-03-25 开源

⇒ **对「执行引擎」这个诉求，`DiffSynth-Engine` 才是更对口的那个**，评估时应一并看。

**对本项目的适配判断**：它的**逐层磁盘卸载 + FP8** 正是 8GB 卡的解药
（对比我现在靠「调小 `decode_chunk_size`」抠显存的做法，是**量级更彻底**的方案）。
**建议实测**：拿它跑一次 Wan2.1-T2V-1.3B，与现有 `local_video_infer` 对比显存与耗时。

### 2.3 SGLang / vLLM-Omni —— ✅ **准确，且可补一条更硬的短板**

| 文案说法 | 核实 |
|---|---|
| 独立 serving 进程，HTTP `/v1/videos` | ✅ vLLM-Omni 提供 `POST /v1/videos`（异步任务）+ `/v1/videos/sync`（同步阻塞），**OpenAI 兼容** |
| 接口/日志由你定，不是黑盒 | ✅ 服务边界清晰 |
| 官方验证是 8×B200，消费卡基线不明确 | ✅ **成立**：官方 profile 均为多卡 + 大主机内存（例：SGLang 双 RTX 5090 profile 需 **~384 GiB 主机内存**）；文档明说「单卡 CPU-offload 配方**未确立 24/32GB 的基线**」 |
| 版本 | SGLang **v0.5.19**(2026-09-03) `sglang.multimodal_gen`；vLLM-Omni **v0.28.0**(2026-08-31)；另有 **xDiT/xfuser** 作 USP/PipeFusion 参考实现 |
| 许可 | vLLM-Omni 标注 **Apache 2.0** ✅ |

**★ 要补的硬短板（对你这台机器尤其致命）**：它实际要的不只是显存，**还有巨量主机内存**。
本项目机器 **RAM 仅 15.3GB**，而官方 profile 要 **384 GiB** ⇒ **当前形态完全不可行**，
即使单卡配方也要求在 24/32GB 显存级别。
⇒ 结论：**SGLang/vLLM-Omni 属「将来有多卡/服务器再说」的选项，现在不必考虑。**

## 第三部分 综合建议（按优先级）

| 优先级 | 建议 | 理由 |
|---|---|---|
| **P0** | **打通「画布生成 → 异构引擎」** | 这是本次核查发现的**最大结构性缺口**：画布生成绕过全部治理（预算/价格/渠道能力/质量先验）。收益高但改动面大，须先出方案再动 |
| **P1** | **实测 `DiffSynth-Engine`**（含 `DiffSynth-Engine`，不只是 Studio） | 逐层磁盘卸载 + FP8 直击 8GB 卡痛点；Apache 2.0 可商用 |
| **P1** | **收敛 `local_video_infer` 与 `video_gen` 两套重复** | 既有模块已支持 LTX-Video（8GB 卡上 diffusers 侧唯一被社区验证的路径），且已进注册表 |
| **P2** | 引入**步数蒸馏档**（预览 4~8 步 / 成片 20+ 步） | 收益 20x 量级；注意蒸馏模型**要求 CFG=1.0**（守卫已留 `distilled` 旁路） |
| **P3** | 研读 **LiteLLM** 收敛渠道层 | MIT 可商用，与 `_resolve_aigc_channel` + `translate_*` 同构 |
| **✗ 不做** | ComfyUI 宿主 / SGLang·vLLM-Omni | 前者 GPL 闸门；后者需 384GiB 主机内存，与 15GB 现实差距过大 |

> **一句话总结第一部分**：异构动态协作引擎**没有**用在这条链路上 ——
> 它是 Agent 侧的「动态选路层」，而画布侧仍是「静态查表」。
> 这不是 bug，但是**一个真实的能力落差**，也是本次调研最值得你决策的一件事。
