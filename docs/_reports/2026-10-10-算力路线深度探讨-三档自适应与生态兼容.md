## 0. 结论（三句话，先看这个）

1. **「本地大模型生成是既定方向，云 API 是兜底+加速」——这个主从关系确认为产品宪法**；
   面向用户硬件差异，落地形态升级成「三档自适应」（全云档 / 主流档 8G / 满血档 16G+）。
   **代码地基已经建好 80%**（探测/水位守卫/选路单点/主备降级全在），不是推翻重来。

2. **「吸收 ComfyUI 的模型优化能力」已经内化了 80%**：它的优化能力实质 = DiffSynth 的
   vram_management（ComfyUI 生态都来抄它）+ accelerate offload + 量化加载——前两样
   我们已通过「主选 DiffSynth + memory_policy 五档」拿到手；**缺的只有 W2 量化档
   （NF4/INT8）和 mmap 磁盘卸载**，落成新任务 H2。用户零门槛：pip 双栈几百 MB、
   模型按需单个下，**永远不需要用户下载 ComfyUI**。

3. **音乐域 8G 本地其实有解**：ACE-Step 1.5（Apache/MIT 可商用、8GB 以下、活跃维护，
   10-09 盘点已核实）排在 Q9 实测——过了它就是本地音乐主力，YuE 退居「远程音质上限选项」。

## 1. 问题一：用户硬件千差万别，产品该押谁？

### 1.1 行业事实（不是猜测）

| 用户群 | 典型硬件 | 占比直觉 | 他们的选择 |
|---|---|---|---|
| 短剧创作者（大众） | 核显轻薄本 / 普通办公本 | **最大池** | 即梦/可灵/剪映——**根本不想装任何东西** |
| 入门 AIGC 玩家 | 8G 游戏本（= 你这台 4060） | 中 | 想省钱、愿意装一个 App，但不想装 Python 环境 |
| 发烧友 | 16-24G+（5-10 万 DIY 机） | 小 | 自己就是 ComfyUI 用户，什么都想本地跑 |

**关键洞察**：你担心的「不是人人有 5-10 万机器」完全正确，但答案不是「放弃本地转全云」——
参考项目 AI-Canvas-tauri 就是全云路线（已核实：本地只跑 ONNX 超分/抠图，生成全走云），
**它因此对 8G 用户没有任何省钱优势，还把每次生成都变成付费调用**。
你的「本地为主」直觉恰好卡中了中间那个最大的付费意愿层：**有 8G 卡、想省钱、怕折腾**。

### 1.2 答案：三档自适应（硬件探测 → 路由表）

| 档位 | 探测条件 | 图像生成 | 视频/音乐/LLM | 用户感受 |
|---|---|---|---|---|
| **全云档** | 无独显 / ≤4G / 探测失败 | 云 API（16 家） | 云 API | 装了就能用，按量付费（= 即梦体验） |
| **主流档（8G）** | 6-12G 独显 | **本地双栈主选**（SD1.5/SDXL 零调用费）→ 云兜底加速 | 云 API 为主 + ACE-Step 音乐（若实测过） | 生图免费不限量，大模型按量 |
| **满血档（16G+）** | ≥16G | 本地主选 + **ComfyUI 通道提示可用** | 本地可解锁更多（远程 YuE 端照跑） | 自己装的 ComfyUI 资产全部复用 |

**比喻（小白模式）**：这不是选一种餐厅，是开一家**按客人身材自动上菜的私厨**——
没带钱包的客人（核显）走自助餐区（全云按量付费）；带了饭盒的客人（8G 卡）家常菜用他家灶台
现炒（本地生图，免费）；自带全套厨具的大厨（发烧友）直接进后厨自炊区（ComfyUI 通道）。
**灶台探测（nvidia-smi）进门时做一次**，菜单自动切换，客人无感。

### 1.3 为什么说地基已有 80%（代码证据，不是愿景）

| 已有件 | 位置 | 作用 |
|---|---|---|
| GPU 探测 | `gpu_acceleration.py:94 _detect_nvidia()` 走 nvidia-smi（解析显存 `:200`） | 三档判定原料 |
| **显存水位守卫** | `model_registry.py`（2026-10-09）：懒加载 + LRU 驱逐 + 15% 安全余量 + **探测失败如实报告不编假数** | 档位内的模型调度 |
| **选路单点** | `execution_decider.py::decide_execution()`（R2 铁律：选路只在这一处） | 挂三档路由的唯一位置 |
| 主备降级 | `resolve_local_image_engine()`：首选不可用自动降备选 + R9 留痕 | 档位内降级已验证 |
| 云兜底 | 16 家 provider + `_resolve_aigc_channel` | 全云档路径现成 |

**缺的只有一块**：`decide_execution()` 目前不读显存探测结果做档位判断——把
`_detect_nvidia()` 的显存数字接进 reasons + 路由偏好，三档就成型了。改动量：小。

### 1.4 这一节的决定

> **「本地为主，云兜底加速」升级为「三档硬件自适应」**：主轴不变，表述更准。
> 新增任务 **H1：硬件分档自适应路由**（挂进 execution_decider，本季，A 类零解冻）。
> 你自己这台 4060 = 主流档，等于「开发环境 = 目标用户的主流环境」，测试天然代表性。

## 2. 问题二：怎么把 ComfyUI 的「模型优化能力」吸收进来——**又不让用户下载 ComfyUI**？

> **（2026-10-10 第二轮用户澄清，本节已按此重写）**用户意图精确定位：
> 想要的是 ComfyUI **本地部署时对模型的优化能力**（8G 卡硬跑大模型的那套显存技术），
> 引入到我们项目里；**不想要的是 ComfyUI 本身**——它连模型包动辄 70G-100G，太重。
> 「本地大模型生成本来就是项目的既定方向（短剧/漫剧/视频/音乐）；云 API 是因为显存
> 不够部署强模型的设备才引入的兜底 + 加速。」——主从关系以此为准。

### 2.1 先把「体积」算明白（小白模式）

**ComfyUI 的 70-100G 不是程序，是模型全家桶**：

| 组成 | 实际体积 | 性质 |
|---|---|---|
| ComfyUI 程序本身 | < 1G | 程序 |
| 一个 SDXL checkpoint | ~6.9G | **权重数据** |
| 一个 Flux checkpoint | ~24G | 权重数据 |
| 社区工作流常用的模型组合 | 几十~上百 G | 权重数据（用户被工作流裹挟全家桶式下载） |

**关键认识**：模型权重是**数据**不是程序，任何方案都省不掉（我们要跑 SDXL 也得下那 6.46G，
已实测在库）。真正的差别是——ComfyUI 用户往往被社区工作流带着全家桶式下载；
**我们的双栈方案是「按需点菜」：pip 装库几百 MB，模型一个一个按需下，registry 懒加载管理**。
所以「不下载 ComfyUI」的真实收益 = 不装那个庞然大物 + 不进依赖地狱 + 不被裹挟下全家桶，
**而不是「不下模型」**（模型该下还得下，这条对谁都一样）。

### 2.2 好消息：这套优化能力，项目已经内化了 80%（附证据）

「ComfyUI 对模型的优化能力」拆开看其实是四样东西，逐一对照我们的现状：

| ComfyUI 的能力 | 实质 | 我们的等价物 | 状态 |
|---|---|---|---|
| 显存管理器（--lowvram/block swap 分块卸载） | PyTorch + accelerate 的 offload 能力包装 | **`memory_policy.py` 五档装载决策**（whole/model/sequential/layer_cpu 四档可用，全部走 accelerate hooks；SVD/SDXL 实测基线，含两次反转定稿纪律） | ✅ **已有** |
| 模型注册/懒加载/显存水位 | 调度逻辑 | **`model_registry.py`**（懒加载 + LRU 驱逐 + 15% 安全余量 + 探测失败诚实报告） | ✅ **已有** |
| 底层推理引擎的显存优化 | DiffSynth 的 vram_management（**连 ComfyUI 生态的 WanVideoWrapper 都封装它当节点用**，V4.40.22 裁定依据②） | **主选引擎就是 DiffSynth-Engine**（pip 库形态：不带节点生态、不带全家桶，自带逐层磁盘卸载 + FP8/INT8/NF4 量化能力） | ✅ **已有** |
| GGUF/量化加载节点 | gguf + bitsandbytes 等开源库的包装 | `quant` 档当前恒 `"fp16"`（`memory_policy.py:217`：FP8/NF4 是 W2 目标） | ⬜ **未落——这是缺口** |

**一句话**：你要的东西 = 「DiffSynth 的显存管理 + memory_policy 的分档调度 + W2 量化档」。
前两样已经在跑（这就是 V4.40.22「主选 DiffSynth」裁定的本意——那条 CHANGELOG 原文写着
「W1/W2 是主线，正是 DiffSynth 被 ComfyUI 生态抄走的那部分显存管理」）；**真正缺的只有
W2 量化档和 layer_disk_offload（mmap 逐层磁盘卸载，`memory_policy.py:41-43` 诚实标注还没做）**。

### 2.3 双引擎各管一摊（这个结论维持）

```
自研双栈（DiffSynth 主选 + diffusers 备选）      ComfyUI 通道（comfy_provider + /host/comfyui/run）
────────────────────────────────────           ─────────────────────────────────────────
服务：全云档 + 主流档（最大用户池）              服务：满血档发烧友（已装用户）
形态：pip 装库、代码内嵌、用户零感知              形态：用户自装、我们 HTTP 调用、资产复用
治理：12 治理切片 + model_registry 水位守卫      治理：不插手（它自成体系）
门槛：无                                        门槛：用户自己付（他们付得起也愿意付）
```

**为什么自研主轴不可替代**（V4.40.22 CHANGELOG 裁定原话）：「治理层 12 切片 / 渠道统一 /
深度集成——这三样 DiffSynth 完全没有，是自研存在的理由」。ComfyUI 给不了：
生成前查账本推荐（draw_book）、生成后自动评分入账（gen_critic）、预算控制（budget_pacer）、
按档位降级（R9 留痕）——**而这些恰恰是「面向结果的生产线」区别于「面向过程的工具」的命根**。

### 2.4 全云档用户想要 ComfyUI 生态怎么办（远期选项，本季不做）

行业解法 = **云 ComfyUI 平台**（runninghub / comfydeploy / fal 这类）：模型和工作流都在云上，
用户零安装。参考项目已把 runninghub 做成 provider 之一。我们的 provider 体系未来接一家即可
（量级：一个 provider 类，~200 行），**不需要自建、也不需要现在做**。

### 2.5 这一节的决定（按用户澄清修正）

> ① **「吸收 ComfyUI 优化能力」的正确落点 = 完成引擎自身的 W2 量化档 + layer_disk_offload**，
> 而不是引入 ComfyUI 或做节点适配——新增任务 **H2：引擎显存优化补全**（本季，B 类：NF4/INT8
> 量化落地 + mmap 逐层磁盘卸载，门槛沿用 W2 原定「画质退化 PSNR ≥30dB 才上线」）。
> 落地后 8G 主流档的模型上限直接抬高一档（DiffSynth 官方：Wan2.1-1.3B 8G 可跑即含此能力）。
> ② 双引擎分层维持：自研双栈当主轴（H1 三档路由地基）；ComfyUI 通道只对满血档已装用户。
> ③ 仍然不做：自研 ComfyUI 节点、本地打包 ComfyUI（用户的「不下载 ComfyUI」诉求恰好由
> pip 双栈满足）。云 ComfyUI 平台 provider = 远期登记不排期。

## 3. YuE 深算：3B 的模型为什么要 24G 显存（小白模式算账）

这是你点名的例证，把它算透，以后所有「模型体积 vs 部署门槛」的判断你都能自己做。

### 3.1 核心公式：显存占用 ≠ 模型体积

**比喻**：显存 = 后厨灶台面积；模型权重 = 常驻锅具；推理时的中间状态 = 颠勺的操作台。
「3B 模型」只告诉你锅具有多大，没告诉你这道菜要同时摆开多少备菜台。

### 3.2 五笔账（YuE 为什么 24G 不是虚标）

| # | 账目 | 大约 | 说明 |
|---|---|---|---|
| 1 | 模型权重 | 3B 参数 × FP16 = **6GB**（每 10 亿参数 FP16 占 2GB，通用算法） | 常驻，卸不掉 |
| 2 | **双塔接力架构** | ×2 ⇒ **12GB 级** | YuE = 语义塔（歌词→音乐语义 token）+ 声学塔（语义→波形 token）**接力生成，两塔都要常驻**——这是它和单塔 chat 模型的本质区别 |
| 3 | **KV cache（长序列记忆）** | 数 GB 且随长度涨 | 音乐 = 几分钟音频 = **上万 token 的长序列自回归**，每步都要记住前面所有内容。这是音乐 LLM 比 chat LLM 吃显存的第一原因——chat 一句话几百 token，一首歌几万 |
| 4 | 激活值/中间张量 | 数 GB | 推理时的临时工作区，和模型大小成正比 |
| 5 | 工程安全余量 | ~15% | PyTorch 显存碎片 + 防 OOM（我们 model_registry 的 15% 余量同款思路） |

**合计：权重 12G + KV cache 数 G + 激活数 G + 余量 → 24G 门槛是工程上诚实的结果，不是官方乱标。**

### 3.3 8G 硬凑的三条理论路，为什么条条是坑

| 路 | 原理 | 为什么是坑 |
|---|---|---|
| INT4 量化 | 权重 6G→1.5G/塔 | **只省权重**：KV cache 和激活值原样不动；且音乐自回归对量化极敏感（音高漂移/伪影），社区无现成 YuE 量化版——**自己调 = 研究级工作量，调通了也未必能听** |
| CPU offload | 权重分块搬 CPU，用时搬回 | 音乐生成 = **几千步自回归，每步都要 PCIe 往返搬一遍权重** → 分钟级变小时级。「能跑」≠「能用」，差一个量级 |
| 分段生成 | 把歌切成 30 秒一段 | 段间衔接处音乐断感；编曲一致性（调性/乐器/情绪跨段延续）正是 YuE 的核心价值，切段 = 自废武功 |

**这就是项目「诚实失败」铁律的由来**（YuE 执行端不可用必须如实报错、绝不返回假音频）——
不是道德姿态，是**算过账之后的工程结论**：8G 硬凑的每条路的产出都不配进产品。

### 3.4 音乐域的完整结论（有惊喜）

之前「音乐只能远程/云」的悲观结论要修正——**10-09 盘点核实过的事实**（`外部模型依赖盘点.md:134`）：

| 模型 | 权重许可 | 显存 | 状态 | 定位 |
|---|---|---|---|---|
| **ACE-Step 1.5** | **Apache/MIT（可商用）** | **8GB 以下** | 活跃更新 | **本地音乐主力候选**（Q9 实测一晚，过了就进能力目录） |
| DiffRhythm | Apache-2.0 | 8G（--chunked） | 停更 10 个月 | 备胎不押 |
| YuE 2.x | **CC BY-NC（商用需授权）** | 24G | — | **远程执行端**（SHIGUANG_YUE_ENDPOINT 已定）= 音质上限选项；且商用本身有许可墙 |
| MusicGen（Meta） | CC-BY-NC + 纯器乐无人声 | 1.5B/8G 无压力 | — | **排除**：许可不可商用 + 唱不了带词的歌，两条硬伤 |

> 顺带把 MusicGen 也查了：本地跑得动但权重 CC-BY-NC（和 YuE 一个坑）+ 只出纯音乐不出人声——
> 记录在案，以后不用再纠结它。

**音乐域三件套（定稿）**：① ACE-Step 1.5 本地实测（Q9 已排，Apache/MIT 无许可顾虑，
过了 = 主流档用户的本地免费音乐生成）② YuE 远程端保持「音质上限/进阶选项」定位
③ 云 API 兜底。**YuE 的 24G 门槛从此不再是我们的问题——它是「满血档/远程端用户」的选项，不是主流档的债。**

### 3.5 这一节的决定

> 不给 YuE 做任何本地量化适配（三条路全是坑，已算账）；ACE-Step 1.5 实测提前到
> **本季 E2 同批**（反正都要下模型，一晚实测两件事）；音乐域按三件套执行。
