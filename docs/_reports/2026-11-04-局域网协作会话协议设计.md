## 二、三处明确不同意的部分

### 2.1 mDNS 不该替换现有 UDP 发现

**你的方案**：`_yourcreativeapp._udp.local.` 服务广播 + 自签证书指纹身份。

**不采纳的理由（实测，不是口味）**：

1. **Windows 没有内置 mDNS service responder**。macOS 有 Bonjour 常驻、Linux 要 avahi，
   Windows 上要么让用户装 Bonjour（装机门槛），要么随包带一个 responder（体积 + 防火墙再弹一次窗）。
   而我们现在的 `team_discovery.py` 是**纯标准库**，零依赖、零安装。
2. **现有实现已经解决了三个真实的坑**（`team_discovery.py:130-180`）：
   - `Beacon.stop()` 后 `_stop` 未复位 ⇒ 停止再启动后 beacon 线程立刻退出，**扫描永远扫不到，界面现象和"网络限制广播"一模一样**；
   - listener 端口占用 ⇒ 静默降级成"只广播不响应"，同事主动扫也扫不到；
   - 广播抑制（企业 Wi-Fi）⇒ **主动 DISCOVER + 单播回复**兜底。
   换 mDNS 等于这三个坑重踩一遍，且新增一个第三方依赖。
3. **mDNS 唯一真正多出来的能力**：能被系统级工具/其他软件看见（Finder、打印机面板那种）。
   我们暂时不需要这个互通性。

**处理方式**：保留 UDP 45123 作为主通道；如果将来要做「手机/平板端也能发现」，再加 mDNS 作为**并列的第二通道**（两者写进同一份 `DiscoveredServer` 列表，去重按 host:port）。**设备身份（自签指纹）与发现机制解耦**——指纹该做，跟 mDNS 无关。

### 2.2 WebRTC / QUIC 在局域网内是负优化

**你的判断**：「WebRTC DataChannel 局域网 5–10ms，对画布同步绰绰有余」「QUIC 多流让大文件不阻塞实时消息」。

**我的实测对照**：

| 场景 | 我们现在的做法 | 实测 | 换 WebRTC/QUIC 的收益 |
|---|---|---|---|
| 512MB 成片上传 | HTTP 分块 POST + 进度回调（`teamUploadAsset`） | 局域网满速，无阻塞问题 | ≈0 |
| 画布同步（100MB 上限的 bundle） | HTTP POST 整份快照 | 局域网内秒级 | 需要把 HTTP 换成 DataChannel，**没有变快，只是变复杂** |
| 实时消息（谁在改哪） | 12 秒 HTTP 轮询（0.3.50 已做） | 够用 | 5ms 延迟对"谁在改第 3 卡"毫无意义 |

**关键点**：WebRTC 的不可替代价值是 **NAT 穿透**（跨公网、跨 NAT 直连），不是局域网延迟。在同一个 AP 下面，TCP 已经接近物理极限。上 WebRTC 要付的代价是：信令服务器、DTLS 证书、ICE 候选收集、多网卡选择、以及"ICE 失败时的降级路径"——**为 0 收益付一整套复杂度**。

**采纳边界**：一旦要做「同事在家里 / 在另一个项目部，不在同一局域网」→ 那时 WebRTC 是**必需品**，我第一个上。现在就上就是过度设计。

**「大文件阻塞实时消息」这个真问题**，我们用更土的办法解决且已够用：大文件上传时把状态行切成 `上传 3/8：xxx.mp4 46%`，实时消息走独立的 12 秒心跳定时器，互不排队（HTTP 服务端是 `ThreadingHTTPServer`，`daemon_threads=True`，本来就不阻塞）。

### 2.3 纯 P2P + CRDT：在**我们的数据模型**上代价被低估了

**你的判断**：「画布空间属性用 CRDT 或属性级 LWW，破坏性操作走锁」。

方向我同意，但有一个你可能没看到的成本：

**我们现在的数据模型是「整份 bundle 快照」**——`_write_bundle()` 把整个 `{nodes, edges, stage3d, ...}` 序列化成 JSON 存成一版（上限 100MB，`team_hub.py:54`）。CRDT 要生效，前提是**状态被拆成可独立合并的单元**（每属性一个寄存器/计数器）。这两者之间隔着一层重构：

```
现在：project.rev → bundle.json（不可分割的整体）
CRDT 要求：node[n].data.position.x 是独立 LWW 寄存器
```

也就是说：**上 CRDT 之前必须先做「bundle → 规范化结构 + 属性级时间戳」的存储改造**，否则只能做整份 LWW（＝谁最后上传谁赢，等于现在的 `push` 冲突检测，没有进步）。

**所以我的方案是「分层一致性」**（见 §三.2），只在本该用 CRDT 的那一层用它，而不是把 CRDT 铺到全系统。

## 三、分层一致性模型（本方案的核心判断）

把「同时编辑」按**数据性质**拆成四层，每层用不同的一致性策略。这不是折中，是因为这四层的冲突语义本来就不一样。

| 层 | 内容 | 一致性策略 | 为什么 |
|---|---|---|---|
| **L0 结构层** | `nodes` / `edges` / 节点属性（位置、可见性、文本） | **属性级 LWW**（每属性带 `updated_at` + `author`），节点级锁兜底 | 两个人在不同属性上改，本来就不冲突；同属性冲突时"后来的赢"符合直觉 |
| **L1 时间线层** | `clips`（顺序、时长、入出点） | 🔴 **必须单权威**（主机/持锁者），禁 CRDT | 序列语义强：LWW 会产生「A 的第 3 段插到 B 的第 2 段后面」这种**看着不报错、剪出来是错的**结果 |
| **L2 资产层** | 图片/视频/音频字节 | **内容寻址，天然无冲突** | `blobs/<sha256>`：同一份文件谁传都落到同一个名字。这是我们**已经有的、别人没有的优势** |
| **L3 意图层** | 谁在看哪、锁了什么、这一步想干嘛 | **纯广播，不需要一致性** | 只是"状态显示"，丢了不损失数据，下个心跳会补上 |

**关键结论**：L2 已经解决了你方案里"资产只传引用、按需拉取"的全部需求——**我们不需要再做一套引用协议，只需要把"按需拉取"的触发点做出来**（现在缺的是"我这没有这个 sha，去谁那儿拿"的设备寻址）。

## 四、接续快照：把它做成真正的一等公民

这是你方案里最值钱的一条，我完全同意。而且好消息：**我们已经有 3 块料，缺的只是把它们组装成一个对象**。

### 4.1 已有的料

| 已有能力 | 位置 | 在接力包里的角色 |
|---|---|---|
| 覆盖前自动另存为新本地工程 | `teamBackup.ts::backupBeforePull`（0.3.47） | 接续时的**本地安全网** |
| 版本 + 备注 + 回滚（历史只增不删） | `Hub.rollback` / `TeamVersions.tsx`（0.3.48） | 接续的**可追溯性**：「他接力的是第 5 版」 |
| 在线状态 / 最后活跃 | `member.last_seen` + `teamPresence.ts`（0.3.50） | 接续的**时机判断**：「他现在在不在，推给他有没有意义」 |
| 内容寻址资产 | `blobs/<sha256>` | 接力包里的**资产引用**（只带 sha，不带字节） |

### 4.2 缺的四样（这才是要做的）

```ts
/** 接续包 = 一次「接着做」的完整上下文（不是文件包） */
type Handoff = {
  handoff_id: string;
  project_id: string;
  base_rev: number;              // 基于服务器第几版（已有）
  from_device: string;           // 谁推的（新增 device 维度）
  to_member: string;             // 推给谁
  // ① 视图状态：打开就落在同一处，而不是从头找
  viewport: { x: number; y: number; zoom: number; selected: string[] };
  // ② 意图标记（L3 层，轻量）
  intents: Array<{
    scope: "node" | "project";
    target: string;              // node id
    state: "done" | "wip" | "blocked" | "todo";
    note: string;                // 「调色已完成，等合成」
  }>;
  // ③ 待办清单
  todos: Array<{ id: string; text: string; done: boolean; owner?: string }>;
  // ④ 资产引用（只 sha，不含字节）
  assets: Array<{ sha256: string; name: string; kind: string; bytes: number }>;
  created_at: number;
};
```

**和现在「交接」的区别**（现在只有 `handoff(project_id, to, message)`，一个字符串 + 一个项目 id）：

| | 现在 | 接续包 |
|---|---|---|
| 打开后看到什么 | 一个项目，从头找 | **落在同一处画布位置、同一缩放、选中同一批节点** |
| 要做什么 | 自己猜 | 待办清单 + 每块的状态标记（已完成/进行中/等他/别动） |
| 资产 | 全量拉取 | 已经有 sha 的直接复用，只拉缺的 |
| 追溯 | 一条留言 | 基于 rev N，可 diff、可回滚 |

### 4.3 「一键接续」的交互（这是差异化所在）

```
A 点「推给李四继续做」
  → 自动打一个「意图包」：当前视口 + 选中节点 + 他刚标记的状态 + 待办
  → 先 push 到服务器（产生 rev N+1），再把这个包挂到 rev N+1 上
B 的机器（在线时）：
  → 12 秒心跳里收到「有一个接续包」
  → 面板顶部一条：「张三 把「第三集」交给你继续 —— 第 6 版，3 条待办，1 处等你确认」
  → 点「接续」：本地先另存（复用 0.3.47）→ 拉 rev 6 → 恢复视口/选中/标记 → 顺手 claim
```

**全程不需要聊天软件补充上下文**——这就是你说的「把进度从一段文字变成可加载的会话状态」。

## 五、设备层（你的自签指纹方案，采纳）

### 5.1 现状缺口

`TeamCred = { address, member_id, name, token }`（`teamClient.ts:28`）——**只有"人"，没有"机器"**。后果：

- 一个人台式机 + 笔记本，两条令牌**分不清谁是谁**，在线状态会显示成两个人；
- 接续包没法说"推给他的**那台有 GPU 的**机器"；
- 资产缓存没法按设备算（哪台机器上有这个 sha）。

### 5.2 设计

```python
# app/core/team_device.py（新文件）
device_id = SHA256(公钥)          # 自签 keypair，首次运行生成，存 data/team/device.key
# 注册到团队时带上去，member = 人，device = 机器，一张 member 下挂 N 个 device
```

- `member` 表不变（人 / 角色 / 令牌）
- 新表 `device(id, member_id, name, platform, fingerprint, last_seen, caps JSON)`
- `caps` 放**能力标签**：`{"gpu": "RTX 4070", "vram_gb": 12, "can_run_local_model": true}`
  → 这才是"把重活派给有卡的机器"的基础
- 广播 payload 从 `{app,name,port,host,ver}` 扩到带 `device_id` + `caps` 摘要

### 5.3 为什么用指纹而不是随机 UUID

随机 UUID 也能唯一标识，但**指纹可以离线验证**：两台机器交换证书时能确认"还是上次那台"（TOFU 模型），不需要服务器背书。这对"团队内部网络"这个定位是对的。

## 六、实施路线（按「是否真的解决你的问题」排）

| 阶段 | 内容 | 为什么排这个位置 | 验收 |
|---|---|---|---|
| **S1** | 设备身份（`device` 表 + 指纹 + 广播带 caps）+ 成员/设备分离显示 | 一切设备级能力的地基；现在不做，后面每一条都要返工 | 一人两机显示成「张三 · 台式（在线）· 笔记本（8 分钟前）」 |
| **S2** | **接续包**（Handoff 对象 + 意图标记 + 待办 + 视口恢复 + 一键接续） | 你要的核心价值，且能复用 0.3.47/48/50 三块料 | A 推到 B，B 点接续后**画布落在同一处、看到待办**，≤3 次点击 |
| **S3** | 节点级锁（L0/L1 分层的落地）：`claim(project, node_id)`，时间线段落用强制单权威 | 没有它，L0 的 LWW 会撞到 L1 的序列语义 | 两人同时改不同节点不冲突；改同一节点第二人被拦并看到「李四 在改」 |
| **S4** | 资产按需拉取（设备缓存索引：谁有哪个 sha → 直连取，主库只做兜底） | 解决"服务器磁盘线性膨胀"，也是"内部渠道传产物"的正解 | 服务器不再随产物线性增长；缺资产时自动去有它的设备取 |
| **S5** | 意图广播（谁在看哪、在改哪，60 秒窗口） | 体感提升，但不影响数据安全，可最后做 | 面板显示「李四 正在改 镜 03 · 2 分钟」 |
| 远期 | 异地协作（WebRTC + 信令中继） | 只有团队不在同一网络时才需要 | —— |

**明确不做**：
- ❌ 全 mesh 多主复制（每台机器都是权威 ⇒ "谁是第 6 版"立刻爆炸）
- ❌ 时间线层 CRDT（会产生"看着对、剪出来错"的序列）
- ❌ 局域网内 WebRTC/QUIC（0 收益换一整套复杂度）
- ❌ 公网穿透（除非明确要做远程协作）

## 七、风险与已知代价

1. **主机掉线**：现在单主机权威，掉线=协作中断。S5 之后可以考虑「迁移主机」（最后活跃的设备被选举接管），但**这是最后一件事**——迁移期间的双写一致性比掉线本身更难处理。
2. **AP 隔离**（客户端隔离）：能收到广播、TCP 连不上。这是**网络策略**，软件无法自愈，只能明确告知「找网管关掉隔离」。
3. **防火墙首次拦截**：Windows 弹窗被用户点「拒绝」后会永久静默失败 ⇒ S1 要加**自查**：监听成功后主动连一次自己，失败就明确说「防火墙拦住了 18770」。
4. **信任边界**：配对码是 6 位数字（100 万组合），已有 1 分钟 10 次限速。但**入队即全权限**（`role` 不参与鉴权）——这是现存最大的安全洞，应在 S1 一并修掉。

| 你的原则 | 落地形态 |

**核心创新空间确实在第 4 项**——而我们的优势是：前三项已经跑起来并且踩平了坑，所以能把全部精力放在"让接续在界面上一键发生"这件事上。
