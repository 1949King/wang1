## 0. 结论速览（30 秒版）

**Q1：AI 画布模块的发展方向是否有正确的理论和方向？**

**有**。三层理论模块（整合稿 / E1 / AgentOS）**互不冲突且互为依赖**，方向清晰且各自内部的判定标准稳健。

| 层 | 模块 | 角色 | 一句话 |
|---|---|---|---|
| **战略** Why | 整合稿「双模式双生态 + 双向电梯」 | 卡位 + 流通 | 站 ComfyUI ↔ 剪映中间地带的卡位 |
| **接口** How 接口 | E1「意图类型契约」 | 校验 + 编排 | 过滤合法性 + 不破坏磁吸几何 |
| **基础设施** How 运行时 | AgentOS S1-S5 五柱 | 调度 + 通知 | 通用 OS 抽象的画布专属化 |

**Q2：是否还需要迭代设计理念和概念？**

**「理念」不迭代，但「执行蓝图 + 基础设施」要补强**。三个补强点（详见 §4）：

| # | 缺口 | 风险 |
|---|---|---|
| ① 蓝图执行断点 | 14 个 P0-P3 动作**没有时间窗 + 没有验收守卫** | 进入 UI 冲刺期就被推迟 |
| ② OS 维度空缺 | S2 进程模型 + S3 通知中心**完全没做** | 执行阶段任务跑出问题没人接管 |
| ③ 双向电梯目前是单向 | 向下降梯（ComfyUI 工作流 → 配方）= **0 进展** | 6 个月后改 schema 是噩梦级迁移 |

**判定**：补强 ≠ 迭代。补强在原框架内补空缺；迭代要重设目标。三层理论不动。

## 1. 三层理论模块的依赖关系

```
┌────────── 整合稿（战略层 Why）──────────┐
│  双模式双生态 + 双向电梯                 │
│  · 小白模式收「想法」                    │
│  · 专业模式收「节点」                    │
│  · 同一份数据 · E1 契约 · 多引擎          │
└──────────────┬──────────────────────────┘
               │ 必须有 ↓
┌────────── E1（接口层 How 接口）─────────┐
│  IntentKind（6 类） · PortSpec · 兼容矩阵  │
│  · 仅校验 + 编排 · 不破坏磁吸几何         │
└──────────────┬──────────────────────────┘
               │ 必须有 ↓
┌────────── AgentOS（基础设施层 How 运行时）─┐
│  S1 窗口 · S2 进程 · S3 通知 · S4 技能 · S5 中枢│
│  · 任务提交/取消 · 通知推送 · 调度稳定性    │
└─────────────────────────────────────────┘
```

**判定**：每一层都不能脱离其它两层独立成立：
- 没有 E1 接口层 → 整合稿的双向电梯无法做合法性校验 → 工作流节点 / 配方的导出都可能是错的
- 没有 AgentOS 基础设施 → 整合稿的工作流节点 / Manifest 闸门没法稳定运行（任务卡死、缺模型没人知道）

三层全部对齐才能支撑「想法 → 成片」全链路。

## 3. 方向正确性自洽验证（三个判定标准）

### 3.1 战略层：整合稿的双向电梯卡位

**判定标准**：是否站在竞争品的中间地带无人占位？

| 现有玩家 | 形态 | 优势 | 缺口 |
|---|---|---|---|
| ComfyUI | 节点生态深 | 几千自定义节点 + 工作流 + 模型组合 | 编程门槛高（Python） |
| 剪映 / 剪映 Hub | 小白顺畅 | 一键成片 + 模板丰富 | 无专业节点、难定制 |
| TapNow | AI 节点编辑 | 对话与产物分离 | 资产深但不沉淀到小白层 |
| **本项目** | 双模式双生态 | 中间地带 + 双向电梯 | 0 进展的板块（工作流节点） |

**结论**：整合稿卡位正确。双向电梯提供了纯 ComfyUI 和纯剪映给不了的混合体验。

### 3.2 接口层：E1 契约的「不破坏磁吸几何」

**判定标准**：E1 是否反向决定了吸附位置？

回看 E1 设计稿 §7「反面案例」明确写了：

> 别做：让契约决定吸附位置 — 等于退回显式连线，磁吸的全部价值归零

E1 把契约定位为「过滤 + 反馈」+「不破坏」+「执行序推导」。这与整合稿 §3.5 第一条铁律（同一份数据）一致。

**结论**：E1 抽象方向正确，与整合稿兼容。

### 3.3 基础设施层：AgentOS 五柱完整性

**判定标准**：S1-S5 是否构成通用 OS 抽象的画布专属化映射？

| 通用 OS 抽象 | AgentOS 对应 | 当前缺口 |
|---|---|---|
| 窗口 / Dock | S1 窗口管理 | 无 |
| 进程 / 任务 | S2 进程模型 | 空 |
| 通知 / 推送 | S3 通知中心 | 空 |
| 应用 / 技能 | S4 技能仓库 | 半 |
| 命令 / 调度 | S5 命令中枢 | 雏形 |

**结论**：方向正确，缺口可补。五柱本身不矛盾，与整合稿 / E1 都兼容。

### 3.4 三层互相验证（最终结论）

- 整合稿 ←依赖→ E1：E1 提供合法性，整合稿才能说"双向流通"
- E1 ←依赖→ AgentOS：AgentOS 提供执行，E1 才能说"参与拓扑排序"
- AgentOS ←依赖→ 整合稿：整合稿说"双模式双生态"，AgentOS 才回答"该被设计为 OS 层"

**三层互为依赖、互不冲突。方向正确，不需要换赛道。**

## 4. 理念是否要迭代？—— 三个补强点

### 4.1 补强 #1：蓝图缺执行断点（最严重）

**现状**：整合稿 §5.1 排了 P0-P3 共 14 个动作，**没有时间窗**、**没有验收守卫**、**没有失败回滚条件**。这导致：

- 一旦进入 UI 冲刺期，连续 5 版（V4.41.16 ~ V4.41.20）都没动蓝图
- 哪个 P0 没做不会被自动捕获（缺 ruff 之类的卡点）
- 4 个待拍板 0 答复（待澄清机制缺失）

**修法**（不新增设计）：

| 动作 | 工作量 | 输出 |
|---|---|---|
| 写一份 `_verify/check_blueprint_progress.py` | 半天 | 跑 ruff 时同时跑，缺 P0 报红 |
| 把"Manifest 必须四类状态翻译完整"做成导入器验收 | 半天 | 工作流节点 schema 自带闸门 |
| 4 个待拍板写入 `docs/_archive/knowledge/` 知识库 | 1 小时 | 不再被遗忘 |

**本质**：把"理论 → 落地"补一个单步单步卡口的执行机制。

### 4.2 补强 #2：OS 维度空缺（S2 + S3）

**现状**：S1 + S5 + V4.41.20 = 「**能装、有入口、还不能用**」。进入执行阶段（工作流节点跑 / ComfyUI 任务跑），没有任务管理、没有通知推送。

**问题举例**：
- ComfyUI 工作流节点跑 5 分钟，期间断网 → 用户得不到通知
- 一键按序跑通「导演卡→分镜→镜头→成片」链路，**没有 S2 = 没法后台线程管理**
- "状态翻译映射表"被整合稿放进 P1，但系统没"通知"通道 = 翻译了传不出去

**修法**：

| S | 落实点 | 工作量 |
|---|---|---|
| **S2 进程模型** | 把 `pipeline_jobs.py` 抽象为 S2 引擎（任务提交/状态/取消/retry）；新增 `_verify/check_s2_engine.py` | 1 天 |
| **S3 通知中心（减半版）** | 先做"任务完成 / 模型缺 / 引擎挂" 三类 → nextAction 推送（不先做中心，做"接入点"） | 半天 |
| **S4 技能仓库 集成** | listPlugins / listProjectTools 与工作流节点 schema 对齐 | 半天 |

**关键修法**：**S2 先做、S3 做减半版、S4 集成为主**。这不破坏现有节奏。

**与整合稿关系**：整合稿 P1 「工作流节点 MVP」依赖于 S2 —— 任务发起 → S2 接管 → 失败 → S3 推送，工作流节点才能稳定跑。

### 4.3 补强 #3：双向电梯目前是单向

**现状**：

| 电梯方向 | 现状 |
|---|---|
| **向上**：小白 → 专业 | ✅ V4.41.18 拖动 / V4.41.19 Ctrl+K 100 项 / V4.41.20 浮层可开可关 |
| **向下**：ComfyUI → 小白配方 | ❌ 工作流节点 MVP 没动、Manifest 闸门没动 |

**风险**：整合稿 §5.3 #4 写到「是否将本稿定位写入技术文档」至今未拍板。**这条等再 6 个月**，回头改 ComfyUI 工作流数据结构 = 噩梦级迁移。

**修法**：从零起步做"向下降梯"。但**不要全做**，按 P2 中拆出最小单元：

1. **Manifest schema（4 类状态翻译）**：半天
2. **单出口工作流节点 MVP**：1 天（先验证单出口）
3. **导入器闸门**：半天

合计 2 天。下版本可启动。

### 4.4 「迭代」与「补强」的边界

| 类别 | 定义 | 适用场景 |
|---|---|---|
| **迭代** | 重设目标 / 重选架构 / 推翻已有方向 | 大方向错了、或赛道已变 |
| **补强** | 在原框架内补空缺 | 方向对、落地执行有缺口 |

**判定**：现在做的是**补强**而非迭代。证据：
- 三层理论互不冲突（§3.4）
- 最近 5 版落地与蓝图空缺呈对称（不是错位）
- 没有竞争品变换赛道（剪映 Hub / TapNow 都没破坏现有卡位）

**因此，本次不引入新理念、不修改 8 条铁律。**
