#意图类型契约设计稿（H1-E1）

> 版本：2026-10-11 · 状态：**设计稿（未实施）** · 适用范围：`vendor/shiguang-canvas`
> 前置阅读：`docs/_reports/2026-10-10-算力路线深度探讨-三档自适应与生态兼容.md`

---

## 0. 一句话定位

**给节点补上「我吃什么、吐什么」的声明，让系统能在不猜语义的前提下校验关系、推导执行序。**

这份契约**不改变磁吸的存在意义**——磁吸仍由几何主导、关系仍由摆放产生。契约只做三件事：

1. **合法性校验**：防止「剧本卡直接连视频卡」这种注定失败的连接被固化
2. **执行序推导**：拓扑排序 + 语义类型 ⇒ 可自动编排流水线
3. **生态对接**：第三方节点能声明接口，不必读宿主源码猜

---

## 1. 现状盘点（先纠正一个误判）

上一轮我曾说「节点只声明外观、没有 wire 契约」——**不准确**。实际已有一套雏形（`stores/node-factory.ts`）：

| 已有 | 位置 | 说明 |
|---|---|---|
| `EdgeType = "prompt" \| "image" \| "video" \| "audio" \| "data"` | `node-factory.ts:16` | 5 种流 |
| `inferEdgeType(sourceKind, targetKind)` | `:548-569` | 按 **source 的 kind** 推断边类型 |
| `buildEdgeOptions()` + `EDGE_STYLE_BY_TYPE` | `:572-600` | 边样式按类型区分（紫虚线=提示词流等） |
| 21 种 `NodeData` 类型 | `:480-501` | 判别联合，字段即真实能力 |

**真正的缺口有三个（比「没有契约」精确得多）**：

| # | 缺口 | 后果 |
|---|---|---|
| **G1** | **只有 single type 边**：一条边一个类型，且**完全由 source 推断** | `image` 连到 `audio` 卡片上，边照样是 `image` —— 无校验 |
| **G2** | **target 侧零声明**：节点不表达「我需要什么输入」 | 无法校验、无法自动补线、无法在磁吸时给出「这两张卡不能吸」的反馈 |
| **G3** | **单进单出假设**：无多端口概念 | 一张导演卡只能整体喂给下游，无法「角色给A、场景给B」 |

## 2. 三层模型

```
┌─ 意图类型 IntentKind ── 语义层：「这是什么」（跨节点可比）
│   例：画面 / 声音 / 文本 / 时间 / 结构 / 空间
├─ 端口契约 PortSpec ── 接口层：「从哪个口进、什么形态」
│   例：{ name:"画面", accepts:["画面"], multi:true, required:false }
└─ 边Edge ──────── 实例层：具体某条连接（现有 EdgeType 降级为它的特例）
```

### 2.1 意图类型清单（从 21 种 NodeData 归纳，6 类）

| 意图 | 承载 | 生产者（节点 kind） | 典型边类型映射 |
|---|---|---|---|
| **结构** Structure | 拆解结果、分镜序列、镜头表 | `directorCard`、`storyboard`、`shotlist` | 新增（现落`data`） |
| **文本** Text | 剧本、提示词、台词 | `script`、`prompt`、`text`、`markdown`、`note`、`config` | `prompt` |
| **画面** Frame | 静帧图像 | `shot`、`image`、`director`、`digitalHuman`、`animation`、`panorama`、`source` | `image` |
| **时长** Motion | 视频片段 | `video` | `video` |
| **声音** Audio | 配音、配乐、音效 | `audio`、`music`、`digitalHuman` | `audio` |
| **控制** Control | 参数、画质档、生成配置 | `generator`、`config` | `data` |

> **纪律**：意图类型**只加不改**。`EdgeType` 的 5 个值保持不变，新意图走新增，绝不重命名既有值——否则历史工程全部失效（schema 迁移成本远大于收益）。

### 2.2 端口契约草案

在 `plugins/types.ts` 的 `CanvasNodeDefinition` 上扩展（**新增字段，老插件不受影响**）：

```ts
export type IntentKind =
  | "structure" | "text" | "frame" | "motion" | "audio" | "control";

/** 端口：声明「这个口吃什么」 */
export type InputPort = {
  name: string;
  accepts: IntentKind[];
  /** 多值口（角色表、参考图集…） */
  multi?: boolean;
  /** 缺省时宿主给兜底（如无参考图走纯文生） */
  required?: boolean;
};

/** 产出声明：一张卡可以吐多种意图（如导演卡吐结构 + 画面） */
export type OutputIntent = {
  intent: IntentKind;
  /** 落到 node.data 的哪个字段（宿主据此搬运数据，不靠插件自找） */
  field: string;
};

export type CanvasNodeDefinition = {
  // …现有字段不动…
  inputs?: InputPort[];
  outputs?: OutputIntent[];
  /** 卡片在小白模式下的一句话用途（喂给 noviceHint 的 override） */
  noviceHint?: string;
};
```

**关键设计**：`outputs[].field` 让宿主知道**数据搬到哪**，第三方插件不必碰 store 内部结构——这是生态能不能起来的关键分界。

## 3. 兼容矩阵（宿主侧单一真相源）

契约由**宿主维护矩阵**，插件只声明自己一列。理由：矩阵一旦分散到各插件，校验就必然出现分歧。

| 消费方 ↓ / 生产者 → | 结构 | 文本 | 画面 | 时长 | 声音 | 控制 |
|---|---|---|---|---|---|---|
| **结构**（导演卡/分镜板） | ✅ | ✅ | ✖ | ✖ | ✖ | ✖ |
| **文本**（剧本/提示词/文本） | ✅ | ✅ | ✖ | ✖ | ✖ | ✅ |
| **画面**（镜头/图/导演台） | ✅ | ✅ | ✅ | ✅ | ✖ | ✅ |
| **时长**（视频） | ✅ | ✅ | ✅ | ✖ | ✖ | ✅ |
| **声音**（配音/音乐） | ✅ | ✅ | ✖ | ✖ | ✅ | ✅ |
| **控制**（生成器/配置） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

规则三条：

1. **控制口通吃**（谁都能被参数配置）；
2. **画面不可直接进声音**（除数字人——它自身产画面+声音，走特例白名单）；
3. **结构只进结构/文本/生成器**——分镜结果不直接变画面，必须过一次镜头卡（这是产品逻辑，不是技术限制）。

## 4. 磁吸如何消费契约（**不破坏原设计**）

**红线：几何仍是关系的唯一来源，契约只做「过滤 + 反馈」，绝不反过来由契约生成位置。**

| 阶段 | 现状 | 加契约后 | 是否改变手感 |
|---|---|---|---|
| 拖拽中 | 五档磁吸按距离 | **不变** | ❌ 无 |
| 咬合判定 | 边距 0 + 重叠 ≥40px | **不变**（仍纯几何） | ❌ 无 |
| 软连接 | 吸附到 strong 生成虚线 | 虚线**按兼容性着色**：兼容=蓝、冲突=琥珀+⚠️ | ⚠️ 仅视觉 |
| 固化 | 点「固化」转正式 edge | 固化前跑一次校验；冲突则**拒绝并说明原因** | ⚠️ 仅把关 |
| 执行 | 用户逐节点点生成 | 校验通过的边 ⇒ 参与拓扑排序，得执行序 | ✅ 新增能力 |

>这样做的价值：**手感零变化**，但从「画完自己看着办」变成「系统知道该怎么跑」。若反过来让契约决定吸附位置，就等于退回 ComfyUI 的显式连线——**那条路不走**。

## 5. 迁移路线（4 阶段，每阶段独立可交付）

| 阶段 | 做什么 | 完成判据 | 风险 |
|---|---|---|---|
| **E1.1 类型层** | 新增 `IntentKind` + 21 种 kind → 意图的映射表（`intentOf(kind)`） | `inferEdgeType` 改为查表实现，行为逐键不变 | 低（纯重构） |
| **E1.2 声明层** | `CanvasNodeDefinition` 加 `inputs/outputs`；**只给内置 21 种节点补声明**，不改渲染 | 全部内置节点有契约，`verify` 脚本校验完整性 | 低 |
| **E1.3 校验层** | 宿主兼容矩阵 + `canConnect(src, dst)`；软连接着色 + 固化把关 | 不兼容边固化被拒且有可读原因 | 中（触及固化路径） |
| **E1.4 编排层** | 拓扑排序 → 执行序；卡片状态灯按序联动 | 一键按序跑通「导演卡→分镜→镜头→成片」 | 中|

**铁律**：
- E1.1/E1.2 **不许改动任何交互行为**，只加声明（回归对比：磁吸相关 vitest 必须逐项通过）；
- 矩阵**只在宿主一处**（`stores/intent-contract.ts`），插件不得自带矩阵；
- 契约缺失 ⇒ **按 `control` 宽容处理**，绝不因缺声明阻断生成（诚实降级，延续项目既有纪律）。

## 8. 待拍板

1. **E1.1 是否即刻启动**？（纯重构，零行为变更，风险最低）
2. **矩阵是否需要「用户可覆写」**？—— 我倾向**不做**：矩阵是产品逻辑，让用户改会立刻失控。
3. **数字人（画面+声音双产出）走特例白名单，还是拆成两张卡**？—— 我倾向**特例**，拆卡会破坏「一张卡演一个人」的直觉。
