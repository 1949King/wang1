> 起因：用户两问 ——

>
> 所有许可证与项目状态均为 **2026-10 检索核实**（许可证会变，勿凭记忆）。

## 一、先明确「执行层」指什么

按 `2026-10-02-画布执行引擎调查.md` 的分层：

- **L1 路由/编排** = 项目自研 7,494 行
- **L2 执行** = 借用（云端 HTTP API / 本地 `diffusers`） ← **本次要调研的就是这一层**
- **L3 推理内核** = 项目零自研

⇒ 所以「找参考」要找的是：**能替换/包裹 `diffusers` 的执行引擎**，以及**编排层可借鉴的架构**。

## 三、★★ 真正该看的其实是「加速库」而非「换引擎」

> **这是本次调研最有价值的发现，且它推翻了本人在 V4.40.20 的一个结论。**

### 3.1 我上一轮说「速度侧四条路封死」——**只在基建层成立，漏了模型层**

V4.40.20 我试的全是**基建层**手段（`decode_chunk_size` / offload / steps / CFG / compile / scheduler），
所以得出「见底」。但**真正的下一刀在模型层：步数蒸馏（step distillation）**。

| 方案 | 步数 | 声称加速 | 关键约束 |
|---|---|---|---|
| **lightx2v / Wan22-Lightning 4 步 LoRA** | 40 → **4** | **20x** | ⚠️ **要求 CFG=1.0**；「4 步偏软，**舒适区 6~8 步**」；与其他 LoRA 叠加相容性差 |
| **FastVideo / FastWan** | → **3 步** | 50x（去噪环节） | 稀疏蒸馏（稀疏注意力 + 分布匹配联合训练） |
| **官方蒸馏**（HunyuanVideo 1.5 的 **8/12 步**、LTX-2 distilled） | → 8 / 12 | — | **质量代价更可控**（原厂自产，非社区） |
| **Spectrum**（xmarre） | 步数不减 | 省 30~35% 计算 | 用 Chebyshev 岭回归拟合隐层特征，**跳过昂贵的 Transformer block**（20 步里实算 13~14 步） |

**业界的实操分档**（值得直接抄成产品策略）：
> **预览档**（4 步蒸馏）用来改提示词、找镜头、找种子、批量出候选；
> **成片档**（20 步基模）用于最终交付；重要镜头做 A/B 对照。
> —— 「创作前期最贵的是等待，交付前最贵的是返工。」

### 3.2 ★★ 它同时解释了我那个「关 CFG 就崩」结论的**适用边界**

| 模型类型 | 关 CFG（=1.0）的后果 |
|---|---|
| **未蒸馏基模**（我测的 SVD-xt） | ❌ **输出报废**（首帧保持 35.1→15.9dB，噪声糊满画面） |
| **步数蒸馏产物**（lightx2v 4 步等） | ✅ **必须关**，蒸馏时就是按 CFG=1.0 训练的 |

⇒ 二者不矛盾：**蒸馏把「无 CFG 也能出好图」这件事训进了权重**。
**后果**：我在 V4.40.20 写的守卫断言「CFG 绝不可关」**范围过宽**，
将来引入蒸馏模型会误伤。**本次已修**：断言改为只约束 `TUNED` 表内**非蒸馏**模型
（新增 `distilled` 标记位旁路），并在注释里显式界定适用范围。

## 五、结论与建议（按优先级）

### 5.1 要不要引入 ComfyUI？—— **不引入**（依据见上一份简报）
GPL-3.0 发行闸门 + 双模型真源 + 本机未安装；且你 2026-08-08 已把「完整 ComfyUI 宿主」列入**明确不做**。

### 5.2 「替代引擎」怎么选？—— **按诉求分层，没有单一替代品**

| 诉求 | 推荐 | 理由 |
|---|---|---|
| 要**节点图执行**且许可宽松 | **InvokeAI（Apache-2.0）** | 唯一「宽松许可 + 自有节点编辑器」；**但需盯 Adobe 收购后的项目活跃度** |
| 要**架构参考**（前端/执行解耦） | **SwarmUI（MIT）** | 「薄前端 + 可换后端」正是本项目画布/执行分层；**只读架构，不引入**（它会带 GPL） |
| 要**低显存视频技术** | **研读 Wan2GP** | 6GB 路径、全量化格式；⚠️ **许可证不允许商用集成** ⇒ **只借鉴思路** |
| 要**加速** | **不换引擎，换/叠模型** | 步数蒸馏（4~8 步）；这是比任何引擎都大的收益 |
| 要**渠道统一架构** | **LiteLLM（MIT）** | 与 ① 同构，MIT 可商用 |

### 5.3 ★ 对本项目的三条具体建议（按收益排序）

1. **【最高收益】引入步数蒸馏档**：给视频生成加「**预览档 4~8 步 / 成片档 20+ 步**」两个档位。
   这比换执行引擎的收益大一个数量级（20x vs 1.x 倍），且**不增加任何依赖**。
   ⚠️ 注意蒸馏模型**要求 CFG=1.0**，须按模型说明设置（守卫已预留 `distilled` 旁路）。
2. **【架构收益】研读 LiteLLM 的 provider 抽象**，对照收敛 `canvas_aigc` 的渠道解析与参数翻译
   （防「每条渠道一段 if」）。
3. **【低显存收益】研读 Wan2GP 的量化/内存管理**（int8/gguf/NVFP4），
   **只借鉴技术**（其许可证禁止商用集成）。

### 5.4 另一个与既有模块的强关联

调研显示：**8GB 卡上只有两条被社区验证的本地视频路径** ——
「Wan 5B 走 ComfyUI 卸载」与「**LTX-Video 走 diffusers（约 10GB）**」。

而项目**既有的 `local_video_infer.py` 已经支持 LTX-Video**（`PIPELINE_CLASS_MAP['ltx']`）。
⇒ 这进一步说明：**既有模块的定位比我那个只支持 SVD 的模块更契合本项目**，
上一份简报里提出的「两套收敛到既有模块」的建议**更应执行**。
