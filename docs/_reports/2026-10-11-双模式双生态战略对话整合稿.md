## 0. 结论速览（30 秒版）

**问**：小白模式简化了连线、端口、参数面板，会不会在功能、能力、生态上产生缺失和劣势？

**答**：功能不缺失（简化的是视图，不是数据），生态是换赛道而非残缺版。但有三个真实风险，均可翻转为结构性优势：

**范式定性（第二场补充）**：ComfyUI 是数据流编程范式（把编程搬进 UI），小白模式是**空间意图范式**（排布即语义、意图胶囊即表达）——两者平级，不是「完整版 vs 阉割版」。详见 §5。

| 风险 | 翻转后的优势 | 关键机制 |
|---|---|---|
| 意图表达天花板 | **动态天花板**：表达力随使用量自适应增长 | 逃生舱即喂养口（切档埋点 + 存为配方） |
| 无法继承 ComfyUI 生态 | **挖矿而非搬家**：收割其成果，拒绝其心智 | 工作流即节点（Workflow-as-Node） |
| 专业模式拼不过 ComfyUI | **双主场**：节点形态承接老用户，round-trip 留住所有人 | 双模式双生态 + 双向电梯 |

**最终架构**：

```
                    ┌──────────── 双向电梯 ────────────┐
                    │  配方展开↑        ↓工作流封装     │
小白模式 ──想法释放──→ 配方（L1）⇄ 工作流节点 ⇐──工作流导入── ComfyUI 用户
（意图编译）              ↑                ↓（黑盒执行）
                    同一份数据 · E1 契约 · ComfyUI/DiffSynth/云端引擎
```

## 1. 第一轮 | 小白模式的简化会不会造成缺失？

### 1.1 功能层面：不会缺失，因为简化的是「视图」不是「数据」

《意图编译范式 2.0》§3 的三条并存铁律就是为防这个问题写死的：

| 铁律 | 保证的事 |
|---|---|
| 同一份数据 | 小白写的字段，专业模式原样可见；`NoviceCard` 只读不写影子数据 |
| 不新增节点类型/字段 | 小白模式是**同一数据的另一种读法**，不是功能子集 |
| 专业模式永远是逃生舱 | 小白卡住的任何地方，一键切档看全图、连全端口 |

端口数据类型、连线、参数面板**没有被删掉，只是对小白隐藏**。能力上限由专业模式 + 底层引擎决定，小白模式不封顶。这和「功能阉割版」是本质区别。

### 1.2 生态层面：不可能、也不应该长成 ComfyUI

《意图编译范式 2.0》§0 写死的判定标准：**任何新功能若要求用户「先理解数据流才能用」，一律不做。**

- ComfyUI 生态 = 程序员写自定义节点（门槛：会 Python）
- 本项目目标生态 = 三级贡献阶梯：**阶 1 配方（会打字）> 阶 2 卡片定义（填表单 / L3 扩充）> 阶 3 节点开发（会 TS）**

> ⚠️ **命名消歧（第二场）**：L1/L2/L3 专指意图胶囊参数层（导演参数 / 进阶 / 专业）；贡献阶梯不再占用 L 前缀，两套术语并存必然误读。

主战场故意放在阶 1。赌的是「会打字的人」比「会写节点的人」多两个数量级——这是差异化卡位，不是劣势。

### 1.3 但三个真实风险必须诚实面对

1. **意图表达天花板**（第二场修正）：排布范式的**自由度并不缺**——卡内（意图胶囊三层）× 卡间（空间排布）是双维度表达，且排布天然适配创作中的软性关系（「这三镜是一个情绪段落」）。真正的缺口是**精确引用表达**（一个产物同时喂多个下游、跨远距离引用），由 E1 G3 多端口 + AI 消歧 + 升档承接。若这类精确表达长期缺口、频繁切档，小白模式才退化成演示模式——§2.1 的动态天花板机制针对的正是它，目标从「补自由度」修正为「补精确引用」。
2. **ComfyUI 现有生态不能直接继承**：ComfyUI 只被当生成引擎用（§2e 检测/拉起），不暴露工作流编辑。社区几千个工作流、自定义节点想变成小白能力，必须经过「工作流 → 卡片/配方」封装层——这层封装目前不存在。
3. **专业模式成熟度决定逃生舱是否真能用**：如果专业模式相对 ComfyUI 太弱，进阶用户学会后直接流失，小白模式的成长路径断裂。

## 2. 第二轮 | 三个风险如何翻转成优势

### 2.1 风险一 → 动态天花板：「逃生舱即喂养口」

**核心观点**：不要试图让意图层一次性表达所有东西——能表达一切的意图层就退化回节点图了（ComfyUI 老路）。意图层只覆盖 80% 高频创作路径（拆故事→出画面→动起来→配音→成片），剩下 20% 长尾**靠使用过程喂出来**：

1. **埋点即需求**：记录每次切档时用户正在做什么（如「想给视频节点加第二张参考图」），自动聚合成意图层待补清单——不用猜用户要什么表达力，数据直接告诉你。
2. **逃生舱回程票**：用户在专业模式拼出来的东西，一键「存为配方」，自动扩展小白模式可表达范围。**专业模式的每次使用都在给小白模式充电**——ComfyUI 没有这个闭环，它的用户产出是「图」，我们的用户产出是「可复用的意图」。
3. **E1 契约 G3 多端口优先做**：它是表达力缺口最集中的地方（角色给 A、场景给 B），也是「一句话带多参考图」体验的前提。

> ComfyUI 的表达力是固定图模型，用户全额买单；我们的表达力随使用量自适应增长。前提是闭环要建。

### 2.2 风险二 → 挖矿而非搬家

继承 ComfyUI 的节点生态 = 把节点图心智模型搬回小白层，恰恰是 §0 写死要避免的。但可以做**单向编译**：挑社区热门工作流（文生视频、换装、首尾帧），封装成 L1 配方——用户看到「古风女主配方」，不是 30 个节点。**ComfyUI 生态从竞争对手变成原料供应链**。算力报告已有伏笔：DiffSynth 连 ComfyUI 生态的 WanVideoWrapper 都被反过来封装使用，「吸收引擎能力、拒绝节点形态」是被验证过的姿势。诚实边界：只覆盖引擎能力范围内的工作流，不承诺全量兼容。

### 2.3 风险三 → 换主场（本轮结论，第三轮被用户修正升级）

本轮原结论：专业模式不要在 ComfyUI 主场（无限节点灵活性）比拼，主打 round-trip、导演台、数字人等创作流程能力。

**修正见第三轮**：用户指出 round-trip 优势与承接 ComfyUI 形态**不冲突，可兼得**——专业模式本身就是节点排布形态，天然能接纳 ComfyUI 用户；「换主场」升级为「双主场」。

## 3. 第三轮 | 关键修正：双模式双生态定位

### 3.1 用户定位（本轮核心输入）

> 小白模式是让小白体验使用、释放想法的通道；专业模式给高阶玩家进阶使用。在我们的生态上，既能继承接纳 ComfyUI 的生态和用户（以及类 ComfyUI 画布生态的用户），又能接纳小白用户和他们灵感、想法的释放。

这个定位成立，且比「换主场」更完整。**竞争力不在两个模式各自，而在双向流通**——ComfyUI 和剪映各占一头，中间地带没人占。

### 3.2 ComfyUI 生态 = 三层，每层继承方式不同

| 层 | ComfyUI 的东西 | 专业模式现状 | 继承机制 |
|---|---|---|---|
| **形态层** | 节点图、端口、连线 | ✅ 已有（21 种节点、边类型、磁吸） | 补齐 E1 契约（尤其 G3 多端口），语义上对齐 ComfyUI 心智 |
| **运行时层** | 几千个 Python 自定义节点 | ❌ 无（画布是 TS，引擎是 DiffSynth） | **不搬节点，搬工作流**：把 ComfyUI 整体当一个引擎节点用 |
| **资产层** | 社区工作流 JSON + 模型组合 | ❌ 无导入 | 工作流导入转换（尽力而为，标注兼容度） |

**关键判断**：运行时层不要试图复刻——把 Python 自定义节点逐个移植成 TS 节点是无底洞。项目已握着一张现成的牌：§2e 已修好 ComfyUI 引擎的检测与拉起（`engine_valid=true` 时自动拉起）。

### 3.3 工作流即节点（Workflow-as-Node）

专业模式新增一种节点：**ComfyUI 工作流节点**。导入社区工作流 JSON 后，在画布上呈现为**一个带输入/输出端口的节点**（端口从工作流入口/出口自动解析），内部黑盒跑在已检测到的 ComfyUI 引擎上。

- 对 ComfyUI 老用户：工作流直接能用，心智无缝
- 对专业模式：获得「无限节点生态」接入能力，但**不污染自己的节点模型**——工作流节点是封装体，不是展开的图
- 对小白模式：工作流节点稳定后可封装成 L1 配方——**ComfyUI 生态成果自动下沉到小白层**

### 3.4 双向电梯飞轮

```
小白用户 ──想法释放──→ 配方（L1）──进阶/被封装──→ 专业模式节点
                                                      ↑
ComfyUI 用户 ──工作流导入──→ 工作流节点 ──封装简化──→ 小白可用配方
```

- **向上电梯**：小白成长后不用换软件，配方可展开成节点图继续深化
- **向下降梯**：ComfyUI 高手的工作流可封装成小白一键可用的配方——ComfyUI 社区做不到（没有小白层），纯小白向产品也做不到（没有专业层承接）

### 3.5 三条纪律（否则双生态互相拖垮）

1. **同一份数据铁律不能破**：工作流节点也是普通节点，遵守 `node.data` 模型和 E1 端口契约，不搞影子数据结构——否则专业模式变成两个互不相通的画布。
2. **ComfyUI 永远是可选引擎，不是硬依赖**：检测不到就回退 DiffSynth/云端，工作流节点置灰并给 `nextAction` 提示。继承生态 ≠ 绑架用户装 ComfyUI。
3. **小白模式不感知工作流内部**：下沉到小白层只暴露配方入口，绝不露出工作流结构——否则小白模式被 ComfyUI 复杂度倒灌，前功尽弃。

## 4. 第四轮 | 工作流导入如何翻译成小白模式（前置设计，不留后账）

**原则**：翻译必须在**导入时**完成，而不是小白模式渲染时临时猜。否则会出现「专业模式有一堆小白模式不敢碰的节点」的分裂状态。

### 4.1 导入即产出「工作流说明书」（Manifest）

导入 ComfyUI 工作流 JSON 时，系统不只创建节点，还强制产出结构化说明书。**没有完整说明书的工作流，只存在于专业模式，不下沉小白模式**——这道闸门是防止复杂度倒灌的关键。

```
ComfyUI 工作流 JSON
      │ 导入
      ▼
┌─ 专业模式：工作流节点（黑盒 + 端口）
└─ 说明书 Manifest ──通过闸门──→ 小白模式：配方卡片
                    └─不通过──→ 仅专业模式可见
```

### 4.2 说明书的三个翻译层

**层一：端口 → 意图（机器自动解析）**，对齐 E1 的 `IntentKind` 六类，复用 `InputPort`/`OutputIntent` 结构——工作流节点和原生节点同一套契约：

| ComfyUI 原语 | 翻译为 | 小白看到的 |
|---|---|---|
| `LoadImage` 入口 | 意图=画面，必填 | 「放一张图进来」 |
| `CLIPTextEncode` 入口 | 意图=文本，必填 | 「写一句你要的画面」 |
| `SaveImage` / `VHS_VideoCombine` 出口 | 意图=画面/时长 | 「你会得到一张图/一段视频」 |
| `KSampler` 的 seed/steps/cfg | 意图=控制，**折叠** | 默认不露，进「进阶」抽屉 |

**层二：语义层 → 人话（人或 AI 补）**：

```
Manifest = {
  自动解析：inputs[], outputs[], 模型依赖[], 硬件档位
  人工确认：一句话说明（「古风人像转水墨动画」）
           每个输入的小白文案 · 配方名 + 封面图
}
```

填写者优先级：① 导入者本人（给「发布配方」激励）② AI 辅助生成候选、人确认 ③ 官方封装。**纪律：语义层没填完，闸门不放行**——宁可不下沉，不出现无名工作流混进小白模式。

**层三：状态与错误 → nextAction（预置映射表）**。最容易被漏、后面最痛的一层，必须导入时就绑定：

| 工作流节点状态 | 专业模式显示 | 小白模式必须显示 |
|---|---|---|
| 运行中 | 节点进度 | 节拍文案（耗时秒数 + 阶段语，复用 P1a 方案） |
| 缺模型/缺自定义节点 | 「missing node: XXX」 | nextAction：「这个配方需要模型 X」+ 下载/换相似配方按钮 |
| 生成失败 | 原始报错 | 3 个出路：换种子 / 改描述 / 换配方 |
| ComfyUI 引擎未检测到 | 引擎状态 | 「需要本地 ComfyUI 才能用这个配方，换云端引擎试试」 |

**这张映射表就是导入流程的验收标准**——导入器创建节点时检查四类状态是否都有翻译，没有就标记说明书不完整，不下沉。

### 4.3 两个防腐机制

1. **漂移检测**：工作流 JSON 存 hash，高阶玩家在专业模式修改后 hash 变化 → 对应配方自动标记「待重新确认」，小白侧显示「这个配方刚被调整过，先试试专业模式」。**宁可降级展示，不可假一致**。
2. **单向封装，双向可见**：配方只引用工作流节点 id + 暴露的输入子集，不复制工作流数据。专业模式的修改自动生效于配方（配合漂移检测），遵守「同一份数据」铁律——配方是视图，不是影子数据。

## 5. 第五轮 | 范式定性 · L3 扩充口 · 双生态单位（第二场讨论并入）

### 5.1 范式定性：空间意图范式与数据流范式平级

ComfyUI 的本质是**数据流编程范式**——带类型的节点图把数据一步步加工成产物，即「把编程搬进 UI」：它开放了模型的使用，没开放工作流的构建权；它的生态是「会建图的人分享图，买家先学会看图」。

小白模式的意图胶囊卡片是**空间意图范式**——排布即语义（挨着 / 聚堆 / 成行 / 居中），卡内有三层意图表达。两者平级：

| 维度 | ComfyUI（数据流） | 小白模式（空间意图） |
|---|---|---|
| 关系表达 | typed 边，精确但需训练 | 空间排布，天然适配创作中的软性关系 |
| 自由度 | 图模型全额买单 | **卡内（意图胶囊）× 卡间（排布）双维度**，创意表达空间不缺 |
| 错误概念 | 类型 / 连接错误，用户排错 | **错误概念被替换**：只有「结果不符合意图」，由 review 灯 + 人话原因 + 三出路承接 |
| 学习义务 | 必须理解数据流 | 归零：永不「排错」，只「改说法 / 重生成 / 微调 L1」 |

### 5.2 L3 完整定位：查证口 + 扩充口 + 永远不是学习口

- **查证口**：看系统干了什么（透明度补「AI 代填」的信任）；「已自动设置」必须可点开看推断依据（如「上游剧本是夜戏，景别推断为近景」）。
- **扩充口**：进阶用户在 L3 编辑 / 扩充字段，「保存为我的卡片」，创造自有意图胶囊卡片——**创意不只在排布里，还能长进卡片本身**。
- **不是学习口**：小白零感知；扩充是权利，不是义务。

### 5.3 双生态单位与创作者阶梯

| 单位 | 创造入口 | 买家成本 | 对应贡献阶 |
|---|---|---|---|
| **排布**（组合方式） | 会讲故事即可 | 零（一眼可读，**排布即工作流**） | 阶 1 配方 |
| **卡片配方**（自定义意图胶囊卡） | L3 扩充 → 保存为我的卡片 | 零（意图胶囊自带解释） | 阶 2 卡片定义 |
| 节点 | 会 TS，走 `extensions` 注册 | 仅专业模式可见 | 阶 3 节点开发 |

创作者阶梯 = **用卡 → 改卡 → 造卡**，每一级可停：小白停在阶 1 完全够用；台阶放在 L3，不逼人升级。ComfyUI 生态只有一种分享单位（图，买家要学），本生态两种且买家零学习——这是「小白有无限创意」的制度化表达。

### 5.4 扩充口三条护栏（防走偏）

1. **诚实映射**：L3 新字段必须映射到管线真实消费的参数；映射不到的标注「仅表达意图，不改变生成」（沿用 2026-09-16 删除三个假设置的判例）。
2. **胶囊语义不破**：新字段必须落在三层之一，带中文标签 + hint——「自带解释」是买家零学习成本的来源。
3. **造卡不改核**：自定义卡片走 `extensions` 注册（注册式扩展），不改 node-factory 核心数据模型、240×200 磁吸不变量、意图胶囊三层结构。

### 5.5 与现行概念一致性核对（防冲突）

| 现行理念 | 双模式双生态的对应 | 冲突判定 |
|---|---|---|
| 北极星（短剧精剪 + AI 导演台画布） | 双生态全部落在 P 轨画布，不动 N 轨剪辑主线 | 无 |
| 四条专注轨（N/P/A/D） | Workflow-as-Node 是 P 轨生态接入机制，不新开轨 | 无 |
| 确认后执行 | Manifest 闸门 + 语义层人工确认 + AI 消歧均是「确认后执行」 | 一致 |
| 诚实生成 | 兼容度标注、「仅表达意图」标注、宁降级不假一致 | 一致 |
| 同一份数据 | 铁律 1 +「配方是视图不是影子数据」 | 一致 |
| 扩展注册表 `extensions` | 阶 2 / 阶 3 贡献的唯一注册通道 | 一致 |
| 冻结区 | ⚠️ 意图胶囊 / L1 / E1 端口改动触及冻结 zone，实施前逐项申请解冻 | 需流程 |

**唯一字面冲突及修正**：铁律 2「不新增节点类型、不新增字段」与阶 2/3 贡献、L3 扩充相抵 → 修正为「小白视图层不私自发明数据，生态新增一律走注册」（见 §6.2）。

### 6.2 铁律汇总（全部对话沉淀）

1. 同一份数据：小白/专业/工作流节点/配方共用 `node.data`，任何一层不写影子数据。
2. 小白**视图层**不私自发明节点类型与字段，只做视图降维；生态新增（阶 2 卡片定义 / 阶 3 节点开发）一律走 `extensions` 注册，不改核心数据模型（第二场修正措辞，解除与贡献阶梯的字面冲突）。
3. 专业模式永远是逃生舱；逃生舱的每次使用都要回流喂养小白模式（埋点 + 存为配方）。
4. ComfyUI 是可选引擎不是硬依赖，检测不到必须回退且诚实提示。
5. 工作流导入 = 节点 + 说明书同时出生；说明书是下沉小白模式的唯一通行证。
6. 状态翻译表是导入验收标准，禁止向小白透传原始错误。
7. 意图类型只加不改，`EdgeType` 既有五值不重命名（历史工程兼容）。
8. 任何新功能若要求小白「先理解数据流才能用」，一律不做。
9. L3 = 查证口 + 扩充口 + 永远不是学习口；扩充字段必须诚实映射真实消费参数（映射不到标注「仅表达意图，不改变生成」），且保住意图胶囊三层结构与 hint。
10. 小白用户永不「排错」：错误概念是「结果不符合意图」，承接 = 人话原因 + 三出路 + 卡片定位，禁止透传内部报错（铁律 6 的哲学化表述，二者并存）。
11. 新能力只在两个维度生长：卡内表达（意图胶囊）与卡间排布（组合方式）；逼用户建立「端口 / 类型 / 参数面板」心智的方案，一律不做（铁律 8 的正向表述）。

### 6.3 待拍板

1. **工作流节点 MVP 范围**：先只支持「整图/整视频」类工作流（单一出口），还是首版就支持多出口？——倾向先单出口，降低 Manifest 解析复杂度。
2. **说明书填写激励**：导入者发布配方给什么激励（署名/首页推荐/未来的配方市场分成位）？——倾向先给署名 + 官方精选位。
3. **默认档位**：首次进入是否默认小白模式（范式 2.0 §8 遗留问题）？双生态定位下倾向「是」，ComfyUI 迁移用户由导入工作流动作自然进入专业模式。
4. **定位落文档**：是否将本稿「双模式双生态 + 双向电梯」写入 `docs/现行技术文档.md` 发展方向章节？
5. **命名消歧**：贡献阶梯改称「阶 1 配方 / 阶 2 卡片定义 / 阶 3 节点开发」，L1/L2/L3 专指意图胶囊参数层——是否确认？
6. **L3 扩充出口形态**：「保存为我的卡片」的配方 schema（含诚实映射声明）是否与配方包格式同批定稿？
7. **铁律 2 措辞修正**（§6.2 第 2 条）是否确认？

**第二场对既有 4 项的立场**：① 单出口——同意；② 署名 + 官方精选位——同意；③ 默认小白——同意（导入工作流动作自然进入专业模式，与双生态定位自洽）；④ 落文档——同意，但守单一事实源纪律：仅在 `现行技术文档.md`「发展方向」节写一段浓缩定位，执行细节留本报告与范式稿，不复制多份。
