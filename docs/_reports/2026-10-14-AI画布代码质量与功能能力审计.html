1.1 缺陷 1：新建画布找不到捏脸卡片/节点 ✅

根因：FaceCard 此前只作为 CanvasShell 的模态弹窗存在，不在 NodeRegistry / NodePalette / node-factory 任何一环 ⇒ 新建空画布根本没有入口。不是「入口藏得深」，是「入口不存在」。

层落地
数据契约node-factory.ts 新增 CharacterData（kind:"character"）+ NodeData 联合成员 + makeNode base/style（260×240）+ BUILTIN_NODE_KINDS
注册registerBuiltinNodes.ts 登记 CharacterNode + 元数据（🧑‍🎨）
视图mediaExtraNodes.tsx 新 CharacterNode：角色库下拉 + 头像 + 🎨 捏脸 按钮
入口NodePalette.tsx 加「角色」项（关键词含「捏脸/脸/角色库」）· CanvasContextMenu.tsx 加右键项 · NoviceCard.tsx 加捏脸菜单项
宿主节点只派发 sg-open-face-card 事件，CanvasShell 承载唯一 FaceCard host
为什么不让节点自己渲染 FaceCard：FaceCard 是 position:fixed 模态，而 React Flow viewport 带 transform。把fixed 模态塞进 viewport 内⇒ 弹窗跟着画布平移缩放、层级被节点遮挡。这条是硬约束，不是偷懒。

1.2 缺陷 2：桌宠 ⇄ Agent 在画布 1/画布 2 都失效 ✅

根因两条，都是设计缺陷不是笔误：

#根因后果
①CanvasOverlays.openAgent 靠 document.querySelector(".libtv-agent-btn") 猜按钮，而 CanvasShell 顶栏「🚀 生成」与「💬 Agent」共用同一个 class永远命中第一个「生成」⇒ 点桌宠打开了错误面板；且桌宠只会「打开」没有「回桌宠」入口
②Agent 开合态存全局单键 shiguang-canvas:agent-dock:open某画布开过 Agent ⇒ 之后每个画布都默认开 → 桌宠全被隐藏，看起来「点不了」

修法：改类型化事件通道，彻底删掉 DOM 嗅探与 MutationObserver——

// 桌宠只发意图，不自己改状态（真相源在 CanvasShell）
window.dispatchEvent(new CustomEvent("sg-toggle-agent"));
// CanvasShell 统一翻转 agentPanelOpen，再回播给桌宠
window.dispatchEvent(new CustomEvent("sg-agent-state", { detail:{open} }));
// 桌宠挂载时主动取一次首帧态（解决"刷新后 Agent 已开着"）
window.dispatchEvent(new CustomEvent("sg-agent-state-request"));
// 状态按画布隔离记忆
`shiguang-canvas:agent-dock:open:${canvasId || "memory"}`

1.3 缺陷 3（重点）：渲染崩溃 React #185 ✅

#185 = Maximum update depth exceeded（无限重渲染）。这是本轮重点对象，结论是：上一轮（V4.43.21）修的只是这一类问题的一部分。

为什么上一轮没修好

上一轮的判定是「zustand selector 每次返回新对象/新数组 ⇒ useSyncExternalStore 判定快照恒变」，并上了静态守卫 _verify/check_canvas_selectors.py。该守卫现在实测 0 违规——说明这一类确实清干净了，但用户仍崩⇒ 存在第二类根因，静态守卫覆盖不到。

本轮定位的完整闭环（逐行核实）

CanvasShell.tsx:585  bondedSides = useMemo(() => bondedSidesMap(nodes), [magneticActive, nodes])
CanvasShell.tsx:589  useEffect(() => setBondedSides(bondedSides), [bondedSides])
      │
      ↓ magnetic/bonds.ts:216  bondedSidesMap() 每轮 const map = {} 新建对象
      ↓   ⇒ bondedSides 引用必变 ⇒ effect 必跑（这是设计意图，不算 bug）
      ↓
store.ts:662  setBondedSides: (map) => set({ bondedSides: map })     ← ❶ 无幂等守卫
      │        裸 set，无条件通知全 store，哪怕内容一模一样
      ↓ 订阅 bondedSides 的 NoviceCard(:175) 全部重渲染
      ↓ xyflow 重渲染后抛 dimensions change
store.ts:665  onNodesChange: 无条件 applyNodeChanges(...)            ← ❷ 放大器
      │        即使 changes 为空也产出全新 nodes 数组
      ↓
      └──── nodes 变 ⇒ 回到 useMemo第一步 ⇒ 成环 ⇒ #185

修法：幂等守卫范式（与项目既有守卫同构）

位置守卫内容纯函数
store.ts setBondedSideskey 数 + 每项 join(',') 相同 ⇒ 整体不 set，bondedSides 引用不变bondedSidesEqual
store.ts updateNodeDatapatch 逐键 Object.is 相同 ⇒ 整个 set 不执行（nodes 引用与 dirtyVersion 均不变）nodeDataPatchIsNoop
windowManager.ts syncOpen已是最小化态 ⇒ 返回原 state 不 set（当前被 open 守卫挡住、非当次根因，防将来成环）内联
CanvasOverlays.tsx 预览 tick()step >= order.length 时只收尾，不再 dispatch sg-preview-focus（修相机抖动）内联
为什么 updateNodeData 的守卫安全：已逐个核查全部调用方（upstreamRefs.ts / useEditorCanvasLink / AgentPanel / GeneratePanel / NoviceCard / CanvasShell.pickNodeByType 等），无一依赖「空转也+1 dirtyVersion」。唯一语义变化是「重复写入同值不再触发自动保存」——这正是期望行为（无实质变更不该落盘）。
nodeDataPatchIsNoop 的两条语义红线（必须与被它替代的 {...n.data, ...patch} 逐字等价，否则就是引入行为差异）：
① 判等用 Object.is 而非 ===（NaN 会被 === 误判成「有变化」）；
② 「值为 undefined」≠「键缺失」：{...data, k: undefined} 会显式新增自有键 k，结果与「原本没有 k」不是同一个对象。所以用 hasOwnProperty 而非 in（展开只复制自有可枚举键，用 in 会把「实际会新增键」误判成空转 = 丢更新）。
整体取保守侧：误判「有变化」只是多写一次（无害），误判「空转」会丢更新（是 bug）。

4.1 结论先行：画布已是行业公认形态，且2026 在收敛

「节点 / 无限画布」不是我们的差异化，是 2026 的行业标准。多个独立来源指出画布正从「界面功能」升级为「产品品类」——ComfyUI 事实上定义了节点画布，Krea / Flora / Wireflow / Figma Weave / Freepik Spaces / Runway / Invoke 全部跟进。

可立刻抄的一条（成本低、收益大）：「每批 8 条 + 每批之间查一致性悬崖 + 末尾统一调色」。我们的抽卡闭环现在有 draw_book 账本和 gen_critic 代理评分器，但没有「批次」概念。加一层批次 + 批间一致性检查，比继续打磨单张评分器更接近生产现场。另可抄：图像嵌入相似度自动过滤角色漂移（余弦相似度低于阈值标记人工复审，行业数据称可减少 60%+ 人工复审量）——来源 tahou.com 引述实操。

可直接抄的三条（按成本排序）：
① 确定性布局引擎（Factory）——我们的导演卡拆解已经产出「按阶段列」的天然结构，但落位靠算法随手放。给它一个「阶段列」概念，Agent 建的项目就能读。
② 执行范围三档（单节点 / 依赖流 / 全项目）——我们的 canvasRun.ts 已有「运行到此处」，补上「单节点」和「全项目」就是完整三档。
③ 幂等签名（Factory）——这条对我们是硬需求：我们已有 stage3dApplySeq / stage3dCastSeq 这类 seq 消费范式，本质就是幂等签名的雏形，但生成类动作（生图/生视频/3D 渲染）还没有这层保护，重复批准可能重复扣额度。

Invideo 这套就是我们「资产母版层」的标准答案，而且结构简单得惊人：四张表（角色表 / 地点表 / 视觉调性表 / 规则表）。我们的角色库已经有 face_params / avatar_url，缺的只是把场景、风格、规则补齐成同构的四张表，并加一道「生成前比对、不match 就重生成」的闸门。这是我认为下一刀最该做的。

4.5 审美治理层：竞品多数也没做，但有替代路径

诚实结论：没有找到把「审美统一 / 成片 QC」做成独立横跨层的成熟产品。主流做法仍是散在各环节（invideo 的 storyboard 连续性检查、creatortribune 的末尾 harmonization、tahou 的光流一致性检测）。

可抄的替代路径做法成本
分镜阶段连续性通读invideo 的做法：角色漂移时改源角色卡而不是重抽该panel，改完存回上下文，后续 panel 自动继承修复低我们的角色卡是结构化数据，比它们更好做
光流一致性检测首尾帧光流场剧烈不连续跳变 = 模型中途放弃；OpenCV 逐帧光流方差设阈值可滤掉大部分崩坏片段中需引入 OpenCV
三层管道论domer.io 的框架：生成 / 分析 / 编排三层才可重复；大多数人热情搭第一层、忽视第二层、用电子表格糊第三层低是判断框架不是功能

5. 未来功能路线图

5.1 主线锚定（沿用既定补齐顺序）

既定顺序 ④抽卡 → ①编剧 → ②导演·节奏 → ③美术·母版。审计后我认为这条顺序需要一处修正：③资产母版层应该提前到 ①编剧 之前。

顺序修正理由（这是本报告唯一的路线建议）：编剧生产端产出的剧本会定义角色与场景，母版层是它的下游但强前置——剧本里的角色描述如果当场不落成母版卡，等抽卡做完再回头补，角色已经漂了。
更硬的证据：竞品 LTX Studio 的 Elements 和 Invideo 的 Context Engine 都是在剧本阶段就建立角色/地点元素，不是等到生成阶段。⇒ 新顺序：④抽卡 → ③母版 → ①编剧 → ②导演·节奏。

5.2 P0（建议下一刀）：资产母版层 = 四张表

直接抄 Invideo 的结构（cast / locations / look / rules），我们已有角色库只缺后三张：

表关键字段我们现状
cast 角色表id / 名称 / face_params / avatar_url / 身高体型 / 声音 / 固定身份描述块（逐字不改，抄 pixmind 铁律）已有 80%角色库 + FaceCard 已通
locations 场景表id / 名称 / 参考图集（3–5 张，抄「锚定参考图集」）/ 光照方向 / 色温 / 空间尺度缺
look 视觉调性表调色板 / 镜头语言 / 颗粒感 / 光照方向约定（风格圣经要短到人两分钟能读完，长文档会被忽略）有零散aestheticPresets / lightingPresets 但未成表
rules 规则表禁生成清单（字幕/商标/法务声明标为「图形」不走视频模型）/ 负面清单 / 命名规范缺

配套闸门（Invideo 的核心机制）：生成前拿候选与四张表比对，不 match 就标记重生成。先做最便宜的一版：图像嵌入余弦相似度对cast 参考图集，低于阈值标「需复审」——行业数据称可减 60%+ 人工复审量。

5.3 P1（三条，按性价比）

优先动作来源 / 理由
P1-1接线 14 个孤儿端点，优先 /host/batch-to-timeline（批量入时间线，直接喂抽卡闭环）、/host/compliance-check（漫剧合规刚需）、/host/diarize-speakers（多人配音）后端已完工，边际成本最低
P1-2生成动作幂等签名：生图/生视频/3D 渲染批准前带签名，防重复扣额度抄 Factory Agent；我们已有 seq 消费范式可扩展
P1-3抽卡加「批次」概念：每批 8 条 + 批间一致性悬崖检查 + 末尾统一调色抄 creatortribune 4 阶段实战流程；比继续打磨单张评分器更贴生产现场

5.4 P2（结构性，等母版层落地后再做）

  • Agent 画布写操作：把 canvasRun.ts 的执行范围补成三档（单节点 / 依赖流 / 全项目），再让 Agent 能「加过渡镜」「把这批的 style lock 统一」这类批量决策（抄 BLOCKLORE「翻译成新节点并入流水线」）。
  • 确定性阶段列布局：新建画布时节点按「素材→种子→分镜→参考→视频段→音频→合成→审→成片」自动分列，Agent 建的项目从左往右读就是一条生产线（抄 Factory）。
  • Agent 自我清理：审计画布、删掉不在活跃流水线的节点、重连剩余并汇报（抄 BLOCKLORE）——这条同时治我们自己的「测试节点堆积」问题。
  • 审美治理层：光流一致性检测（成本中，需 OpenCV）+ 分镜阶段连续性通读（成本低）。建议先不做——等母版层四张表到位后再建管辖层，否则是给空气加制度。
  • 对外 Agent OpenAPI：记忆里 C 线「做不做待拍板」，本轮不展开。

5.6 需要拍板的两件事
