1. **每个卡片拖动比较卡顿、缓慢、不流畅**

## 一、卡顿根因（症状 1）

### 🔴 根因 A：拖拽开始时全图 `JSON` 深拷贝（最重）

**证据链**：

```
CanvasShell.tsx:1498  onNodeDragStart={(e, n) => { magNodeDragStart(e, n); beginGraphEdit(); }}
        ↓
store.ts:1439         beginGraphEdit: () => { pushGraphHistory(get); }
        ↓
history-store.ts:46   export function pushGraphHistory(get) {
history-store.ts:47     const snap = cloneGraph(get().nodes, get().edges, get().selectedId);
        ↓
history-store.ts:33   export function cloneGraph(nodes, edges, selectedId) {
history-store.ts:39     nodes: JSON.parse(JSON.stringify(nodes)) as Node[],   ← 全图深拷贝
history-store.ts:40     edges: JSON.parse(JSON.stringify(edges)) as Edge[],
```

**为什么是它**：每次开始拖任意一张卡，都会对**全画布所有节点 + 所有连线**做一次 `JSON.parse(JSON.stringify(...))`。这个操作是同步阻塞的，跑在主线程上，而且：

- 节点 data 里带 `imageUrl` / `videoUrl` / `script` / `prompt` 等长字符串，序列化成本随内容线性增长；
- 卡片越多、文本越长，这一下越久；
- 它发生在 **拖拽按下瞬间**，用户的第一感受就是「按下去卡一下才跟手」。

**量化参考**：一张带 2KB 文本的卡片，序列化约 2KB；50 张卡 + 100 条边 → 约 100KB+ 的 JSON 往返，主线程上通常 5~30ms 的量级，恰好在「一帧 16.7ms」的预算里制造掉帧。

### 🔴 根因 B：每个拖拽帧触发「全店重渲染 + 咬合全量重算」

**证据链**：

```
ReactFlow 拖拽每帧 → onNodesChange(changes)
        ↓
store.ts:627  onNodesChange: (changes) => set((state) => ({
store.ts:629      nodes: applyNodeChanges(changes, state.nodes),   ← 新数组
store.ts:630      dirtyVersion: state.dirtyVersion + 1,
                }))
        ↓
CanvasShell.tsx:449  const nodes = useCanvasStore((s) => s.nodes);   ← 订阅了整个数组
        ↓
CanvasShell.tsx:474  const bonds = useMemo(() => computeBonds(nodes), [magneticActive, nodes]);      ← 每帧重算
CanvasShell.tsx:481  const bondedSides = useMemo(() => bondedSidesMap(nodes), [magneticActive, nodes]); ← 每帧重算
        ↓
CanvasShell.tsx:485  useEffect(() => { useCanvasStore.getState().setBondedSides(bondedSides); }, [bondedSides]);
                     ← 每帧再写一次 store，触发第二轮渲染
        ↓
useMagneticDrag.ts:74  const spatialIndex = useMemo(() => new SpatialIndex(nodes), [nodes]);
                     ← 每帧从零重建空间索引（遍历全部节点重新分桶）
```

**四个叠加成本**：

| 环节 | 每帧成本 |
|------|---------|
| `CanvasShell` 因 `nodes` 变化重渲染 | 整棵子树 diff |
| `computeBonds(nodes)` | 建索引 + 全节点邻域扫描 |
| `bondedSidesMap(nodes)` | 再扫一遍全表 |
| `new SpatialIndex(nodes)` | 全节点重新分桶 |
| `setBondedSides` 写回 store | 第三轮渲染 |

**这正是 React Flow 官方文档点名的最常见性能陷阱**（见第三节对照）。

### 🟡 根因 C：`writeNodePos` 也在拖拽中改 store（V4.28.2 引入的路径）

```ts
// useMagneticDrag.ts:94
const writeNodePos = useCallback((id, pos) => {
  const state = useCanvasStore.getState();
  let changed = false;
  const next = state.nodes.map((n) => {           // ← 每帧重建整个数组
    if (n.id !== id) return n;
    if (n.position.x === pos.x && n.position.y === pos.y) return n;
    changed = true;
    return { ...n, position: { x: pos.x, y: pos.y } };
  });
  if (changed) useCanvasStore.setState({ nodes: next });   // ← 又触发上面整条链
}, []);
```

**关键**：V4.28.2「靠近即吸附」让 `onNodeDrag` 里**每帧都调用 `writeNodePos`**（`useMagneticDrag.ts:245`）。在吸附范围内，每帧都重建 nodes 数组 → 又触发根因 B 的全套重算。**这与根因 B 形成正反馈**：越靠近目标，越卡。

比 `position` 变化的判断已经做了（`x === pos.x`），这部分是好的；问题是**数组本身每帧都是新的**，导致所有 `[nodes]` 依赖的 `useMemo` 全部失效。

### 🟡 根因 D：`.nv-card` 上有 `transition`，会与拖拽的 `transform` 打架

```css
/* novice-cards.css:19 */
.nv-card { transition: border-color 0.15s, box-shadow 0.15s; }
```

这条本身只过渡 `border-color` / `box-shadow`，**不直接**过渡 `transform`——但选中态切换（`.nv-card.on` 改 border + box-shadow）会在拖拽期间叠加一次 paint，配合根因 B 的重渲染，会放大掉帧感知。

> 备注：React Flow 卡片位移走的是 `transform: translate()`，本身不触发 layout。如果后续为了「更顺滑」给它加 `transition: transform`，**会导致每帧插值追赶，反而更卡**——不要加。

## 二、吸附手感根因（症状 2）

### 🔴 根因 E：吸附落点**强制边对齐**，纵坐标被「瞬移」

这是「上下吸附感觉有问题」的**决定性根因**。

**代码**：

```ts
// MagneticEngine.ts:203  getSnapPosition
const gap = -2;
switch (direction) {
  case "left":   return { x: targetPos.x - dragSize.width - gap, y: targetPos.y };   // ← y 硬取目标 y
  case "right":  return { x: targetPos.x + targetSize.width + gap, y: targetPos.y }; // ← y 硬取目标 y
  case "top":    return { x: targetPos.x, y: targetPos.y - dragSize.height - gap };
  case "bottom": return { x: targetPos.x, y: targetPos.y + targetSize.height + gap };
}
```

**几何模拟结果**（目标卡 `T=(1000,1000)` 240×200，拖拽卡在 T 右侧水平间隙 10px）：

| 用户垂直错开 | 判定方向 | 落点 | **垂直位移** |
|-------------|---------|------|------------|
| 0 px | left | (1238, 1000) | ±0 |
| 30 px | left | (1238, 1000) | **−30** |
| 60 px | left | (1238, 1000) | **−60** |
| 100 px | left | (1238, 1000) | **−100** |
| 140 px | left | (1238, 1000) | **−140** |
| 180 px | left | (1238, 1000) | **−180** |
| 220 px | left | (1238, 1000) | **−220** |

**结论**：只要判定为「水平吸附」，落点 `y` **一律强制等于目标 `y`**。用户稍微竖着错开一点拖过去，卡片会**自己跳上去对齐**，最大位移可达 ±200px（整整一个卡高）。

**这就是「上下吸附不对」的真实体感**——不是方向算错，是**纵坐标被强行拽走**。

> 注：方向判定本身是**正确的**。我用模拟验证了左/右/上/下四种工况，最终落点与目标的 `edge-gap` 均为 `0.0`（`gapx=2` 或 `gapy=2` 的重叠，符合 `gap=-2` 融合设计），轴对齐方向也对。**所以不要改 `oppositeDirection` / `getDirection`**，问题在落点的「对齐自由度」。

### 🟡 根因 F：对角吸附时，`hypot` 压缩了可用吸附窗口

**代码**：

```ts
// MagneticEngine.ts:69
return { gap: Math.hypot(gapX, gapY), gapX, gapY, overlapX, overlapY };
// 判定：if (gap > config.weakDistance) continue;   ← weakDistance = 120
```

**模拟**（目标在右下，拖拽卡水平靠近）：

| 水平间隙 | 垂直错位 | `hypot` | 是否吸附 |
|---------|---------|---------|---------|
| 110 px | 0 | 110.0 | ✅ |
| 110 px | 100 | 110.0 | ✅ |
| 125 px | 0 | 125.0 | ❌ |
| 120 px | 0 | 120.0 | ❌（边界） |

**问题**：`hypot(gapX, gapY)` 是**斜边距离**。当纵向错开 100px 时，`hypot` 把纵向差值算进了「距离」，导致：

- 用户想把卡片**并排贴**（只关心水平间隙），但纵向稍微错位，`hypot` 就把总距离抬高；
- 纵向错位 100px 时，水平间隙必须 < ~66px 才够 120 阈值。

**体感**：**「并排贴的时候，稍微上下不齐就吸不上」**。这就是用户说的「左右吸附有时候不灵」。

### 🟡 根因 G：`medium` 档是死代码

```ts
// MagneticEngine.ts:119-122
if (gap < config.instantDistance) level = "instant";        // <10
else if (gap < config.strongDistance) level = "strong";     // <60
else if (gap < config.mediumDistance) level = "medium";     // <50  ← 永远不可达
else level = "weak";
```

`strongDistance(60)` 排在 `mediumDistance(50)` **之前**，所以 `gap ∈ [50,60)` 时先命中 `strong`，`medium` 分支**永不执行**。

**阈值实测**：`gap=5→instant / 15→strong / 45→strong / 55→strong / 70→weak / 115→weak`。

**当前影响**：V4.28.2「靠近即吸附」下，等级只用于目标优先级 + UI 反馈，**不影响吸附力度**，所以不构成功能 bug。但它是**维护隐患**：五档里有一档是死的，后续谁按「medium 档」调参都会踩空。

### 3.2 tldraw 的 Snapping System（最值得借鉴的算法对照）

来源：https://deepwiki.com/tldraw/tldraw-v1/11.4-snapping-system

tldraw 解决的是**同一个问题**（画布上形状靠近时自动对齐 + 显示对齐辅助线），它的做法与你有三处关键差异：

| 维度 | tldraw | 你的实现 | 借鉴建议 |
|------|--------|---------|---------|
| **吸附点** | 每轴定义 **6 个吸附点**（`minX/midX/maxX/minY/midY/maxY`），两形状间 **9 组合/轴**，共 18 次测量 | 只有「边对边」一种关系和四向 | **加「中线对齐」** 会显著提升「对齐到位」的手感；并且能自然支持「纵向不强行对齐」 |
| **容差判据** | **分轴独立**判断：`gapX` 在阈值内就吸 X，`gapY` 在阈值内就吸 Y，**互不干扰** | `hypot(gapX, gapY)` **合并两轴**成一个距离 | ⭐ **这是根因 F 的正解**：改成分轴独立判定，并排贴时纵向错位不再吃掉横向窗口 |
| **对齐自由度** | 只调整**被吸附的那个轴**，另一轴保持用户拖到哪就是哪 | 吸附时**另一个轴也强制对齐**（`getSnapPosition` 里 `y = targetPos.y`） | ⭐ **这是根因 E 的正解**：吸 X 就只动 X，别碰 Y |
| **容差数值** | 2px（辅助线匹配容差） | `weakDistance=120` / `bondTolerance=2` | 你的 `bondTolerance=2` 与之一致 ✅ |

**tldraw 的核心源码位置**：`packages/core/src/utils/utils.ts` 的 `Utils.getSnapPoints()`（约 1085–1262 行）。算法三步：

1. 对每个其他形状，算所有吸附点组合的 gap（每轴 9 个）
2. 每轴取「阈值内的最小 gap」，**保留符号**决定吸附方向
3. 把「与该最小 gap 相差 < 2px」的吸附点**全部标记为 snapped**（支持多点同时对齐）

**对齐辅助线的画法**：吸附后用偏移修正后的 bounds 生成线，X 轴在 `minX/midX/maxX` 处画**竖线**，Y 轴在 `minY/midY/maxY` 处画**横线**，线的长度**覆盖移动形状与目标形状两端**。

### 3.3 dnd-kit 的 Modifier 机制（借鉴「位移变换」的架构）

来源：https://dndkit.com/

dnd-kit 把「吸附」实现为 **Modifier**——一个纯函数，输入 `transform`，输出修正后的 `transform`：

```ts
// @dnd-kit/modifiers 的 createSnapModifier 核心（极简）
export function createSnapModifier(gridSize: number): Modifier {
  return ({ transform }) => ({
    ...transform,
    x: Math.ceil(transform.x / gridSize) * gridSize,
    y: Math.ceil(transform.y / gridSize) * gridSize,
  });
}
```

**借鉴点**：`snapCenterToCursor` 这个 modifier 保证「拖拽元素中心跟随光标」。这正是你**根因 B/C 的解法方向**——**不要每帧写 store**，而是在**渲染层**做位移修正（React Flow 提供 `node.origin`、或用自己的 wrapper 层），store 只在**松手时**提交一次。

### 3.4 Windows 11 / PowerToys FancyZones 的「预览矩形」

来源：GNOME Tiling Shell（复刻 Win11 Snap Assistant）、SmartGrid

| 行为 | Win11 / Tiling Shell / SmartGrid | 你的实现 |
|------|--------------------------------|---------|
| 拖拽中显示**落点预览** | ✅ 半透明蓝色预览矩形，实时显示「松手后会去哪」 | `MagneticLines` 只画**贴合缝线**（目标卡被贴边），不画「卡片将占的矩形」 |
| 吸附触发 | 预览高亮 + 松手落位 | 自动吸附（V4.28.2 用户裁定） |
| 释放感 | 「移开预览区 = 不吸附」 | 进入 120px 就吸住，**没有「退出吸附」的手感** |

**借鉴点**：Win11 系列的灵魂是**预览矩形先到位，松手才落座**。你现在的实现是「进入范围立刻瞬移」——这在 V4.28.2 是用户明确要的（「只要靠近就自动吸附」），但**配合根因 E 的强制对齐**，就变成「卡片自己跳走」。**保留「靠近即吸附」不变，只修「落点自由度」，手感就能对齐 Win11。**
