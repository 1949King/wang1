## 四、处置建议

### 不要做的

❌ **不要跑 `git checkout .` 或 `git restore .`** —— 会把 7451 个文件（含 6963 个 OpenShot 源码）全部还原回工作区，污染项目、且它们大多已明确下线。

### 建议做的（按优先级）

**P0 — 把"归档"这个事实提交固化**

当前 `docs/_archive/` 下 43 个文件是 untracked、`docs/knowledge/*` 是 `D`。这状态会让每次 `git status` 都刷屏 7000+ 行，也让后续任何 `git add .` 有风险。

```bash
# 1) 先确认 .gitignore 已忽略不该进的目录
#    已有：thirdparty/ (176) / vendor/infinite-canvas/ (115) / vendor/AI-Canvas-tauri/ (118)
#    建议追加：
echo "openshot-qt/" >> .gitignore
echo "libopenshot/" >> .gitignore

# 2) 提交归档搬迁 + 功能下线（分两个提交更清晰）
git add docs/_archive docs/knowledge docs docs/.gitignore .gitignore
git commit -m "chore(docs): 知识库归档至 docs/_archive，索引重建"

git add -u    # 记录 app/ 与根目录的下线删除
git commit -m "chore: 清理已下线模块（账号运营/短剧筛选/OpenShot 桥接/旧剪辑器第二套）"
```

**P1 — 确认 `catalog.json` 去留**

若它是知识库索引且已作废，随归档一起 commit 即可；若新版仍在引用，需找回。

**P2 — 建立 git 卫生纪律**

当前仓库只有 5 个有效提交、间隔最长 1 个月，工作区长期与 HEAD 脱节 → 每次都会积累成"7000 行变更"的噪声。
建议：每次大范围重构/归档后**立即提交**，哪怕提交信息只是 `chore: archive docs`。

## 五、本次排查方法（可复用）

| 步骤 | 方法 | 作用 |
|---|---|---|
| 1 | 按顶层目录聚合 `D` 数量 | 迅速定位 98% 在 openshot，缩小战场 |
| 2 | `git status --untracked-files=all` 收集 `??` | **关键**：把 `D` 与 `??` 按 basename 配对 → 识别"搬迁" |
| 3 | 逐文件 `os.path.exists` 核实磁盘 | 区分"真删"与"改状态" |
| 4 | 关键词全盘搜索替代品 | 判定功能是否真丢失（而非搬家） |
| 5 | `git ls-tree <commit> -- <path>` 逐提交数文件 | 建立时间轴，定位何时消失 |
| 6 | 交叉比对记忆/文档记载 | 用「已下线」记录佐证"故意清理" |

**核心心法**：`git status` 里大量 `D` 看起来吓人，但**只要能把 `D` 和 `??` 配成对，就能立刻区分「搬迁」与「删除」**。真正需要警惕的只有"`D` 了但找不着新家、也没有替代品"的那一小撮。
