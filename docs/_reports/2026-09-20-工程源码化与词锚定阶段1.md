## 一、先回答：我们项目有「视频代码化」能力吗？

**有，但只到一半 —— 而且最该承担这件事的文件是死代码。**

### 1.1 已经具备的（工程即数据）

工程文件本身就是一份 JSON（`editor_module.py:4532-4548`）：

```python
project_data = {
    "version": "1.2",
    "clips": self._clips_snapshot(),   # ← 整条时间轴
    "timeline_zoom": ..., "subtitles": ..., "subtitle_styles": ...,
    "stickers": ..., "master_volume": ..., "sequence": ...,
    "export_time": ...,
}
json.dump(project_data, f, ensure_ascii=False, indent=2)
```

| 能力 | 状态 | 证据 |
|---|---|---|
| 工程 = 结构化数据 | ✅ | 上表；落盘扩展名 `.timeline`（`_autosave_project`） |
| 人可读 | ⚠️ 半 | `indent=2` / `ensure_ascii=False`，但字段是英文缩写、时间是裸浮点 |
| 可版本演进 | ✅ | 有 `version` 字段 |
| 可 diff / 回滚 | ✅ | `project_snapshot`（工程级快照，回归项 PROJSNAP 覆盖 20 项） |
| 可重跑 | ✅ | 渲染链读的就是它 |
| **锚在词上** | ❌ | 全库 `anchor` 命中全是几何/视觉概念（旋转枢轴、角色视觉符号），无文本锚定 |
| **Agent 主编辑面** | ❌ | Agent 走 `editor.*` capability 调 API 改写 `_clips`，不直接读写 `.timeline` |

### 1.2 ⚠️ 核查中的关键发现：`timeline_dsl.py` 是死代码

`app/core/timeline_dsl.py` 自称「**时间轴 JSON-DSL 数据契约**」，
含 `Timeline` / `Track` / `Clip` / `Keyframe` / `Transition` / `Effect` / `Marker`
+ 序列化 + `validate_timeline()`（`:715`）+ `convert_from_v1()`（`:757`）+ JSON Schema。

**它本该就是「视频的语言」。但实测：**

| 检查 | 结果 |
|---|---|
| 全库 `from ... import timeline_dsl` | **只有 1 处**：`editing_capabilities.py:57` |
| 该处是否真的使用 | **否** —— 只 import，文件内零引用（`grep "Timeline\|validate_timeline\|convert_from_v1"` 在该文件仅命中 import 行与文档字符串） |
| `editing_capabilities.py` 自身被谁引用 | 生产代码**零引用**（只有 `tests/unit/test_video_editing_e2e.py:520`） |

⇒ **两者叠加 = `timeline_dsl.py` 从未接入过任何真实路径。**

**这不是要删它，而是说明**：项目想要「视频即代码」的意图早就有了（连版本迁移函数都写好了），
**只是缺一个把它接上真实数据的动作**。本轮的工程源码层就是补这一环。

## 二、本轮升级一：工程源码化

### 2.1 新增 `app/core/timeline_source.py`

把同一份 `_clips` **投影**成另一种形态 —— 不是替换 `.timeline`（它仍是真相源），
而是补一条**给人看、给人改、能进版本管理**的视图。

同一份数据，两种形态：

```jsonc
// .timeline（JSON，机器友好）                // 工程源码（人友好）
{"id":"clip_b","start_time":10.0,           [2] 00:10.000 → 00:25.400  (15.4s)  轨道 0 · video
 "duration":15.4,"in_point":2.0,              标识  clip_b
 "effects":{"brightness":1.1}}                名称  冲突
                                              素材  E:/素材/02.mp4
                                              取用入点  2
                                              取用出点  17.4
                                              特效  {"brightness": 1.1, "contrast": 1.05}
```

### 2.2 三条硬约束（都做了测试）

| 约束 | 做法 | 验证 |
|---|---|---|
| **不丢信息** | 已知字段显式渲染；**未知字段落到「扩展」段**（插件自定义字段也不会丢） | 往返差异 = **0 项** |
| **精度显式** | 时间码为毫秒精度；原数据超出毫秒时**照实截断并写进源码告警区**，不静默 | 用 `duration=1.00049` 验证告警产出 |
| **解析失败要响** | 未知语法/未知标签/非法时间码 → 抛 `SourceParseError`，**不猜不吞** | 8 项非法输入全部正确报错 |

### 2.3 开发中修正的两个自身缺陷（值得记下来）

| # | 症状 | 根因 |
|---|---|---|
| 1 | `id` 往返后「缺失」 | 我把 `id` 排除在渲染外（当内部字段），却要求往返键集合一致 —— **自相矛盾**。`id` 是片段身份锚，人改源码后回读要靠它定位，**必须渲染** |
| 2 | `in_point`/`track` 往返后「多出」 | 比对时用「非空」算原始键集合，把 `0.0` 当成缺失 → 误报。**「有意义的零」不等于「空」** |

⇒ 第 2 条是通用陷阱：**判断「字段是否被渲染」不能用「值是否 falsy」**。

## 三、本轮升级二：词锚定阶段 1（采集词级时间戳）

### 3.1 为什么这是硬前置

原方案里我已查明：`drama_understanding_engine.py` 的三处 `transcribe()` **均未开词级时间戳**，
只有段落级 start/end。**段落级只够「定位到这句话」，做不了词锚定。**

### 3.2 改动

| 文件 | 改动 |
|---|---|
| `app/core/ai/whisper_asr.py` | `transcribe()` 新增 `word_timestamps: bool = False`；两种后端（faster-whisper / openai-whisper）都透传；新增 `_extract_words()` 把两种形态归一成 `[{"text","start","end"}]` |
| `app/modules/lego/drama_understanding_engine.py` | 新增 `WordTiming` dataclass；`DialogueSegment` 末尾追加 `id` / `words`（带默认值）；**3 处 `transcribe` 调用全开词级**；两处构造点填 `id` + `words` |
| `app/modules/lego/character_cache.py` | 序列化 **与** 反序列化都补 `id` / `words` |

### 3.3 顺带修掉一个存量静默丢数据

`character_cache.py:360-369` 的台词序列化**只写** `start_time/end_time/speaker/text/emotion`，
**漏了 `volume`/`speed`** —— 而反序列化处却老老实实 `dlg.get("volume", 0.0)`。
⇒ **缓存回读的 volume/speed 永远是 0.0**，且无任何报错。本轮一并补上。

> 这又是一例「一个字段横跨序列化/反序列化两处，漏一处就静默失效」
> （同角色库字段模型、同 DialogueSegment 新增字段的教训）。

### 3.4 已验证

| 项 | 结果 |
|---|---|
| `transcribe` 签名含 `word_timestamps` | ✅ |
| `_extract_words` 两种形态归一 | ✅ attr / dict 都正确 |
| 空白词丢弃（不留无锚定价值的词抬序号） | ✅ |
| **脏数据不崩**（`start='bad'` 降级为 0.0） | ✅ |
| `DialogueSegment` 新字段 | ✅ |
| **旧式构造仍可用**（向后兼容） | ✅ `id=''` / `words=[]` |
| 词区间 → 时间区间换算 | ✅ `[1,3)` → `0.300s~0.900s` |
| 锚点贯通到工程源码并往返无损 | ✅ |

**注意**：本轮完成的是**原料采集**（阶段 1）。
「改文案 → 自动重新锚定」（`re-anchor` 匹配算法）仍是阶段 3，**尚未实现** ——
现在的 `id` 只是当次分析的局部标识，跨版本对应要靠方案里设计的
`text_fingerprint` + `difflib` 序列对齐来完成。
