## 0. 一句话结论（先看这里）

按 **27 个功能域**对标业界最佳开源实现后：

- **架构类型「相同」的占绝大多数**，其中 **6 个域已经收敛到与顶级开源同构**（画布执行引擎、ASR、音频、转场滤镜、云 Provider、NLE 引擎）——这是本轮最反直觉、也最值得高兴的发现：**项目不是"架构错位"，而是"覆盖面与健壮性"的差距。**
- **明确 ≥40% 差距的有 8 个域**，其中 **1 个是「功能性缺失」**（不是做得差，是根本没有）。
- **最痛的缺口 = 互操作性**：项目 **完全没有 OTIO / FCPXML / 时间线级 EDL** 能力（只有 YouTube 章节 EDL）。而 auto-editor、Shotcut、Kdenlive、DaVinci 全部把 OTIO 当标配。这一条直接决定「项目能不能进专业剪辑工作流」，是**投入产出比最高的补强点**。

## 3. ≥40% 差距详析（8 条，按投入产出比排序）

### 3.1 【最关键】时间线互操作缺失 —— 差距 ~50%（功能性缺失）· 层 A
- **现状**：全库 **无 `opentimelineio` import**；`fcpxml` 仅出现在 2 处**文件扩展名白名单**（`local_asset_manager.py:100`、`materials_module.py:184`），无解析器；EDL 仅 `chapter_markers.py:231` 导出 **YouTube 章节**（CMX3600 子集），**非时间线级 EDL**。
- **标杆做法**：**OpenTimelineIO**（Pixar/ASWF，Apache-2.0）用 `otio.adapters.read_from_file("x.aaf")` 一行打通 FCPXML/AAF/EDL/Premiere；`auto-editor` 直接把自动剪辑结果导出为 OTIO/Premiere/Resolve/FCP。
- **为什么值钱**：补上「**导出 OTIO + 读入 OTIO**」= 项目立刻能进专业工作流（人工在 Premiere 精修后回导），且这是**纯新增模块、零冻结区改动**。
- **建议**：新增 `app/core/interchange/otio_adapter.py`，把 `timeline_dsl.py` 的 `Timeline/Clip/Track` 与 OTIO 双向映射。参考 `opentimelineio` 的 adapter 插件协议。

### 3.2 帧插值自研非模型 —— 差距 ~60%（质量天花板）· 层 D
- **现状**：`ai_interpolation.py:7` 源码原话 *"不是深度学习插帧（无 RIFE / DAIN 等模型）"*，用 `SceneChangeDetector`+`ContextAwareInterpolator` 做传统插值。
- **标杆**：**RIFE**（实时、轻量、8GB 显存可跑）/ FILM / EMA-VFI 才是当代观感。
- **建议**：这是**能力升级**而非修 bug，需按 D 层拍板（换模型 = 产品档次变化）。

### 3.3 转场覆盖度 + 伪别名 —— 差距 ~45% · 层 A/C
- **现状**：`transitions.py` 共 **55 个**，对标注释自称"对标 OpenShot 400+"。且 **3 个是别名冒充独立转场**：
  - `glitch` → `xfade=transition=pixelize`（与 `pixelize` 同滤镜）
  - `iris_in` → `circleopen`、`iris_out` → `circleclose`、`wipe_circle` → `radial`
- **标杆**：OpenShot 400+（含自定义 GLSL）、MLT `frei0r` 生态。
- **建议 A（可直接）**：先修正伪别名标签/参数，避免用户选"故障"得到的其实是"像素化"；**建议 C（需解冻）**：若要扩到真·GLSL 转场需动画布渲染通道。

### 3.4 TTS 引擎覆盖窄 —— 差距 ~45% · 层 B
- **现状**：`voice_generator.py` 链式回退 **Coqui → gTTS → edge-tts**（line 320-409），全失败诚实报错（符合"不返回假音频"铁律）。
- **标杆**：**Piper**（本地、快、多音色）、**ChatTTS**（中文自然）、**GPT-SoVITS**（音色克隆）。
- **建议**：新增 Piper 后端（纯本地、无网依赖），与现有 3 个并存。

### 3.5 Agent 编排缺图状态/checkpoint —— 差距 ~45% · 层 B
- **现状**：`agent_loop.py` 是自研 ReAct（`parse_tool_calls`/`build_tool_schemas`/`AgentLoop`），有 `agent_task_store.py`/`agent_session.py` 做持久化，但**无 LangGraph 式"图状态 + 断点续跑 + 人在环审批节点"抽象**。
- **标杆**：**LangGraph**（状态图+checkpointer+interrupt）。
- **建议**：不需换框架，可**借鉴其 checkpoint 语义**补到 `agent_session`（项目已有 `ERR_WAITING_APPROVAL`，说明"人在环"半成品已在）。

### 3.6 MCP 客户端自研 —— 差距 ~40% · 层 B
- **现状**：`mcp_client.py`(667) `McpClientManager` 自研 stdio/SSE + preset 管理。
- **标杆**：官方 `modelcontextprotocol/python-sdk`。
- **建议**：评估「迁官方 SDK」vs「保留自研但补协议版本/能力协商」——属拍板项。

### 3.7 插件系统双套并存 —— 差距 ~40%（架构债）· 层 B
- **现状**：`PluginManager`（`plugin_manager.py`）+ `ExtensionsRegistry`（`extension_base.py`）**两套互不相通的插件体系**（`PluginBase` / `Extension` ABC / `PluginExtension`/`SkillExtension`/`McpExtension`）。
- **标杆**：**pluggy**（pytest 官方，hook 规格 + 插件发现）。
- **建议**：合并为一套（注意：`app/plugins/` 是真家，旧 `plugin_*.py` 已归档勿合并——见项目不变量 §2）。

### 3.8 工程文件无标准互操作 —— 差距 ~40% · 层 A/B
- **现状**：`project_manager.py`/`project_snapshot.py` 自发 json 工程格式。
- **标杆**：Kdenlive `.kdenlive`（MLT XML）/ OTIO。
- **建议**：与 3.1 合并——导出侧同时给「工程 json + OTIO」两种。
