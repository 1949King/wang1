1结论先行 TL;DR

OpenFilm 是什么（一句话）
  • 它把「一部电影」压缩成一个 HTML 文件（film.html），把「一个镜头」压缩成一个函数（网页里暴露 window.film.frame(t)，画出任意时刻），把「剪辑软件」做成一个本地浏览器编辑器（Studio）。你的编码 Agent（Claude Code/Codex 等 10 个）把电影写成网页，你亲手改，无头 Chromium + ffmpeg 逐帧渲染成片。
  • 它对我们最大的帮助不是代码，是三个「协议级」设计：① frame(t) 纯函数契约 + 宿主时钟劫持——AI 生成的任意画面可确定性重放、可并行渲染、可自动质检；② 统一 NLE 导出中间层——AI 粗剪成果一键变 FCPXML/剪映工程，交回人工精修；③ Agent 改动感知回执 + git 闭包版本史——Agent 批量改片子不丢人审、随时可回滚。
  • 它没有的，恰恰是我们有的：多素材智能筛选、ABCD 融合矩阵、抽卡选优闭环（draw_book/gen_critic）、22 万行 Python 生产引擎——OpenFilm 是「生成型」工具，拾光剪影是「素材重组型」工厂。别妄自菲薄，也别整体照搬。
✅ 落地建议（详见第 6、7 节）：按 P0/P1/P2 三档借鉴——P0 是「帧精确 seek + 双 shuffle 质检」（直接治我们预览-导出不一致的老毛病）；P1 是「NLE 导出中间层 + Agent 回执 + inverse undo」；P2 是「技能三段式 + Provider 密钥安全 + git 版本史」。全部是设计借鉴，零依赖引入，不触碰冻结区与 EditorModule._clips 真相源。

3架构总览：五层，全部围绕一个协议 ARCHITECTURE

它的整个系统围绕 SPEC.md（OpenFilm Protocol 0.1）展开——这份 216 行的协议用 RFC 2119 关键词写成，是「film.html 格式 + frame(t) 契约 + 宿主职责」的唯一权威。代码只是协议的参考实现。

① 文档层 film-doc.mjs（965 行）—— 一部电影 = {stage, tracks:[{clips}]}
film-doc.mjs · film-doc.d.mts · timeline.mjs(965) · look.mjs(358) · shared.mjs(413)

film.html 只有两个顶层字段（多一个就报错，film-doc.mjs:297）；轨道 = <section>，片段 = 4 种原生 HTML 标签（iframe=网页镜头 / video / img / audio，film-doc.mjs:473）；入点/出点不在字段里，编码在 URL 片段 #t=2,6（film-doc.mjs:680）；读写闭环保留未变片段的原始文本，AI 改片不产生垃圾 diff（film-doc.mjs:916-964）。

▼ 被宿主托管
② 宿主层 host.mjs（479 行）—— 时钟劫持 + CDP 逐帧驱动
host.mjs · render.mjs(190) · seekable.mjs(101) · locations/overrides/media-links

4六大架构创新（带证据） INNOVATIONS

创新 1：frame(t) 纯函数契约 + 宿主时钟劫持

整个系统的地基。页面只暴露 window.film = {frame(t), duration, ready}（SPEC.md:130-136）；宿主把页面能读到时间的一切都改成 t（host.mjs:24），于是 frame(t) 退化为数学纯函数——同一 t 永远同一帧，与之前画过什么无关。

为什么是创新：Remotion 等框架靠「约定」达到确定性；OpenFilm 用宿主强制保证，并配套机器验证（见创新 2）。这意味着：并行渲染、帧缓存、单镜头重渲、质检，全部只是「对不同的 t 求值再截图」。

SPEC.md:152 — "For the same t, frame MUST produce the same picture, whatever was drawn before it and in whatever order frames are requested."

创新 2：「同 t 双 shuffle」自动质检（look 命令）

openfilm look 把「渲染正确性」这个不可判定问题转成机器可验证规则：同一组 t 用两种固定乱序各画一遍，逐帧比对（look.mjs:88-101），不一致就精确报告「哪个 t 画出了两张不同的画」并列罪魁（时钟/未播种随机/帧间状态）。

附带一整套成片质检：文字被裁切检测（cutText，look.mjs:103-108）、平色检测、EBU R128 响度波形（look.mjs:248-267）、轨道重叠检测。test/ 目录放的就是「Agent 典型错误」网页样本（clock/impure/subtle-shift/cut-text/throws）——测试哲学是「给 AI 会犯的错写样本，再断言工具输出」。

创新 3：帧精确 seek 双保险

逐帧渲染的最大敌人是视频 seek：① currentTime setter 打 +0.001 补丁，修掉帧边界 seek 落到上一帧的问题（约 1/3 概率发生，host.mjs:12-15）；② 渲染前把慢 GOP 素材（关键帧 1–4 秒）转成关键帧每 0.25s 的近乎无损副本，按版本+路径+mtime 哈希缓存（seekable.mjs:1-5, 67-91）。

为什么重要：这是「预览-导出一致性」的工程正解——预览、质检、导出三处走同一套帧定位逻辑，从根上消灭「预览对的、导出错的」。

创新 4：统一 NLE 导出中间层（FCPXML/剪映）

内部时间线 → planNleTimeline 规划成编辑器无关的表格（帧边界 round 对齐消除一帧缝隙；隐藏轨转 disabled 不丢弃，nle.mjs:9-19）→ 写三种工程：FCPXML 1.10（音量转 dB、字幕作可编辑 Basic Title，fcpxml.mjs:56,115-138）、剪映/CapCut 草稿三件套（微秒时间、素材登记媒体库，jianying.mjs:14-289）、xmeml（PR/DaVinci 免插件）。

杀手细节：网页镜头导出 NLE 时单独渲染成 ProRes 4444 带 Alpha（exports.mjs:1178-1199）——AI 生成的合成画面进专业软件后仍保留合成能力。「AI 粗剪 + 人工精修」工作流由此成立。

创新 5：Agent 改动感知回执 + git 闭包版本史

回执：Agent 写文件 → 服务端文件监视 → WebSocket 推 {type:'film', rev}；编辑器记 ours 集合，watcher 回来的同 rev 视为回声忽略；冲突以服务端为准重合并；文件写一半置 broken 暂停编辑而非崩溃（use-film.ts:55-141）。

版本史就是 git：每项目独立 repo 于 .film/history，绝不碰用户自己的 .git（history.mjs:1-5）；版本内容 = 影片闭包（递归解析所有引用文件，closure.mjs:1-21）；大媒体按内容哈希外置、git 树里只放指针，APFS/Btrfs clone 秒存（history-store.mjs:1-11）；系统绝不自动 commit，每次提交都是用户的；未提交改动切分支时 park 到 refs/openfilm/parked/。

创新 6：技能体系 = 可执行的剪辑方法论

SKILL.md 三段式：What has to be true（成片验收清单）/ What you have（工具边界）/ With the person（协作契约）（collage/SKILL.md:11-34）；description 写中英双语触发词让 Agent 匹配口语请求（long-to-short/SKILL.md:3）。

long-to-short 技能五条硬约束（long-to-short/SKILL.md:12-23）：不断章取义（if/not 不能切掉、答案必须带问题）、每条独立成片、每刀落在停顿处、竖屏构图避让 App 按钮区、先自审再看（「a clip you would scroll past is not done」）。lyric-video 更要求「每字落在唱词时刻、误差两帧内、用数字汇报吻合度」（lyric-video/SKILL.md:16-18）。

🎩 另一个值得注意的设计：overrides（人机协同修改保护）。人在 Studio 里对网页镜头内元素的微调（位置/样式/文字）按 CSS selector 存在 clip 的 overrides 字段里，每帧绘制后应用（SPEC.md:75-85）；轨道可标 locked——「人专属，Agent 不许改」（SPEC.md:49）。MANUAL 要求 Agent「改之前重读 film.html，只改你打算改的」。AI 重生成永不覆盖人工修改——这正是我们「批量生成 + 单点修正」场景的解药。

🔵 C 档：只作参照（思想价值，不搬代码）

6不适用与风险（诚实清单） LIMITS

#事实影响
1「网页即镜头」内容模型与我们基因不同：OpenFilm 的镜头是 Agent 用代码画出来的（生成型），我们的镜头是已有素材的筛选重组（重组型）。它没有多素材智能筛选、ABCD 情绪矩阵、抽卡选优闭环。内容生产模型不搬；只搬协议/工程/导出层。反过来说：我们的抽卡闭环是它没有的，这是我们的独门优势，继续按 ④抽卡→①编剧→②导演→③美术 顺序补齐
2v0.2.0 很新（2026 年项目），长期维护未知；SPEC 自称 0.1 draft。只借鉴经过验证的设计（本次全部一手核实过行号），不做技术选型依赖
