## 零、先回答事实问题：现在是三维吗

**不是。卡片画布是 100% 纯二维。**

| 事实 | 代码位置 |
|---|---|
| `ViewMode` 中 `canvas` 与 `stage3d` 是两个**并列视图** | `store.ts:126-135` |
| 卡片位置只有 `x`/`y`，React Flow 原生节点模型，无 z | 全套节点渲染在 `CanvasShell.tsx` |
| 三维场景坐标为 `Vec3 = [number, number, number]` | `stage3dScene.ts:22` |
| `Stage3D.tsx` 是完整 three.js：WebGLRenderer / OrbitControls / TransformControls / UnrealBloom / EffectComposer | `Stage3D.tsx:6-11, 993` |
| 三维场景导出「截图」回写画布卡，**无坐标映射** | `Stage3D.tsx:2737` `readRenderTargetToDataURL` |

**结论：三维不是「没有」，是「有但被隔离」。**

## 一、问题定义

### 1.1 用户原话

> 「目前咱们的卡片画布是一个三维的形式吗？……二维画布，感觉会不会差点什么东西？能不能往下一代概念的发布进行迭代，但保留现在已有的一些概念、理念？」

### 1.2 拆解

| 子问题 | 答案 |
|---|---|
| 是三维吗 | 纯二维 |
| 差点什么 | 不是缺 z 轴，是**卡片与三维舞台之间没有发生关系** |
| 往哪迭代 | 「平面 + 深度语义」——视觉仍二维，卡片多三样能力 |
| 保留什么 | 一图胶囊卡片 / 磁吸咬合 / 双档 / 降维参数 / 生成闭环 **全部保留** |

### 1.3 明确否决的方向

| 否决项 | 理由 |
|---|---|
| ❌ 伪 3D 卡片（透视倾斜 transform） | 视觉噪音，拖拽手感立即劣化，无表达价值 |
| ❌ 无限缩放 3D 空间 | 小白模式用户彻底迷路，与「降维」初心相反 |
| ❌ 重写卡片模型 | 316 行 `NoviceCard.tsx` + 244 行 `types.ts` 全保留 |
| ❌ 改冻结区 | 本方案不动 `canvas-magnetic-intent` |

## 三、核心概念：空间语义画布

### 3.1 一句话定义

> **画布保持二维交互，卡片获得「深度 / 视角 / 取景」三个语义属性，并与已有的三维导演台双向贯通。**

### 3.2 与现有理念的关系（保留声明）

| 现有理念 | 本方案如何处置 |
|---|---|
| 一图胶囊卡片 | **保留**。能力挂在卡片内部，不改胶囊形态 |
| 磁吸 / 咬合 / 贴合缝 | **保留且正交**。磁吸管 `x/y`，深度层管「前后」，两轴独立互不干扰 |
| 小白 / 专业双档 | **保留**。空间能力默认仅小白模式开放，专业模式保持纯净节点画布 |
| 降维参数（3~5 个开关） | **保留**。深度信息**自动推导**，不给用户加手工参数 |
| 生成闭环 | **保留**。立体预览直接消费生成结果，不引入新输入源 |

**红线：磁吸的 `edge-gap` 判据只作用于 `x/y`，深度不参与吸附计算。** 避免把两个正交系统耦合成不可测的复合体。

## 四、三层能力设计

三层**可独立交付**：做完第一层就能用，不必等三层全齐。

### 4.1 第一层 · 空间记忆（成本：低）

**问题**：卡片只能在平面上，前后关系只能用「叠层」表达，且叠层的视觉语言不可读。

**设计**：

| 项 | 内容 |
|---|---|
| 数据 | 复用已有 `intentDepth`（1~3），**不新增字段** |
| 规则 | 同位置前后卡片自动成「层」；`stack` 方向的磁吸结果写入层关系 |
| 视觉 | 前景层：投影加深 + 轻微上浮；后景层：降饱和 + 轻微缩小 |
| UI | **复用已有 `StackBadge`**，不新增任何 UI 元素 |

**技术落点**：
- `NoviceCard.tsx`：`intentDepth` 参与 className 派生（新增 ~6 行）
- `novice-cards.css`：新增 `.nv-card[data-depth="1|2|3"]` 规则（~24 行）
- **不碰冻结区**

**验收**：同一位置 3 张卡叠放，肉眼可立即分辨前后，且不需要点开任何面板。

---

### 4.2 第二层 · 立体预览（成本：中）

**问题**：生成结果一律平面，看不出景深与机位；要跳视图才看得到。

**设计**：

| 项 | 内容 |
|---|---|
| 形态 | 卡片内嵌「微舞台」——**只读**、可转的小预览窗，占卡片内容区 |
| 交互 | 鼠标拖 = 转视角；滚轮 = 远近；**不可编辑任何东西** |
| 数据源 | 复用 `thumbOf()` 已取到的图；深度/角度来自 `intentDepth` + `lastCameraName` |
| 视觉 | 用 CSS `perspective` + `transform` 做**体感**，非真三维渲染 |

**关键技术判断（重要）**：

> 卡片内**不跑第二个 three.js WebGL 上下文**。

原因：一张画布可能有几十张卡，每张卡一个 WebGL context 会瞬间打爆浏览器上下文上限（通常 8~16 个），并吃掉全部显存。正确做法是——

**方案 A（推荐）：CSS 伪三维**
- 用 CSS `perspective` + `rotateY/rotateX` 让缩略图产生立体感
- 配合视差层（前景/中景/背景三张图错位移动）
- 成本极低，零显存，几十张卡无压力

**方案 B（进阶）：单例离屏渲染 + 纹理分发**
- 全局仅 **1 个** three.js 渲染器，离屏渲染到 canvas
- 把结果作为纹理分发给各卡片的 `<img>`/`<canvas>`
- 需要帧调度器（只有可见卡片参与渲染）
- 成本高，但能做真实光影

**建议先做方案 A**，验证「用户是否真的需要转动」；若需要，再升级方案 B。

**技术落点**：
- 新建 `novice/MicroStage.tsx`（约 120~160 行，纯 CSS 三维）
- `NoviceCard.tsx` 内容区分派（新增 ~10 行）
- `novice-cards.css` 新增微舞台样式（~60 行）
- **不碰冻结区**

**验收**：不跳视图，就能判断这张卡的景深与机位是否合理。

**问题**：已有完整镜头数据（`shotSize` / `lastCameraName` / `captures[]` / `AspectId`），但画布上完全不显示，构图靠脑补。

## 五、实施分包与顺序

### 5.1 依赖关系

```
P0（零风险 CSS 补账）
 └─→ P1（跟手 + 单轴吸附）        ← 手感地基，需解冻
      └─→ P2（整列让位）            ← 补齐手机主屏手感
           └─→ 第一层（空间记忆）
                └─→ 第二层（立体预览）
                     └─→ 第三层（镜头取景）
```

### 5.2 为什么手感必须排在前面

> **「跟手」是地基。** 地基未打就盖楼层，每一层都会继承同一个毛病——用户摸到的仍是「卡片自己跳走」，深层能力再好也无感。

而且第二层与第三层都要在**卡片内部**加东西，卡片因此变复杂；如果此时拖拽还不跟手，新增内容的渲染成本会叠加到已经过载的拖拽路径上（见 `UseMagneticDrag.ts:245` 每帧 `writeNodePos`），手感会进一步恶化。

### 5.3 工作量评估

| 层 | 新增文件 | 修改文件 | 估行数 | 碰冻结区 |
|---|---|---|---|---|
| P0 | 0 | 3 | ~25 | ❌ |
| P1 | 0 | 2 | ~60 | ✅ |
| P2 | 2 | 2 | ~260 | ✅ |
| 第一层 | 0 | 2 | ~30 | ❌ |
| 第二层 | 1 | 2 | ~230 | ❌ |
| 第三层 | 1 | 2 | ~130 | ❌ |

**除 P1/P2 外，其余全部不碰冻结区。**

## 六、风险与红线

| # | 风险 | 应对 |
|---|---|---|
| 1 | 多卡 WebGL 上下文爆掉 | 第二层**严禁**每卡独立 three.js；先走纯 CSS |
| 2 | 卡片变复杂 → 拖拽更卡 | 手感修复（P1）必须先行；新增 DOM 需控制层数 |
| 3 | 深度与磁吸耦合 | 深度**不参与** `edge-gap` 计算，两轴严格正交 |
| 4 | 小白模式信息过载 | 三层能力**默认折叠**，仅选中卡展开 |
| 5 | 专业模式被污染 | 三层能力用 `isNovice` 门控，专业模式零感知 |
| 6 | 冻结区误改 | 任何涉及 `canvas-magnetic-intent` 的改动前，**必须取得明确解冻授权** |

## 七、与手机主屏方案的关系

两份方案是**正交**的，不冲突：

| 方案 | 管什么轴 | 目标 |
|---|---|---|
| 手机主屏拖拽手感（前一份） | `x/y` 平面手感 | 摸起来顺 |
| 空间语义画布（本份） | 深度 / 视角 / 取景 | 看起来懂 |

**顺序建议**：先「摸起来顺」，再「看起来懂」。因为「摸起来顺」是每次交互都触发的基础体验，「看起来懂」是理解层面的增益。
