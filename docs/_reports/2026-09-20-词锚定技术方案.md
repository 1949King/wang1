# 词锚定技术方案（Word-Anchoring）

> 来源：Hypit 适配调研（`docs/_reports/2026-09-20-Hypit适配分析.md`）的 P1 项
> 日期：2026-09-20 ｜ 状态：**方案待评审，未动代码**
> 口径：本方案所有「现状」结论均取自**本地实际代码**，标 `file:line` 可核对

---

## 一、要解决什么

**问题（一句话）**：现在剪辑片段的落点锚在**秒**上，而 AI 的结论（哪句台词、什么情绪）也是秒。
文案一改就要**重新分析 + 重新落点**，AI 分析出来的东西保不住。

**目标（一句话）**：让片段的落点锚在**台词的词**上 —— 改文案只需**重排**，不必重分析。

**非目标（本轮明确不做）**：
- 不引入 Hypit / SVML（跨栈、协议限制，见适配报告 §五）
- 不改 `_clips` 的既有字段语义（只通过 `metadata` 扩展）
- 不做「改文案 → 自动出片」的端到端闭环（那是阶段 4 之后的事）

### P0-1 · 采集词级时间戳

**现状**：三处 `transcribe()` 都没开词级时间戳，`DialogueSegment` 里没有词。

**改动**（`app/modules/lego/drama_understanding_engine.py`）：

| 位置 | 现状 | 改为 |
|---|---|---|
| `:397` `transcribe(...)`（可能是封装函数） | 无 word timestamps | 透传 `word_timestamps=True` |
| `:430` `model.transcribe(video_path, language="zh", task="transcribe", vad_filter=True, vad_parameters=...)` | 同上 | 加 `word_timestamps=True` |
| `:439` `model.transcribe(video_path, language="zh", task="transcribe", verbose=False)` | 同上 | 加 `word_timestamps=True` |

**数据结构新增**：

```python
@dataclass
class WordTiming:
    """单个词的时间与文本。词锚定的最小单位。"""
    text: str
    start: float
    end: float


@dataclass
class DialogueSegment:
    start_time: float
    end_time: float
    speaker: str
    text: str
    emotion: EmotionalTone
    volume: float
    speed: float
    # ↓ 新增（带默认值，必须放在末尾 —— 现有构造点在 :410-418 用的是关键字实参，
    #   但 dataclass 不允许「无默认字段」排在「有默认字段」之后）
    id: str = ""                                  # 当次分析的局部标识，如 "d0012"
    words: List["WordTiming"] = field(default_factory=list)
```

> ✅ **构造点核对已完成（2026-09-20）**：全库 `DialogueSegment(` 共 **3 处**，
> **全部使用关键字实参**，无位置实参调用 ⇒ 在末尾追加带默认值的字段**不会静默错位**：
>
> | 位置 | 构造方式 |
> |---|---|
> | `drama_understanding_engine.py:410` | 全关键字 ✅ |
> | `drama_understanding_engine.py:459` | 全关键字 ✅ |
> | `character_cache.py:445` | 全关键字 ✅ |
>
> ⚠️ 但 `character_cache.py:445` 那处是**从 JSON 反序列化**（`d.get("start_time")` 等），
> 新字段若要持久化，**该处也必须同步补上 `words` / `id` 的读取**，否则缓存回读会丢锚点原料。
> 这是「一个字段横跨多处、漏一处就静默失效」的又一例（同角色库字段模型的教训）。

**成本**：`faster_whisper` 开 `word_timestamps=True` 会略微增加转写耗时（词级对齐），

### P0-2 · 「同一句话」的身份问题（本方案最容易想错的地方）

**先承认一件事**：改文案 = 重跑 ASR = **时间也变了**。所以
**不存在「内容派生出来的稳定 id」** —— 任何 `hash(text)` 方案在文本变化时必然失效，
而「文本变化」恰恰是我们要支撑的场景。

**正确设计**：id 只作**当次分析的局部标识**，跨版本的对应关系由**重新锚定（re-anchor）**解决。

锚点里存三样东西，各司其职：

| 字段 | 用途 | 变化时 |
|---|---|---|
| `dialogue_id` | **快路径**：同一次分析内定位 | 重新分析后可能失效 |
| `text_fingerprint` | **慢路径**：跨版本匹配（去标点的原句） | 不改这句就不变 |
| `word_span` | 词区间 | 随 fingerprint 一起迁移 |

## 四、锚点数据结构

写在 `Clip.metadata["anchor"]` 里，**不改 `timeline_dsl` 的既有字段**：

```python
clip["metadata"]["anchor"] = {
    "kind": "dialogue",
    "schema": 1,                       # 便于将来演进
    # ── 主锚点 ──
    "dialogue_id": "d0012",            # 当次分析的局部 id
    "text_fingerprint": "你别走我一个人怕",   # 去标点原句（跨版本匹配用）
    "from_word": 3,                    # 词序号（0-based，含）
    "to_word": 9,                      # 词序号（不含）
    # ── 保底 ──
    "fallback_range": [12.4, 15.1],    # 原时间范围：锚点彻底失效时回落到此
    "orphan": False,                   # re-anchor 后仍未匹配上 → True
}
```

**为什么必须有 `fallback_range`**：不是每段素材都有台词（空镜、BGM 段、纯动作）。
锚点匹配失败时**绝不能把 clip 丢掉或挪到 0** —— 回落到原时间点，宁可不动。

## 五、重排算法（re-anchor，纯函数）

**输入**：`clips_with_anchor`（待迁移）、`new_dialogues`（新分析结果）、`similarity_threshold`

**输出**：`ReAnchorPlan`（**只描述差异，不写数据**）

```python
@dataclass
class ClipShift:
    clip_id: str
    old_range: Tuple[float, float]
    new_range: Tuple[float, float]
    reason: str          # "id_hit" | "fingerprint_match" | "orphan" | "unchanged"

@dataclass
class ReAnchorPlan:
    shifts: List[ClipShift]
    matched: int
    orphaned: int
    unmatched_new: int   # 新增台词数（可提示用户"有新台词可自动入轨"）
```

**步骤**：

1. **快路径**：`dialogue_id` 在新序列中且 `text_fingerprint` 一致 → 直接取
   `new_dialogue.words[from_word:to_word]` 的时间，`reason="id_hit"`
2. **慢路径**：id 失效 → 用 `difflib.SequenceMatcher` 对新旧台词序列做**整体对齐**
   （不是逐条比对 —— 利用顺序约束能大幅提升准确率），再对候选做文本相似度确认
   （`SequenceMatcher.ratio() >= threshold`，建议 0.75，可配置）→ `reason="fingerprint_match"`
3. **孤儿**：两条路都失败 → `orphan=True`，`new_range = fallback_range`，`reason="orphan"`
4. **排序与冲突**：按 `new_range.start` 排序，检测重叠
   - 若与**无锚点**片段重叠 → 标注冲突，**不自动改**，交用户决策
   - 有锚点片段之间由台词顺序天然保证不重叠（词序号单调）

**纯函数的意义**：可以脱离 Qt / `_clips` 单测，覆盖「改一句 / 删一句 / 插一句 / 整段重写 / 重排顺序」五种场景。

### 与既有让位机制的呼应

项目里已有同类纪律 —— 磁吸整列让位（`magnetic/reflow.ts` 的 `planReflow()` 同样是
「先出 plan / ghost，位移在 `onNodeDragStop` 才执行」）。
**本方案沿用同一条时序红线**：计算与落地严格分离。

## 六、与 `_clips` 并发纪律的配合（**红线**）

`_clips` 是**跨线程共享**的（画布桥 HTTP 线程 + autosave 每 3s 序列化）。
因此：

| 阶段 | 纪律 |
|---|---|
| 计算 re-anchor plan | **只读**：用 `self._clips_snapshot()` 取一次快照，绝不在锁外遍历 `self._clips` |
| 落地 plan | **整段 `with self._clips_lock:`**；非原子替换（清空 + 逐个 append）必须在锁内 |
| 禁止 | 把 `self._clips` 引用交给 `json.dump`（会写出半截列表的损坏工程） |

`_clips_lock` 是 **RLock**（可重入），内部函数再取锁不会死锁 —— 但**不要**因此省略外层锁。

## 八、回归验证

| 项 | 做法 |
|---|---|
| **纯函数单测** | 五种场景各一例：改一句 / 删一句 / 插一句 / 整段重写 / 两句交换顺序 |
| **不变量** | ① 无锚点片段的 `range` **必须不变** ② `orphan` 片段回落到 `fallback_range` ③ 有锚点片段按词序单调，不产生新重叠 |
| **时长** | **不设「总时长守恒」断言** —— 台词变了时长本来就该变，设了会误导 |
| **锁纪律** | 并发压测：一边 re-anchor 落地、一边 autosave 序列化，断言「不完整读 = 0 次」（沿用既有压测口径） |
| **冻结区** | 涉 `editor_module.py` 的锁点方法时按冻结区纪律走（解冻 → 改 → 复跑守卫 → 补记录） |
| **一键** | 挂进 `_verify/` 并纳入 `run_all_checks.py` |

## 九、风险与回退

| 风险 | 缓解 |
|---|---|
| 词级时间戳准确度不足（中文 ASR 分词粒度问题） | 阶段 1 先只采集不消费；用真实素材核对词边界是否合理，再进入阶段 2 |
| re-anchor 匹配错（把 A 句的锚点挂到 B 句） | 相似度阈值可配置 + **孤儿优先于错配**（匹配不确定时倾向标 orphan，让用户看到） |
| 改文案后片段大范围 orphan | 属**预期行为**（确实找不到对应句子）；UI 需明确呈现「N 个片段失去锚点」，而不是静默 |
| 与既有 `STORYAPPLY` 回灌路径冲突 | 两条路径都写 `_clips`；落地前先确认谁先谁后，必要时统一走同一个写入器 |

**回退方式**：锚点是 `metadata` 里的**附加字段**，删掉它即回到「纯时间轴」的现状，无数据损坏。

## 十、明确不做

- ❌ 不做「锚点即真相」—— `_clips` 仍是唯一真相源，锚点只是**重排的依据**
- ❌ 不在拖拽/编辑过程中实时重排（位移一律在执行阶段做）
- ❌ 不为无台词片段造锚点（那是伪锚定，比没锚点更危险）
- ❌ 不改 `timeline_dsl` 既有字段的语义或单位
