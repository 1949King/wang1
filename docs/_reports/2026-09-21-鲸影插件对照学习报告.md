## 一、结论先行

**鲸影的「生成管线」比拾光剪影完整；拾光剪影的「剪辑 + 工程纪律」比鲸影强得多。**
两者不是替代关系——**该学的是它的「调度与优化闭环」，不该碰它的「成片」环节**。

### 最高价值的 5 个可借鉴点（按性价比）

| # | 借鉴点 | 拾光剪影现状 | 优先级 |
|---|---|---|---|
| 1 | **多账号额度池**（配额/轮换/指数退避/失败换号/免费优先） | **完全没有** | 🔴 最高 |
| 2 | **`capabilities` 能力声明 + 自动路由** | 只有「provider 名字回退顺序」 | 🔴 高 |
| 3 | **评分回写闭环**（得分+增益组合写回评分簿 → 下次按历史选） | 有质检，**无回写** | 🔴 高 |
| 4 | **`quote` 报价 + `health` 健康检查** | 无（生成前不知道花多少钱） | 🟡 中 |
| 5 | **每段 gate（auto/ask/manual）+ 段落可重跑** | 无 | 🟡 中 |

## 二、架构对照

### 2.1 Provider 抽象层 —— 差距最大的一处

| 维度 | 鲸影 | 拾光剪影 |
|---|---|---|
| 接口 | `id` + `capabilities` + `quote` + `submit` + `status` + `fetch` + `health`（**6 方法**） | `BaseCloudProvider(api_key, base_url)` + `last_usage`（**面向 LLM 对话**） |
| 视频生成入口 | 同一套 Provider 抽象 | **另一条路**：`video_generation_client.generate()`（同步阻塞） |
| 调用模型 | **异步任务**：submit → status 轮询 → fetch | **同步**：一次调用等结果 |
| 能力声明 | ✅ `capabilities{textToVideo,imageToVideo,firstLastFrame,lipSync,maxDurationSec,resolutions}` | ❌ 无（仅 `_resolve_provider_order()` 按名字回退） |
| 报价 | ✅ `quote(stage, spec) → {qualityTier, costEstimate}` | ❌ 无 |
| 健康 | ✅ `health() → {ok, quotaRemaining}` | ❌ 无 |
| 本地兜底 | mock provider / ComfyUI | ✅ **`_call_local_fallback()`（ffmpeg 合成）** ——这条你**已经有** |

> **鲸影的「薄抽象」主张**：新增供应商 = 一个适配器文件 + capabilities 声明，**流水线零改动**。
> 你现在的 provider 是「一个类 + send 方法」，视频侧则只有 seedance/cogvideo 两个内置 + 名字回退。

### 2.2 额度调度器（AccountPool）—— 你完全没有

鲸影的数据结构与算法：

```
账号条目：{provider, credential, dailyQuota, usedToday, qualityTier}

选路顺序：同供应商内
  ① qualityTier 高 → 低
  ② 配额未耗尽
  ③ 最近使用时间（均衡负载）

退避：失败后 60s 起，翻倍，封顶 30min
降级：免费额度耗尽 → 降级到付费 key
换号：提交失败**当场换下一个健康账号重提**（坏号冷却，不被反复拖死）
审计：每次选择记录理由（quota/decide 事件）
```

**拾光剪影现状**：`_resolve_aigc_channel()` 只是「渠道解析」，无配额概念、无健康状态、无退避。

### 2.3 提示词四层 + 评分回写闭环

| 层 | 鲸影 | 拾光剪影对应物 |
|---|---|---|
| 1 | **风格 DNA**（全局画风/色调/一致性 token） | ❌ 无 |
| 2 | **分镜模板**（景别/运镜/时长结构） | ⚠️ 部分（`_gen_prompts` 里由 LLM 自由生成） |
| 3 | **逐镜提示词**（可手写 + 模板变量注入） | ✅ `guard_pipeline.enhance_prompt()` 注入守护约束 |
| 4 | **负向/一致性注入**（自动生成、可覆盖） | ✅ **`guard_negative_all()`（30-40 条负面词）** |

**回写闭环（你没有的那一半）**：

```
生成 → 抽帧 → 评分（LLM 评审 + 用户点赞/重拍） → 高分提示词进模板库
                                        ↓
                          下一镜同风格 → 模板库命中 → 自动复用 + 微调
```

- **评分维度**：一致性 / 构图 / 动作 / 时长利用率 / 风格符合度
- 模板库按**风格 DNA 命名空间**隔离；**重拍记录降权**

> 拾光剪影已有「打分」（`_render_score_results` + 打分卡），但**只展示、不回写** —— 这是最容易补的一环：
> 把打分结果写进一个「提示词/增益评分簿」，下次生成前按历史得分选约束组合。

### 2.4 其他可参考设计

| 设计 | 说明 | 对你的价值 |
|---|---|---|
| **gate（auto/ask/manual）** | 每段三种模式，可随时切换并**重跑该段** | 你的管线是全自动；加 gate 可支持「人工接管某一段」 |
| **一致性资产库** | 角色/场景主图 + 逐镜变体登记，**参考图自动注入提示词** | 你的角色库更强，但「参考图自动注入」可补 |
| **风格基因（记忆）** | 风格 DNA / 模板评分演化 / 重拍反馈**跨会话沉淀** | 你有 `memory_store`，但没沉淀「风格偏好」 |
| **自我审计** | `whale_self_audit` 扫描自身 → 生成 AUDIT-REPORT.md；**「每天 diff 这份报告就是进度日志」** | 你已有 `run_all_checks`（22 项，**更强**）；可借鉴「报告 diff 即日志」的做法 |
| **凭证保险库** | `~/.whale/whale.json`（**0600 权限 + 原子写入**），API 只回脱敏，绝不落日志 | 可对照检查你的 key 管理是否满足这三点 |
| **口型同步段** | 有配音的镜头自动跑对口型，**失败回退原片**（不致命） | 你的项目有数字人模块，可对照 |
| **预置内容包** | 5 套题材（都市逆袭/仙侠/悬疑/甜宠/科幻），无 key 也能全链路出片 | 你的「剧本模板」可借鉴 |
| **provider matrix 单一事实来源** | `src/selfaudit/matrix.ts` 被健康路由/白名单/审计报告共享 | 你已有 `agent_capability_catalog`（同思路）|

## 四、建议的落地顺序

### 第一优先：额度池调度（省钱 + 稳定性直接见效）

在 `video_generation_client` 之上加一层 `provider_pool.py`：

```python
账号条目 = {provider, credential_ref, daily_quota, used_today, quality_tier, health}
选路 = quality_tier 降序 → 配额未耗尽 → 最久未用
失败 = 指数退避（60s 起翻倍，封顶 30min）+ 当场换健康号重提
降级 = 免费/低价档耗尽 → 升到高档（或反向：质检不过才升档）
```

**为什么先做它**：你的痛点是「生成贵 + 偶发失败」，这块能同时改善**成本与出片率**，且**零 UI 改动**。

### 第二优先：能力声明 + 自动路由

给视频 provider 加 `capabilities`（文生/图生/首尾帧/时长/分辨率），
把 `_resolve_provider_order()` 的「名字回退」升级为**按能力选路**。

### 第三优先：评分回写

把现有打分（`_render_score_results` 的数据）**写回**一个评分簿，
生成前按「同风格历史得分」选负面词/增益组合。**这是把你的「守护」从『静态规则』变成『会学习』的关键一步。**
