# 第一部分 项目本质

## 1.1 一句话

> **拾光剪影 = 一个人，维护着一个已经长成平台的三体系统。**

它起步是"本地短剧精剪工具"，但因为 AI 生成能力被不断接入，逐步长出了第二、第三个系统。
每个系统都有自己的**状态模型、时间观、失败观**，而它们之间没有统一的世界观 —— **这是所有技术债的总根源**，
不是"代码写得烂"，而是**架构演化速度超过了抽象速度**。

## 1.2 三层本质（它其实是三个东西）

| 层 | 本质是什么 | 真相源 | 规模 | 技术栈 |
|---|---|---|---|---|
| **① 剪辑器** | 一个 PyQt6 桌面视频编辑器，对标剪映的专业版 | `EditorModule._clips`（`editor_module.py:481`）+ RLock | `editor_module.py` 9,717 行 + lego 层 70,613 行 | PyQt6 + FFmpeg/MLT/PyAV 双内核 |
| **② 生成编排引擎** | 一个异构模型调度器（质量/成本/延迟/资源的实时目标函数） | provider 池 + 影子价格 λ + 质量先验 q̂ | `app/core/ai/` 41 文件 | 纯数值 + 轻量模型（规格书铁律） |
| **③ 创作台** | 一个节点式 AI 创作画布（React Flow） | Zustand `store.ts` 2452 行 | 真源 106 文件 / 38,740 行 | React 19 + TS + three.js |
| **粘合层** | 让三者互相看见 | HTTP 18765 + SSE `/host/agent/events` + `/host/timeline-snapshot` | `canvas_server.py` 3,273 行 | 自研桥 + token 鉴权 |

**关键事实**：三层之间**没有共享的数据模型**。剪辑器的 clip 变成画布的 node，再变回 clip，走的是
"盖章 + JSON 快照 + 整段替换"（`editor_canvas_link.stamp_clip:31` → `agent_replace_timeline_clips:8083`），
**而不是同一套领域对象**。

## 1.3 三条主线的世界观冲突（债的根因，本表是本文核心）

| 维度 | ① 剪辑线 | ② 生成线 | ③ 画布线 |
|---|---|---|---|
| **状态所有权** | `EditorModule._clips`（有锁、有快照、有原子替换） | 无长期状态，只有任务队列（`canvas_gen_jobs`） | Zustand store（前端内存 + localStorage） |
| **时间观** | **绝对时间轴**（帧/毫秒，可撤销，顺序确定） | **无时间**（一次请求一次响应，可取消） | **无时间**（图结构，拓扑序，可 undo/redo） |
| **失败观** | 失败要**可见**（用户要看到哪一帧坏了） | 失败要**降级**（六级降级，尽量出东西） | 失败要**诚实**（不假成功，宁可留空） |
| **变更粒度** | 单帧 / 单 clip（细，可撤销） | 整段生成（粗，原子） | 单节点 / 整图（中，可撤销） |
| **一致性要求** | **强**（音画必须对齐 ~280ms 冻结区） | **弱**（可重试、可换渠道） | **中**（节点连线必须自洽） |
| **测试方式** | 手工样片 + 帧级验证 | 仿真器（`simulator.py`，零成本可复现） | 纯函数单测（8 个 .test.ts，磁吸/序列化/映射） |

**冲突实例（不是假设，是实测）**：

1. 剪辑线要"声音和画面差不超过 280ms"，生成线要"能出片就行" → 于是音画纠偏被**冻结成不变量**，
   而生成线的降级（六级降级中的 `quality_down`）**可能产出音画不同步的成片**，两者靠人守。
2. 剪辑线失败要可见，生成线失败要静默降级 → 于是**同一个 `except` 该不该 `pass`，在不同模块有不同答案**
   （项目为此定了判定线，见 §3.3）。
3. 画布线用 `undo/redo` 图历史，剪辑线用 `_apply_action` 命令栈 → **两套撤销语义**，
   "画布改 → 回流到时间线"这一步的撤销语义**至今没统一**。

## 1.4 为什么必然产生债（四条结构原因）

| # | 结构性原因 | 表现（实测） |
|---|---|---|
| R1 | **抽象速度 < 演化速度**。三体系统本应有统一领域模型，但功能是竖切加的（用户要求"做一块接一块"），每次竖切都在旧结构上补一块 | `editor_module.py` 从 13,321 行（2026-08-11）→ **9,717 行**（已拆 8 个 mixin）→ 但**总规模仍在涨**，因为新增功能进了别的文件 |
| R2 | **单人带宽 ≈ 维护天花板**。428,670 行 / 1 人 → 任何"顺手统一"的动作都做不完，只能"谁动谁改" | 8 组同名类并存 52 组（`PluginManager` ×2、`Keyframe` ×3…） |
| R3 | **守卫缺失的地方必然复漂**。有守卫的地方很稳（冻结区 85 锁点、单文件 2000 行基线），没守卫的地方全漂了 | **双库：文档称 0 分叉，实测 23 分叉 / 副库缺 19 文件** |
| R4 | **AI 协作放大了产出，也放大了不一致**。文档提到"能力新增要四处接线，否则静默失效"（`agent_capability_catalog` 守卫就是为此而生） | 同一件事在 3-4 处描述：能力表、handler、action 白名单、前端 `agentPolicy.ts` |

## 1.5 本质结论

> 这个项目的技术债**不是质量问题，是结构必然**。
> 所以优化目标不该是"把代码写干净"，而该是：
> **给每一个会复利的口子装上守卫，让债的增长速度降到 0 或负。**
> 已有证据表明这条路走得通 —— 凡是有守卫的地方（冻结区、文件规模），项目都守住了。

# 第二部分 技术债台账

## 2.1 债务总览

| 级别 | 定义 | 数量 | 是否复利 |
|---|---|---|---|
| **S** | 会持续恶化，今天不堵明天更贵 | 3 | ✅ 复利 |
| **A** | 影响稳定性/可维护性，有明确危害 | 4 | 部分 |
| **B** | 造成理解成本，但可共存 | 4 | 缓慢 |
| **C** | 表面数字吓人，实际收益低 | 3 | ❌ 不必急 |
| **非债** | 看似是债，实为资产/有意设计 | 4 | — |

## 2.2 S 级（复利债，必须先堵）

### S1 · 双库副本无 CI 卡点 → 已复漂（**最高优先**）

**证据（实测 vs 文档）**：

| 项 | 项目文档 §6.7 声称 | 本文实测 |
|---|---|---|
| Phase 0-a 分叉合并 | ✅ "78 文件 MD5 100% 一致，漂移=0" | — |
| 当前分叉 | §2b 基线：分叉 22 / 副库缺失 16 | **分叉 23 / 仅主库 19**（口径细微差异） |
| Phase 3 CI 防漂卡点 | 未开始 | —— |

**分叉最大的文件**（主库已走远，副库落后）：

| 文件 | 主库 | 副库 | 差 |
|---|---|---|---|
| `magnetic/useMagneticDrag.ts` | 468 | 153 | **315 行** |
| `bridge.ts` | 1976 | 1704 | 272 |
| `store.ts` | 2452 | 2223 | 229 |
| `StudioPages.tsx` | 451 | 352 | 99 |
| `magnetic/MagneticEngine.ts` | 276 | 188 | 88 |

**为什么是 S 级**：Phase 0-a 花力气合并到 0，**现在又漂回 23 个** —— 这是"债复利"的实证。
`useMagneticDrag.ts` 差 315 行意味着**三段式手感、过冲、咬合阻尼这些核心手感，副库完全没有**。
一旦有人按副库改，主库的冻结核心会被回退。

**根因**：合并是一次性动作，漂移是持续过程。没有卡点，一次性动作必然被持续过程吃掉。

**解决**：见 §3.2 P0-1。

### S2 · `editor_module.py` 上帝类 9,717 行

**证据**：实测 9,717 行（`app/modules/lego/editor_module.py`），占全库 2.3%。
45 个 >1200 行文件占全部行数 **23.0%**；>2000 行 12 个（与 `_verify/check_file_size.py` 基线一致）。

**已有进展**：已抽出 8 个 mixin（`editor_ui_builder_mixin` 1387 / `editor_agent_panel_mixin` 2330 /
`editor_effects_mixin` 1053 / `editor_agent_runtime_mixin` 919 / `editor_ai_process_mixin` 524 /
`editor_ai_tools_mixin` 420 / `editor_export_panel` 455 / `ai_agent_panel` 682），
并沉淀了 7 个 AST 精确搬运脚本（`scripts/extract_*_mixin.py`）。

**为什么仍是 S 级**：拆分工具链已成熟，但**还差 5 段最重的没拆**（见 §3.3 P1-4 的具体行号区间）。

### S3 · 副库未被 git 跟踪 → 无回滚能力

**证据**：项目文档 §2b 原文——"副库 `vendor/AI-Canvas-tauri/` **未被 git 跟踪** ⇒ 改它之前必须先备份
（无法用 git 回滚，**项目曾因此在需要回退时无路可走**）"。

**为什么是 S 级**：这是**唯一一条"出事就不可逆"的债**。其他债最坏是返工，这条最坏是**永久丢失**。
本会话已有前车之鉴：3 张未跟踪的 PNG 被误删后**永久无法恢复**。

**解决**：见 §3.2 P0-2。

### A3 · 测试资产"虚胖"（真基线未知）

**实测**：

| 指标 | 数值 | 判断 |
|---|---|---|
| Python 测试文件 | 115 个 | — |
| `def test_` 总数 | 512 个 | 看着不错 |
| **测试行数占比** | **8.6%** | 偏低（健康项目通常 15-25%） |

| `tests/legacy/` | 44 文件，仅 print 就 1,548 处 | ⚠️ 历史回归，**多半已跑不通** |

**核心问题不是"测试少"，而是**：**没有人在跑。** 没有 CI（`stability_gate.py` / `arch_guard.py` / `frozen_zone_guard.py` 都是手动执行），
所以 512 个测试**是否还全绿是未知数**。这让"测试资产"变成了"测试负债"—— 它给人一种有保护的感觉，但没有。

### A4 · 主题盲区面（938 处内联样式 / 45 文件）

**实测**：`setStyleSheet(` **938 处 / 45 个文件**。

**不变量 #8** 已定规则："每新增一个内联控件必须回 `set_theme()` 补刷新"。
938 个点意味着**任何主题调整都需要人工核对 938 个位置** —— 这是典型的"规则正确但无法执行"。

**正确解法不是全量重写**（那是几周工作量），而是**先给新增装上守卫**（见 §3.4 P2-8）。

## 2.6 看起来像债，其实是资产（别动）

| 项 | 为什么是资产 |
|---|---|
| **冻结区 9 zone / 85 锁点** | 这是本项目最成功的设计。**证据**：凡是进冻结区的功能（音画纠偏、播放/退出、clip 变换、画布磁吸）**都没有回归**；而未进冻结区的模块反复改 |

| **12 个 >2000 行文件"只许减不许增"** | 守卫思路正确（基线冻结 + 只降不升），**这是本文推荐的模式** |

# 第三部分 优化方案

## 3.1 四条原则（先定原则，再排工期）

| # | 原则 | 理由 |
|---|---|---|
| P-1 | **只堵复利口，不追漂亮** | 债的绝对值不重要，**增长速度**才重要。堵住 S 级，债就开始净减少 |
| P-2 | **用守卫固化，不靠记性** | 项目已有证据：有守卫的地方守住了，没守卫的地方全漂了 |
