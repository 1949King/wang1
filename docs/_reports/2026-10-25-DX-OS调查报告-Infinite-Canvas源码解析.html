① 画布保存的「版本号 + 409 冲突」协议 补你的 G 缺口

它怎么做：保存时把「我基于哪个版本改的」一起提交，服务端版本不一致就返回 409，由前端决定是「覆盖」还是「接受远端」。

// canvas.js → saveCanvas()
body: JSON.stringify({
  title, icon, nodes, connections, viewport,
  client_id: CLIENT_ID,
  base_updated_at: Number(lastCanvasUpdatedAt || canvas.updated_at || 0)   // ← 关键
})

if (res.status === 409) {
  const remote = data.detail?.canvas || data.canvas;
  if (localCanvasDirty || saveCanvasAgain) {        // 本地还有没存完的改动
    lastCanvasUpdatedAt = remote.updated_at;            // 更新基线后重试
    saveCanvasAgain = true;
    return;
  }
  if (remote) applyRemoteCanvasData(remote);           // 否则接受远端，放弃本地
  return;
}

你的现状：全库无 revision / 409 / ETag / 乐观锁 —— 这是你自己审计记下的缺口。写入口靠 glue/policies.py 的 TIMELINE_WRITE_ENTRYPOINTS 登记册 + 棘轮收敛来「事后约束」，而 agent_policy.py:185 的 can_auto_retry 无运行时调用方，等于「写不重试」只靠机制缺失。

怎么落地：给 EditorModule._clips 的每条写入路径加一个 revision（整数或 updated_at 毫秒）。序列化快照时带 base_revision；保存时版本不匹配返回 409 + 当前快照。前端（store.ts）照它这套三分支处理。这套做法比 CRDT 便宜两个数量级，而你当前是单机，根本不需要 CRDT。

四个必抄的交互细节：

机制它怎么实现为什么重要
拖拽快照重算 _dragInitialTimeline 存拖拽起点的深拷贝，每次 mousemove 都从快照重算，绝不累加增量 避免浮点累加漂移 —— 拖 100 次位置不准是剪辑工具最常见的隐蔽 bug
滚动编辑
(Rolling Edit)		 拖两段接缝：左段变长、右段变短，总长不变；带物理约束（右段头部最多回退到 trimStart） 专业剪辑软件标准操作，比你单独拖左右边缘快得多
推挤物理 _applyCenterDragPhysics()：拖动整段时，后面的段被自动推开，不重叠 避免「拖到一半发现被挡住，还得先挪开别的」
时长只增不减 growTimelineIfNeeded() 只在需要时增长；getVisualDurationFrames() = 最远端 × 1.30 ×1.30 是视觉留白，让用户能把段拖出当前时长之外；只增不减防止误操作把时长缩到 0

还有个反常识的点值得你记：它不用 ResizeObserver，而是用 requestAnimationFrame 轮询 checkResize()，注释写「比 ResizeObserver 更可靠」—— 因为画布缩放时 ResizeObserver 回调时机不稳。

对你：你的剪辑时间线真相源是 EditorModule._clips，音画纠偏 ~280ms 在冻结区。上面「快照重算」和「×1.30 视觉留白」这两条是纯逻辑，可以独立验收益，不碰冻结区。
