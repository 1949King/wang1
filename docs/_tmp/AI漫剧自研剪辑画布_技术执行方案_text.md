AI漫剧「自研剪辑 + AI画布生成」系统
技术执行方案与参考建议（对话整理稿）
说明：本文件由前期多轮技术讨论整理而成，用于指导项目落地与选型决策。文中涉及的模型规格、显存占用、渲染耗时、价格量级等均来自公开信息汇总，模型改版与调价极快，所有数值请以各厂商官网及你自己的实测为准。
一、项目定位与总体结论
本项目由「剪辑模块」与「AI画布生成模块」双核心构成，其余模块（调控、体验、拓展）均为对两个核心的补充与体验完善，拓展模块包含MCP与插件等外挂功能。
核心结论：剪辑是确定性系统（同素材同操作同输出，失败可复现），AI画布是概率性系统（同提示词多结果，失败只能重试）。两者必须物理隔离，仅通过「不可变资产库」以资产指针方式流转，禁止在任务开始阶段互相引用对方的数据结构。
产能现实：按两天一小更（约1–2分钟成片）、五天一大更（约3–5分钟成片）的节奏，漫剧一分钟约需25–35个镜头，小更20–30镜、大更60–90镜。单机单卡在大更周必然积压，这是物理限制，必须接受「本地出草稿+云端出成片」的混合架构。
二、系统架构：双核心 + 调控 + 体验 + 拓展
2.1 两个核心的边界
剪辑模块：确定性操作，核心对象是轨道、片段、关键帧、时间码，用户心智是「精确到帧」，负责裁切、变速、插帧、稳像、调色、超分、字幕、音频对齐、导出。
AI画布模块：概率性操作，核心对象是任务、候选集、版本、seed，用户心智是「从一堆里挑一个」，负责文生视频/图生视频/首尾帧/参考图生成并产出候选集。
检验标准：删掉任一核心，另一个仍能独立编译、独立跑通；若不能，说明边界已渗漏。绝对禁止在剪辑面板放「重抽一次」按钮，也禁止在画布内拖拽时间线。
2.2 中间层：不可变资产库
数据流：分镜表(CSV/JSON) → AI画布按镜号生成N个候选+元数据 → 人工挑选入库为「镜头资产」（带版本号，原始产物不动，仅标记current）→ 剪辑只读资产库把选中镜头上轨 → 回写分镜表触发首尾帧重生成。两条硬约束：①剪辑模块永远不直接调用生成模型，它只知道「镜头ID+时长+分辨率」；②原始产物永不覆盖，每次重生成都是新版本v1/v2/v3，剪辑轨道上存的是asset_version指针。
2.3 调控模块：价值在「可复用」
把所有调控项收敛为「卡片+预设」：角色卡（正侧背三视图+固定seed+LoRA/参考图权重）、镜头卡（景别/运镜/时长/首尾帧锁定）、风格卡（画风/色调/颗粒/字幕样式）、批次策略（每镜出几条、废片淘汰规则、何时升级云端）。判断标准：能否存成预设、能否一键应用到50个镜头。
2.4 体验模块：效率的真正来源
优先级：①队列与断点续跑（价值超过其余所有项之和）；②失败分类与自动重试；③缩略图/预览缓存；④批量操作；⑤9:16与16:9双版本一次排队。明确不做：精细关键帧曲线、多机位、实时特效预览——精剪交给剪映/DaVinci，你的定位是「分镜表到粗剪的自动化流水线」。
2.5 拓展模块：MCP与插件是两个相反方向
插件=你的软件调用外部能力（新视频API/字幕引擎/超分），接口要小且死板（init/execute/cancel/report_progress），沙箱隔离，权限显式声明。MCP=外部Agent调用你的管线，暴露的是「动作」而非功能（submit_shot/pick_version/render_timeline/rerun_shot/get_queue_status），每个动作必须幂等并带task_id。拓展模块必须是纯外挂、绝不能成为核心依赖；检验标准是卸载全部插件后两个核心+调控+体验仍能完整跑出一条片子。
三、模块流转与回环机制
采用「顺序交接 + 受控回环」：画布生成后通过内部通信直接流转到剪辑细调优化，坏片段退回重生成。这与「工作开始阶段双向互相引用数据结构」是两回事，前者是标准流水线。真正会失控的是回环，必须把规矩定死。
3.1 先分清两种「坏」
凡是「呈现不好」留剪辑：时长/节奏、抖动/闪烁/色偏、分辨率/超分、音画不同步——都是确定性操作，不需重抽。凡是「内容错了」回画布：人物崩坏/身份漂移/穿模、首尾帧接不上/运镜方向反、提示词漏元素/风格跑偏、风控拒绝/模型报错。把这个写成代码里的failure_type枚举，禁止「未知原因→全部重跑」的兜底分支。
3.2 回传消息必须带五样
①shot_id+asset_version；②failure_type；③失败帧的时间码；④变更后的约束delta（新时长/画幅/首尾帧/景别）；⑤原始生成快照（seed/prompt/模型/步数，用于跳种子或升级策略）。其中约束delta最关键——若剪辑发现镜头实际需要8秒才接得上，画布必须拿到新需求，否则就是无效返工。
3.3 回环必须有界
单镜最大重试N次（建议3），超限后不再重跑而是升级策略（换模型/换参考图权重/拆分镜头/人工介入）。自动判坏只用于硬指标（黑帧、花屏、分辨率不符、时长不足、NSFW命中、解码失败）；审美与一致性判坏第一版必须人工确认。每次重试记retry_count与原因进资产表。
3.4 内部通信落地（单机版）
红线：视频文件永远走磁盘引用，不走进程间数据通道。推荐最朴素抗造方案：一张SQLite任务表（task_id/shot_id/job_type/payload_json/status/retries/error_code/时间戳/result_asset_id）+ 产物落盘 assets/{shot_id}/v{N}.mp4 + meta.json + 通信只传asset_id/路径 + 状态机轮询推进。不用Redis/消息队列。必须加幂等（同shot_id+约束哈希识别已在跑/已完成）与产物不可覆盖。
3.5 闭环漏洞
剪辑「细调」可能改变镜头语义前提（5秒对话裁到2秒口型对不上、横屏裁竖屏构图重心变），这类操作应触发「是否需要回炉」的二次判定。同时留一个「允许剪辑就地修复而不回炉」（局部inpaint/插帧）的出口，与回炉出口分开。
四、执行引擎选型：ComfyUI的取舍与开源替代
结论：不需要把ComfyUI作为后端执行引擎。ComfyUI对本项目只是「适配层」而非「引擎层」，其不可替代价值只有两点——新模型Day-0适配（仅几周窗口）和节点级缓存/局部重跑（后者你本就要在自研执行引擎里做）。
4.1 分层看自研边界
L1调度层（DAG/拓扑/增量执行/哈希缓存/队列/幂等/失败重试）：难度中低、几千行Python，必须自研，这是产品核心骨架。L2资源层（显存加载卸载/量化读取/多卡/张量生命周期）：坑密，尽量复用。L3模型适配层（dtype/量化格式/VAE分块/注意力kernel/音频VAE/MoE/采样器）：难度高且永无止境，绝对不要自研，对你的产品无差异化价值。
4.2 关于「挂后台才能用」的事实澄清
ComfyUI是C/S架构，前端只是静态HTML/JS，main.py才是引擎，REST+WebSocket通信。可用--api --disable-auto-launch纯headless启动（浏览器永不打开），或反代只放行/prompt /history /view /ws /system_stats并对/返回403。真正该担心的不是网页端，而是：①它是不完全可控的独立进程；②几十GB环境与依赖漂移；③许可证不确定。
4.3 推荐Runner架构（纯后端，无后台黑盒）
画布前端 → 参数抽象层schema（你的、稳定、版本化）→ 自研执行引擎（DAG或线性链/哈希缓存/队列/幂等/资产版本/失败枚举）→ Runner接口（统一submit/poll/cancel/result+失败枚举）→ DiffusersRunner(默认,进程内import即调)/DiffSynthRunner(低显存/长视频/去闪烁)/SGLangRunner(需隔离或高吞吐)/CloudRunner(本地跑不了直接甩云端API)。候选：diffusers首选(pip装、进程内pipe、Apache2.0、已有Wan/H3/CogVideoX/HunyuanVideo/LTX等pipeline)；DiffSynth-Studio为低显存补充(内置FP8量化/磁盘卸载/IP-Adapter/LoRA/去闪烁/长视频扩展)；SGLang/vLLM-Omni为进程隔离Worker；ComfyUI降级为第4顺位兼容保险。
4.4 关于把引擎代码copy进项目
不建议vendoring（内嵌第三方整仓）：视频推理栈改动最频繁，内嵌等于你自承担全部升级成本且无该领域上下文；许可证义务不因拷贝消失；体积与CI成本高。更稳做法：精确锁版本+一键重建容器/devcontainer（解决环境漂移，代价比内嵌小两个数量级）+加一层自己的Runner适配器（换实现只改一个文件，这才是真正可控）。
4.5 ComfyUI若确需保留的治理清单
独立venv/容器+精确锁死PyTorch/CUDA/xformers/ComfyUI版本；systemd/supervisor守护+健康检查探针+失败重启告警；日志结构化串联prompt_id↔shot_id↔asset_version；超时强杀防「永远卡在99%」；显存隔离独占GPU；自定义节点白名单制并留档来源/版本/许可证；禁止outbound联网。必须以feature flag控制——关掉它系统照样完整跑通，这是检验它有无反客为主的唯一标准。许可提示（非法律意见）：ComfyUI主程序协议公开资料说法不一，第三方节点各自为政，须去pinned版本仓库读LICENSE并留档；对外分发需过法务，仅自建服务器跑风险低得多；diffusers与Wan权重(Apache2.0/MIT)更干净。
五、模型选型与分档
5.1 文本侧（性能释放取决于显存）
单卡24GB：Qwen 27B级稠密版INT4或同档GLM中尺寸，是消费级显卡上能力与速度最均衡的一档。双卡24GB/单卡48GB+：上32B–35B MoE的Q5/Q6量化。4卡以上/H100/国产集群：GLM大尺寸版或Qwen超大MoE的4bit量化，需SGLang/vLLM多卡并行工程。提醒：激活参数少不等于省显存（MoE所有专家权重都要加载）；协议比分数重要（逐字核对license）；性能释放一半取决于推理框架，选模型不如先选好框架。
5.2 视频侧（漫剧胜负手是角色一致性+原生音频）
可部署最均衡：阿里Wan系列（协议干净、生态最全、门槛低5B可跑720P、中文提示词好），但单次时长是硬伤（本地普遍5–15秒）、多数无原生音频。漫剧最对口：MiniMax H3（原生音画同出、多参考图角色锁定、首尾帧控制强），但社区商用许可非Apache/MIT。其他：HunyuanVideo 1.5（写实/二次元一致性强、时长短显存高，适合精品镜头）；LTX（速度最快、低显存可跑、画质让步，适合分镜打样）；SkyReels-V3/CogVideoX-3（参考图一致性与首尾帧控制，适合电商与转场）。
工程结论：跨镜头人物一致性不能指望模型，必须在工作流层解决（角色资产卡三视图+固定seed → 参考图生视频/IP-Adapter/LoRA → 一致性专项模型）。你的自研软件核心价值应落在「资产管理」上，而非「调用哪个模型」。
六、硬件配置方案（2万预算）
铁律：显存容量>算力>架构代次。16GB是本地跑视频的分水岭，24GB才是稳定量产线。2026年显卡溢价严重，2万买不到5090级工作站，以下为「整机含显卡2万」的现实选项。
方案A（均衡主力，推荐）：RTX 5070 Ti 16G + i7/Ryzen7 + 64GB DDR5 + 2TB NVMe + 850W金牌，能跑H3 720P/Wan14B Q4，上限720P。方案B（偏画质）：RTX 5080 16G + 缩水CPU/内存，同显存推理更快但扩展差。方案C（堆并行）：2×RTX 5060 Ti 16G + 64GB + 大电源，双卡独立跑不同镜头吞吐近翻倍，需会配多卡。方案D（不建议生产机）：2×二手3090 24G，矿卡重灾区无保修。
必守：别省内存和硬盘（32GB底线/64GB稳，1TB起步2TB从容，路径全程不用中文空格）；必须N卡；电源预留30%余量；价格以当天询价为准。
七、云端/本地混合调度策略
路由器不是「哪个好就用哪个」，而是成本×时效×难度三维打分，据此把镜头自动分档：L1草稿（本地最快模型低步数）；L2常规单人对话固定机位（本地主力H3/Wan）；L3困难多人物/复杂运镜（本地先试一次失败即升云端）；L4关键首集/高潮/宣发（直送云端高配，不在本地试错）；L5特殊打斗/流体/长镜头（云端专项模型）。关键原则：L4不要在本地上试错——本地跑三次废片的时间+电费+等待往往比直接云端更贵。
路由器六个工程细节：①入站归一化（下载第一件事就转码成house format，剪辑模块从此只认这一种，这是混合方案能否长期维持的分水岭）；②幂等与去重（约束哈希含角色卡版本/prompt/时长/画幅）；③模型常驻vs冷启动（常驻主力+LoRA切风格，队列加截止时间优先）；④云端生命周期管理（记result_expires_at做到期预警，task_id/provider/model_version落库）；⑤预算闸（物理闸不可绕过：每集硬上限+单笔上限）；⑥熔断与降级（连续N次5xx/风控摘除M分钟，本地连续OOM自动降分辨率或切云端）。可选对冲(hedge)：截稿压力极大的L4镜头本地云端同时提交谁先合格用谁，只对距截稿不足X小时的镜头开并设上限。
八、云端API测试方案
第一步（0成本）：先用免费额度跑通「提交→轮询→下载→入库→落库元数据」链路，重点验证异步状态机、结果文件过期时间（最阴险的坑，须记result_expires_at）、限流码429、审核拒绝错误码、返回规格是否一致。
第二步：建立本地baseline——同20条镜头先本地跑一遍记录耗时/显存/废片率，之后每个云端数字都用「相对本地」表达。第三步：测试集必须是你自己的素材（不用官方demo prompt），抽20–30条覆盖难度梯度L1静态对话/L2简单运镜/L3双人互动(测穿模率)/L4动作流体/L5跨镜一致性(测角色漂移，漫剧生死线)，同一套输入喂给各家。
第四步：记录字段——成本（标价/实际扣费/重试次数/单可用镜头成本=标价×平均生成次数，务必乘重试次数）、性能（排队/推理/下载/P50/P95）、质量（硬指标+人工软指标）、稳定性（失败类型/同因失败/卡死率）、合规（审核拒绝率/误杀率）。第五步：预算闸物理化（单家硬上限300–500元、代码写死、超了自动停），加余额告警webhook。
关于「会不会崩」：99%出在长时间批量跑，需单开耐久测试——连续提交8–12小时观察显存泄漏/OOM自愈/队列堆积；拔网线杀进程测断点续跑；并发从1拉到上限；处理「永远卡99%」的超时强杀。顺序：视频模型优先（决定产能和账单、差异极大，测出「哪类镜头走哪家」分档表），LLM往后放（是commodity，一天测完）。
九、技术债务治理
AI生成代码的债形态特殊：同一件事被写五遍每遍不一样、且没有一行你真正读懂。原则是先体检定位、避免盲目重构导致系统瘫痪。
9.1 体检工具
ruff/pylint（未用变量/重复代码）、vulture（死代码）、radon（圈复杂度/可维护性）、pydeps/importlinter（依赖图/跨模块import，验证模块边界是否被打破）、mypy --strict渐进式（假类型注解）、pip-audit+pipdeptree（漏洞/依赖冲突）、cloc（代码量涨但功能没涨=纯债）。跑完先不修，只出报告，找Top5「改了收益最大」的点。
9.2 三个大概率已烂且必须优先修
①资产schema漂移（最高优先级，会炸数据）：给schema加版本号+单向迁移层（read升latest/write只写latest）+旧产物离线迁移备份，迁移脚本必须有反向验证。②错误处理三种方言混用（raise/return None/print/sys.exit）：收敛为统一Result风格或自定义异常hierarchy，禁止业务层捕获裸Exception。③环境不可复现：精确锁版本+一键重建容器/devcontainer。
9.3 修债节奏
别停更，每个周期拨15–20%时间还债雷打不动；只修「路径上的债」；童子军规则（改一个函数顺手修它和邻居的类型注解与错误处理）；任何重构必须先有测试（重构前写），无测试的重构在AI项目里等于闭眼拆承重墙。
十、剪辑模块体验优化
只盯一个指标：从分镜表定稿到粗剪成片的人均分钟数。按投入产出比：①代理剪辑proxy workflow（收益超其余之和——时间线跑低码率代理，导出静默换回原片，全程只认指针不污染架构）；②缩略图胶片条+波形（入库时后台异步抽帧）；③键盘优先+快捷键一张纸并锁死（防AI改UI顺手改掉快捷键，需回归用例）；④命令模式撤销重做+自动保存+崩溃恢复三件套一起上；⑤批量操作与批量重跑。明确不做精细关键帧/多机位/实时特效——每加一个高级交互先问：剪映能否30秒做完？能就别做。
十一、AI剪辑功能定位
判断正确：达不到Agent水平就当功能亮点，不强行引入。很多被叫「AI剪辑」的东西根本不需要大模型——用确定性算法就能做、成本极低、可控可复现不幻觉：静音/爆音检测自动切空白、语音转字幕自动打轴（漫剧刚需）、镜头时长按BGM onset对齐节拍、横转竖安全区检测、废片自动标记（黑帧/花屏/过短/无声）。做成「一键优化」按钮即可，与概率性的AI画布明确区分。真正的Agent剪辑设观察指标，等它能稳定完成「把第12镜换成角色B版本并重剪这一场」这种带意图任务再引入。
十二、给「AI编程小白」的落地纪律与排期
执行者靠AI写代码，复杂度必须压到最低否则三个月变屎山。纪律：①用中文写清规格（输入输出/目录结构/错误码）再让AI写代码；②一次只加一个功能跑通再下一个；③强制写端到端测试（给定分镜表CSV能否产出可播mp4）；④每天git commit（崩了能回退）；⑤文件路径/编码/API密钥三类人工逐行review。
模块边界物理化：四个顶层目录对应四个模块，目录间禁止跨import（用lint卡死）；两核心唯一通道是assets/的JSON schema。落地顺序（先纵向切片再横向铺满）：①正向通路跑通一个镜头（分镜表→画布→入库→上轨→导出mp4）；②手动回环（人工标坏→一键重排→新版入库→轨道指向新版）；③失败分类+策略表；④自动判坏（仅硬指标）+有限重试；⑤可观测性（每镜生命周期卡）。自动回环放最后，过早自动化只会得到一台高速生产废片的机器。
画布后端打磨四件事（前端UI已出，后端按序）：①异步任务状态机+持久化队列（断电重启接着跑）；②产物不可变+版本指针；③幂等；④可观测性。验证顺序（两周）：diffusers原生pipeline把一个模型从schema跑到mp4落盘→同期做L1执行引擎→换DiffSynth-Studio对比显存/耗时/废片率→再决定要不要第三个Runner与图执行引擎（很可能你只需线性任务链+条件分支）。
先跑通再自研：在你的软件成型前（大概率半年以上），先用ComfyUI工作流+FFmpeg批处理脚本+Excel分镜表这套土办法跑通产能。先验证业务，再决定要不要自研。
