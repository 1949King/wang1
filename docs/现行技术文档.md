## 1. 产品定位与北极星

### 1.1 是什么

**拾光剪影**是 PyQt6 桌面端「**短剧精剪 + AI 导演台画布**」。活路径只有两条：

- **剪辑模块**（时间线编辑、预览/播放、导出）
- **AI 画布**（导演台节点、生图/生视频、含智能体与画布数字人）

运营/发布、短剧筛选已**彻底删除**（2026-09-15），不再作为迭代主题。

### 1.2 北极星（当前）

> 竖切可重复：**导演台（含数字人）→ 分镜图 → 入轨精剪**。智能体只做「确认后执行」的遥控器，**不默认一键成片**。

### 1.3 四条专注轨（资源配比）

| 轨 | 配比 | 内容 |
|---|---|---|
| **N 剪辑** | ~30% | 时间线手感、建议入轨、冻结区回归 |
| **P 画布** | ~35% | `vendor/shiguang-canvas` 节点/落盘/诚实生成 |
| **A Agent** | ~25% | 白名单、确认后拉片/去水词/批量；剪辑↔画布 round-trip |
| **D 数字人** | ~10% | 画布 `digitalHuman` 节点（TTS+形象；口型成片有模型再接） |

### 1.4 明确不做

- 不重写时间线架构（真相源永远是 `EditorModule._clips`）
- 不换壳：Wails / OpenTake-Tauri 宿主 / tldraw 替换主画布 / Dify 当剪辑运行时
- 不默认「一键全链路成片」当主入口
- 不恢复短剧筛选/账号运营的功能体（仅保留接口壳）
- 不做 D1–D4（向量库 / 智能 B-Roll / 万能 EDL / 完整的转场库）

## 2b. UI 归属真相 & 依赖升级纪律（2026-09-25 实测固化）

### UI / 前端到底有几套？（消除「双前端」歧义）

**不是两个前端，是「一个 Qt 桌面壳 + 一份 React 画布源码 × 两个宿主」**：

| 角色 | 位置 | 说明 |
|---|---|---|
| Qt 桌面壳 | `app/main_qt6.py` + `app/modules/lego/`（PyQt6） | 主程序：剪辑 / Agent / 素材等 |
| **画布前端（唯一源码）** | `vendor/shiguang-canvas/`（102 文件 / 38,707 行） | React + Vite，画布功能只在这一处实现 |
| 宿主 A（默认） | `engine=shiguang` | WebEngine **嵌入** Qt6 主程序 |
| 宿主 B | `engine=tauri` → `vendor/AI-Canvas-tauri/` | **独立桌面进程**，Qt 不嵌入 WebEngine |

切换开关见 `app/core/canvas_runtime.py`（`get_canvas_engine()`，兼容历史取值 `aic`/`ai-canvas`）。
通信：`canvas_server.py`（端口 18765）+ SSE；Tauri 侧有 `/host/tauri-closing` 回调。

⚠️ **副库 `vendor/AI-Canvas-tauri/`**：它本身是一个 git 仓库（第三方仓库的克隆），
但**项目侧的 `src/libtv/` 副本此前从未被跟踪** ⇒ 改它无法回滚，项目曾因此在需要回退时无路可走。
**已于 2026-09-25 补齐**（详见 §2c.4）。双库漂移基线（2026-09-25 收敛后）：
**分叉 0 / 副库缺失 7**（硬编码在 `_verify/check_canvas_dual_repo.py`，
**判据是「不超过基线」，不是「等于 0」**）。收敛经过见 §2c.5。

### 依赖升级纪律（体检结论，2026-09-25）

**分级规则：patch 直接打 · minor 需回归验证 · MAJOR 一律禁止盲升。**

⛔ **钉死的包（有硬约束，禁升）**：
- `numpy 1.26.4` —— **numba 0.64 要求 numpy<2.1**，且 opencv / torch 的 ABI 建立在 numpy 1.x
  ⇒ 升 2.x 会连锁炸整条 AI 链。**任何涉及 numpy 的升级提案先查 numba 与 opencv 约束。**
- MAJOR 禁升清单：`moviepy 1.0.3`（API 大改，视频合成主链路）· `opencv-python-headless 4.x` ·
  `librosa 0.11` · `mediapipe 0.10` · `anthropic 0.25`；前端 `vite 6` · `typescript 5` ·
  `vitest 2` · `@vitejs/plugin-react 4` · `three 0.185`

✅ **已打补丁**（本机 .venv312）：`cryptography 50.0.1` · `imageio 2.37.4` · `Pillow 12.3.0` ·
`requests 2.34.2`；画布 npm：`@xyflow/react 12.11.6` · `react/react-dom 19.3.0` · `zustand 5.0.15`

⏸ **待评估（需专项回归）**：PyQt6 三件套 · transformers · dashscope · onnxruntime · aiohttp

⚠️ **npm audit 5 个漏洞（1 critical + 1 high）全在 vitest 工具链** —— 全是 devDependencies
（不进发布包），触发场景是「本地 vitest UI server 监听」（本项目只用 `vitest run`）；
修复需 `vitest 2→5 + vite 6→8` 双 major 跳跃 ⇒ **刻意不修**（收益 << 破坏面）。
如需修：`npm audit fix --force`，之后必须重跑 vitest + tsc + build + 双库校验。

## 2c. 粘合层契约 + 提交前 11 道卡点（2026-09-25 建立 / 2026-10-09 扩至 11 道并入库）

### 2c.1 粘合层契约（`app/core/glue/`）

**要解决的问题**：三条主线（剪辑 / 生成 / 画布）世界观不同，原本靠**散落的字段字面量**
互相看见 —— `canvas_node_id` / `canvas_kind` / `canvas_title` 在三处硬编码，
无 schema 版本、无校验、无溯源，任一处的字段改名都会**静默失效**。

**做法**：新增契约层（`app/core/glue/`，纯标准库、零项目依赖），把跨线字段收拢为单一来源：

| 模块 | 职责 |
|---|---|
| `schema.py` | 跨线字段集合（`LINK_KEYS` 等）· 别名表 · `GlueProvenance` 溯源 · `GLUE_SCHEMA_VERSION` |
| `convert.py` | 三向转换：`clip_to_glue` / `glue_to_outbox` / `canvas_payload_to_glue` / `glue_to_clip_patch` / `glue_to_clip_row` |
| `validate.py` | 桥边界校验：`validate_envelope` / `validate_canvas_payload` / `validate_clip_row` |
| `policies.py` | **三条世界观冲突的显式策略**（见下） |

**铁律**：
1. **字段名保持原样** —— `canvas_node_id` 等被前端与已有工程文件依赖，改名＝破坏兼容。
   契约层的价值在「收拢 + 校验 + 溯源」，不在「重命名」。
2. **只新增不改行为** —— 由 `_verify/check_glue_contract.py` 的**等价性断言**保证：
   契约层输出必须与 `editor_canvas_link` 既有实现**逐字段一致**，不等价即失败。
3. **契约在桥边界强制**（`canvas_server.py` 的 `/ingest` 与 `/host/timeline-snapshot`）——
   该文件不在冻结区，因此可以在**不动前端一行代码**的前提下给跨线传输上约束。

### 2c.2 三条主线世界观冲突 → 显式策略（`glue/policies.py`）

| 冲突 | 现象 | 消解方式（契约，非重构） |
|---|---|---|
| ① **失败观** | 剪辑线要失败可见 / 生成线要静默降级 / 画布线要诚实失败 ⇒ 同一个 `except` 该不该 `pass` 各有答案 | 把判定线变成**可执行数据**：`SILENT_EXCEPT_UI_WHITELIST`（可接受）/ `SILENT_EXCEPT_REVIEW_TARGETS`（须补日志）/ `SILENT_EXCEPT_FROZEN_PENDING`（需先解冻），由 `silent_except_verdict()` 判定 |
| ② **时间观** | 剪辑线用命令栈、画布线用图 undo/redo ⇒ 跨线写入的撤销语义不统一 | `TIMELINE_WRITE_ENTRYPOINTS` 声明**唯一合法写入入口**（`agent_replace_timeline_clips` / `_apply_action` / `_add_clip_to_timeline` / `batch_add_clips` / `_delete_clip` / `set_clips_writer`）；`may_assign_clips_wholesale()` 限定整段赋值只允许出现在 `editor_module.py` |
| ③ **一致性观** | 剪辑线要求音画 ≈280ms 强对齐，生成线可降级出片 ⇒ 降级产物可能破坏不变量 | `cross_lane_acceptance()`：**默认只收完整交付**（`ACCEPT_DEGRADED_MAX = 0`）；降级产物须显式 `degraded_ack=True` 才准入，且准入后自动打 `glue_degraded` / `glue_origin` / `glue_lane` 标（可筛选、可回滚） |

> 设计取舍：**不统一三条线，只统一它们的交界处**。一次性统一等于三条线全部重写，
> 会全面触碰冻结区，且单人带宽下必然烂尾（详见
> `docs/_reports/2026-09-25-项目本质与技术债分析及优化方案.md` §3.5 反模式清单）。

### 2c.3 提交前 11 道卡点（`scripts/precommit_gates.sh`，**已入库**）

> **2026-10-09 结构性改动**：卡点逻辑此前**只存在于 `.git/hooks/pre-commit`**，而 `.git/`
> 不入库 ⇒ ① CI 拿不到（所以 `ci.yml` 只能另写一套，两边必然漂移）② 换机器即丢
> ③ 改了什么没人能 review。现已搬到 `scripts/precommit_gates.sh`（入库），
> `.git/hooks/pre-commit` 降级为 3 行 shim。支持 `--all`（全量，CI 用）与增量两种模式，
> **判定标准完全一致**；node / ruff / `.venv312` 缺失时显式跳过并说明（不误报成门禁失败）。
> 全量体检单入口：`bash scripts/check_all.sh`（门禁→pytest→覆盖率棘轮→vitest→run_all_checks）。

| # | 卡点 | 脚本 | 拦什么 |
|---|---|---|---|
| ① | ruff 逐文件存量棘轮 | `scripts/ruff_gate.py` | 新文件 >0 违规 / 已有文件超基线（**只减不增**） |
| ② | ruff format --check | `ruff` | 仅警告，不阻断 |
| ③ | 冻结区守护 | `scripts/frozen_zone_guard.py` | 9 zone / 90 锁点的哈希漂移 |
| ④ | 稳定性门禁 | `scripts/stability_gate.py` | 裸except / 静默except / product-print / 未定义名（存量入基线，只减不增） |
| ⑤ | 粘合层契约 | `_verify/check_glue_contract.py` | 跨线字段与既有实现不等价 |
| ⑥a | 架构守护 | `scripts/arch_guard.py --scan app` | 分层纪律（UI 层不得写业务逻辑） |
| ⑥b | **双库一致性** | `_verify/check_canvas_dual_repo.py` | **副库副本漂移（防复漂 —— S1 的核心卡点）** |
| ⑦ | 前端三卡点 | tsc 棘轮 ≤37 · vitest · 质量棘轮 | 画布改动只有这一道（⑦a/⑦b/⑦c） |
| ⑧ | 单文件规模守卫 | `_verify/check_file_size.py` | 单文件超 2000 行（存量冻结，只减不增） |
| ⑨ | 路由 mixin 属性 | `_verify/check_canvas_route_attrs.py` | `cs.*` 静默失效 |
| ⑩ | **pyqtSignal 参数类型**（2026-10-09 新增） | `_verify/check_qt_signal_types.py` | typing 泛型别名进 `pyqtSignal` ⇒ **整模块 import 崩**（ruff/tsc 看不见，见 V4.41.0 缺陷①②） |
| ⑪ | **素材不出域**（2026-10-09 新增） | `_verify/check_provider_egress.py` | `SHIGUANG_NO_EGRESS` 硬约束失效 |

> 覆盖率棘轮（`_verify/check_coverage.py`）**不在 hook 里** —— 它要多跑一遍全量 pytest
> （约 4-5 分钟），放 hook 会让每次提交都卡 5 分钟。它挂在 `check_all.sh` 与 CI 的
> unit-tests job 上。语义：逐文件「已覆盖行数只增不减」，见该脚本文件头。

> ⚠️ 双库卡点必须 `always_run: true`。理由：副库 `vendor/AI-Canvas-tauri/` 在主仓被 gitignore，
> 它的改动**永远不会出现在主仓的暂存清单**里，靠 `files:` 过滤会永不触发 ⇒ 卡点形同虚设。

**两个必须知道的坑（实测）**：
- `stability_gate.py` 的 `SKIP_DIRS` 原先漏了 `app/temp` 等 gitignore 草稿目录，
  导致写一次临时脚本就带进几十条 print 违规、把门禁顶红 —— **631 项新增违规里 564 项来自草稿目录**，
  门禁因此长期处于红状态、无人执行。已在 `SKIP_DIRS` 中补齐草稿/缓存目录。
- `arch_guard.py` **必须传 `--scan`**，无参时只打印 usage 空转（exit=0 但一次都没扫）——
  属「看起来有守卫、实际没守卫」，钩子里已固定为 `--scan app`。
- **`ruff` 卡点 2026-10-07 换实现：整文件判定 → 逐文件存量棘轮。** 原实现是
  「对暂存文件整体 `ruff check --no-fix`」，其**意图**（增量严格）没错，但**整文件判定**
  踩到结构性缺陷：白名单（`app/modules/lego` / `app/core` / `ai_tools`）下
  **167 个文件带 1016 处历史违规**（`modules.py` 76 · `editor_effects_mixin.py` 55 ·
  `editor_module.py` 50 …），而这些文件最后一次提交多在 2026-09-21/22，
  **早于本 hook 诞生（09-26）**，从未被门禁扫过 ⇒ 任何对它们的正当改动都会被
  与本次无关的存量债拦死。极端例子：冻结区的 `editor_module.py` 有 50 处存量违规
  ⇒ **等于核心文件永远无法提交**（本轮固化时实测撞上，`git log` 亦无任何
  `--no-verify` 绕过记录，历史做法是「把要提交的文件先清干净」，但那对
  9479 行冻结文件不现实）。
  **现改为**按 `stability_gate.py` 的同一范式做**逐文件基线棘轮**：
  `scripts/ruff_gate.py` + `docs/knowledge/ruff_gate_baseline.json`。
  **门禁没有放松** —— 新文件 >0 违规、或已有文件超过其基线，一律 `fail=1`；
  用**逐文件**（而非全局计数）是为防「A 文件修 3 处、B 文件加 3 处」此消彼长。
  `--update` 还自带反后门约束：抬高既有权、或为 HEAD 中不存在的新文件建基线，
  都必须显式 `--force`。
  体检/重设：`python scripts/ruff_gate.py --all | --report | --update [--force]`。

### 2c.4 副库回滚基线（修正 §2b 的表述）

§2b 原文「副库 `vendor/AI-Canvas-tauri/` 未被 git 跟踪」**表述不够精确**。实测：

- 副库**本身就是一个 git 仓库**（第三方仓库 `github.com/Tenney95/AI-Canvas-tauri` 的克隆，
  1 个上游提交 `6cb0e46`，分支 `master`）。
- 真正未跟踪的是 **`src/libtv/`**（89 文件，项目侧画布副本）—— 此前从未 `git add`，
  这才是「改它无法回滚」的真实范围。

**已于 2026-09-25 补齐**：提交 `ed3ea53` 把 `src/libtv/` 纳入跟踪，
`git diff` / `git checkout` 实测可用。

> ⛔ **该子仓库 origin 是第三方仓库，绝对不要 `git push`。**
> ✅ 提交时若报 `Author identity unknown`，用主仓身份临时注入：
> `git -c user.name=$(git -C .. config user.name) -c user.email=$(git -C .. config user.email) commit ...`
>
> ✅ **同目录 eslint 已豁免 `src/libtv/**`**：该目录是移植进来的画布源码，
> 在本仓库实测有 228 条规则冲突（`no-explicit-any` 120 / `no-unused-vars` 46 / react-hooks 32 …），
> 且集中在 `CanvasShell.tsx` / `Stage3D.tsx` / `store.ts` —— 这些文件**在主库是冻结区**。
> 为满足宿主 lint 去改它们会变成大重构、触碰冻结等价物、并让双库漂移更严重。
> 按「移植代码沿用来处纪律」的边界，本目录不参与宿主 lint。
> **⚠️ 订正（2026-09-26 实测）**：此处原文写「主库侧由 shiguang-canvas 自己的 eslint 负责」，
> 但实测**真源 `vendor/shiguang-canvas` 并没有 eslint 配置**（无 `eslint.config.js` / `.eslintrc*`，
> `package.json` 里也没有 `lint` 脚本）⇒ **画布真源目前根本没有 lint 门禁**。
> 详见 §2f。
> 另：`scripts/pre-commit` 的 eslint 调用已加 `--no-warn-ignored`，
> 否则被忽略文件会触发 warning，而 `--max-warnings=0` 会把它升级成失败、堵死提交。

2. `*.test.ts`（5 个）—— 宿主已有 166 个自有测试，引入主库测试会带来规则冲突与失败用例，收益低。

而该文件当时属「仅主库有」⇒ 半收敛会留下 **TS2307 断引用**。
**教训：收敛副本必须一次补全，分批同步会在中途留下断引用。**

### 2c.6 副库「永远报分叉」的真因：autocrlf 改写行尾（2026-09-25）

收敛后双库校验仍报 `canvasVersion.ts` 分叉，**但两文件文本逐行相同、解码后 md5 一致**。
实测根因：

| 位置 | 行尾 |
|---|---|
| 主库 `canvasVersion.ts` | 31 × LF，0 × CRLF |
| 副库同一文件（工作区） | 31 × CRLF，0 × LF |
| 副库索引 / HEAD | 31 × LF（正确） |

副库 `core.autocrlf = true` ⇒ `git checkout` 把索引里的 LF 写成工作区 CRLF；
而 `git status` **比较前会归一化**，所以显示「干净」——
于是出现「**守卫常红、git 说没事、看不出为什么**」。

> 这类「守卫常红且归因不明」正是守卫被忽视的成因（与技术债报告里
> `stability_gate` 因草稿目录噪声而长期红、`arch_guard` 无参空转属同一类病）。

**修法（三步，顺序不能反）**：
1. 副库设 `core.autocrlf false`（字节忠实）
2. 副库加 `.gitattributes`：`src/libtv/** -text`（永不转换行尾，其它机器/克隆同样生效）
3. 用索引内容重建工作区 —— ⚠️ `git checkout -f` **无效**（stat 缓存让它判定"干净"而跳过重写），
   必须**先删除工作区文件再 `git checkout`**，git 才会从索引重建。

**结果**：字节级分叉 1 → 0；**卡点实证：制造漂移→exit=1 拦住；还原→exit=0 恢复**。

## 2d. 冷启动优化 + PyQt6↔mediapipe DLL 陷阱（2026-09-25）

### 2d.1 冷启动从 ~55s 降到 ~1s（热态实测）

**真因（实测，非推测）**：`DependencyChecker.check_dependencies()` 为了「检查依赖」，
用 `__import__(import_name)` **把 16 个包真的导了一遍**（必需 9 + 可选 7），
而调用方 `_check_environment` **只用到其中一项**（PyQt6 是否存在）—— 其余 15 个导完即丢。

| 包 | 导入耗时 | | 包 | 导入耗时 |
|---|---|---|---|---|
| transformers | 33.7s | | mediapipe | 4.3s |
| torch | 11.2s | | 其余 | 均 < 1s |

**修法**：`__import__` → `importlib.util.find_spec`（只**定位**模块，不执行模块代码）。

| 方式 | 16 个包总耗时 |
|---|---|
| `__import__`（旧） | **27.04s** |
| `find_spec`（新） | **0.02s**（**1226×**） |

**附带第二处**：`check_gpu()` 原先进 `import torch`（热态 2.56s，冷态更久）只为问「有没有 GPU」。
改为**优先 pynvml**（0.06s），不可用才回退 torch；设备名实测一致
（`NVIDIA GeForce RTX 4060 Laptop GPU`）。

**实测对比**：

| 指标 | 优化前（冷态） | 优化后（热态） |
|---|---|---|
| 「检查运行环境」耗时 | 54s | **0s** |
| 首个日志 → 应用启动成功 | ~55s | **1s** |
| 首个日志 → 画布就绪 | ~60s | 5s |

> 口径提醒：优化前是**冷态**（闲置 11h）、优化后是**热态**，两次不可直接相减。
> 但机制上确实去掉了 **27s 的真实导入执行**（上表实测），冷态收益只会更大。

**行为等价性**（改前必须证明）：两种方式对 16 个包的判定逐项比对，15 项一致；
唯一差异 `mediapipe`（find_spec=True / \_\_import\_\_=False）**恰恰是新行为更准确** —— 见下。

**排查开关**：置 `SHIGUANG_STRICT_DEPS=1` 可恢复旧的「真导入」探测。

### 2d.2 ⚠️ 陷阱：PyQt6 与 mediapipe 的 DLL 加载顺序冲突

**实测（顺序敏感）**：

| 顺序 | 结果 |
|---|---|
| 裸 `import mediapipe` | ✅ |
| `import PyQt6` → `import mediapipe` | ❌ `ImportError: DLL load failed while importing _framework_bindings` |
| `PyQt6.QtCore` / `QtGui` / `QtWidgets` → mediapipe | ❌ 均失败 |
| **`mediapipe` 先 → `PyQt6` 后** | ✅ |

与 cv2 / torch / easyocr / transformers 的任意组合都正常 ⇒ 冲突只在 PyQt6。

**当前架构没有踩到**：姿态解析走**独立子进程**
（`app/core/ai/pose_extract_service.py:4` 明示「以独立子进程运行 pose_worker.py」，
用 `subprocess.run([sys.executable, worker, ...])`），子进程不加载 PyQt6 ⇒ 正常。

**但历史实现踩到了**：`check_dependencies` 在**主进程内**（PyQt6 已加载）真导 mediapipe
⇒ 必然失败 ⇒ 把它误报成「未安装」（其实是装了的，`0.10.21`）。
改用 `find_spec` 后，这个**误诊顺带消失了**。

> 结论：**将来若要把姿态推理搬进主进程，必须先解决此 DLL 冲突**
> （候选：保持子进程隔离 / 调整导入顺序 / 换 nvidia-ml-py 与 mediapipe 版本组合）。

### 2d.3 新发现（待处理）：提示词封面图失败未缓存

## 2e. 画布「引擎未安装」误报的修复（2026-09-25）

### 现象
画布顶栏常驻指示点显示「**引擎未安装**」（`CanvasShell.tsx:819` → `missing`），
但本机其实**装了两份完整 ComfyUI**。

### 根因（两层，第二层是隐性坑）

**① 检测层** —— `comfy_provider._find_engine_dir()` 原来只查 4 个固定位置
（`SHIGUANG_COMFY_HOME` → `<项目>/thirdparty/ComfyUI` → `<项目>/comfyui` → `app/core/ai/comfyui`），
未覆盖实际的安装位置 ⇒ 误报。

**② 拉起层** —— `_find_engine_python()` 原来只认 `<引擎>/python_embeded/` 与 `<引擎>/venv/`；
**秋叶整合包的解释器在引擎的上一级**（`ComfyUI-aki-v1.7/python/python.exe`）⇒ 命中不了
⇒ 静默回退到拾光剪影自己的 venv（**没有 ComfyUI 依赖**）⇒ 就算目录指对了**也拉不起来**。

### 修复（`app/core/ai/comfy_provider.py`，非冻结区）
- 新增 `_common_install_candidates()`：补「桌面下 `ComfyUI*/ComfyUI`」与「项目同级目录」两类常见位置
  （只做一次 `listdir`，**不递归全盘**）
- 新增 `_own_python_candidates()` / `_has_own_python()`：统一「引擎自带解释器」的判定口径，
  覆盖官方 `python_embeded` / 源码版 `venv` / **整合包 `../python`** 三类布局
- `_find_engine_dir()`：在候选中**优先返回自带解释器的那一个**（只有它才拉得起来）；
  选中的目录记 INFO 日志（避免「不知道用的哪一份」）
- `_find_engine_python()`：复用 `_own_python_candidates()`，与上半边口径一致

### 实测（本机）
```
修复前：engine_dir=None            has_engine=false  ⇒ 画布显示「引擎未安装」
修复后：engine_dir=...\ComfyUI-aki-v1.7\ComfyUI
        engine_python=...\ComfyUI-aki-v1.7\python\python.exe（存在）
        has_engine=true           ⇒ 提示变为「目录已就绪，导入工作流时会自动拉起」
```
自动选中了**秋叶整合包**（本机唯一自带解释器的那份）。
另一份 `D:\_comfy_compare\ComfyUI`（源码版，无自带解释器）被正确排在其后。

> 若你的 ComfyUI 装在别处：设环境变量 `SHIGUANG_COMFY_HOME` 指向引擎目录即可，
> 该路径优先级最高，无需改代码。

## 3. 架构分层与真相源

### 3.1 分层铁律

```
Application (main_qt6.Application)
  └── MainWindow + ModuleRegistry（懒加载 LEGO 模块）
        ├── ui_widgets / modules/lego    # UI：只负责渲染、交互、事件分发
```

- **时间线真相源 = `EditorModule._clips`**。
- 禁用 `AppState`、孤儿 `ExportRenderer`（已清理，见[12-app_state](#附录)历史说明）。
- 轨索引用 `find_track_index_by_type`，禁止硬编码 `track == 1`。

### 3.3 双内核调度（`app/core/editor_scheduler.py`）

| 操作 | 倾向内核 |
|---|---|
| preview / probe | LIGHTWEIGHT（PyAV） |
| clip / export / multi_track / ai_clip | PROFESSIONAL（FFmpeg/MLT） |

### 3.4 渲染三级 fallback

```
RenderManager.render()
  ├─ ① C++ 引擎（NVENC/QSV/AMF 硬件加速）
  ├─ ② FFmpeg CLI（subprocess）
  └─ ③ CPU 回退（moviepy/纯计算）
       └─ 失败自动降级，需保留兼容回退
```

- 导出统一走 `RenderManager` + `editor_export`，禁止在 UI 里硬拼复杂 FFmpeg 命令。
- GPU 检测统一走既有 `GPUDetector`/`HardwareDetector`，禁止重复造硬件检测逻辑。

## 7. 编码规范（浓缩）

- 命名：类大驼峰；方法/函数 `snake_case`；私有成员 `_` 前缀；常量 `UPPER_SNAKE_CASE`；变量见名知意。
- 导入：标准库 / 第三方 / 本地项目模块三段分组；优先 `from app.xxx`；禁冗余导入与循环导入。
- 分层：UI 只渲染；core 处理数据与状态；MainWindow 调度；不跨层硬编码调用。
- 注释：类与核心方法必须说明职责；关键逻辑加行内注释；不写废话。
- 异常：禁止裸 `except: pass`；必须记日志或给用户清晰提示；必填/格式校验、按钮防重复点击覆盖。
- 日志：core 用 `logger`，禁止裸 `print()`。
- 弹窗：必须绑定 `parent`；关闭后刷新父界面；耗时任务后台线程 + 信号回主线程更新 UI。
- 状态：登录/权限/版本/用户归 auth 模块统一管理。
- 修改原则：**最小侵入、最大兼容**；保留旧路径或 fallback；不擅删原代码、不私增无用文件。
- 验证：改 Python 后至少 `py_compile` 或对应测试；改导出/渲染后验证 C++/FFmpeg fallback。

## 11. 代码审查标准（浓缩）

- **正确性** 🔴 — 边界/索引/位置校验（反例：播放头在端点切出 0 秒空片段）。

- **性能** 🟡 — N+1、重复全量扫描、每次全量重建 UI。
- **测试** 🟡 — 核心路径（剪切/删除/撤销、AI 入口）有测试。

五步流程：自审 → pre-commit 自动拦 → PR 填清单 → Reviewer 五维审 → CI 双门禁全绿合并。
