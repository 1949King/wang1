## 二、Wave 0 — 地基与收口

### #14 并行工作区收口（最高优先，不做则后续全部带病）

**现状核实**：`git status` 显示 **67 个未提交文件**，归属另一条并行线（app 侧视频编辑 e2e +
本机视觉模型线）。其中：
- `stability_gate` 报 **34 项新增违规**：`app/test_video_editing_e2e.py`（29 项 print-statement）、
  `app/core/canvas_shot_vision.py`（3 项 swallow-except）、
  `app/core/capability_handlers_editor_skills.py`（1 项）、`app/core/reference_breakdown.py`（1 项）。
- tsc **新增 2 个错误**（基线 37 → 39）：`src/storyNodes.tsx`（接 `getVisionModel()`）、
  `src/plugins/infinite-compat.tsx`（`PluginRuntimeAI` 签名补参）。

**要做的事**：
1. **`app/test_video_editing_e2e.py` 的处置（规划初稿此处判断有误，已核实修正）**：
   该文件是 **e2e 测试脚本**，位于 `app/`（= `SCAN_ROOT`）下，而 `SKIP_DIRS` **按目录名跳过**，
   它不在任何 SKIP_DIRS 里 ⇒ 被当 product 扫。它的 `print` 是**正常输出**
   （e2e 脚本靠 stdout 汇报断言结果），改成 logger 是把测试脚本改成产品代码的形状。
   **正解：把该文件移出 product 树**（挪到 `_verify/` 或 `tests/` 等不在 `SCAN_ROOT` 下的位置），
   **而不是**扩 `SKIP_DIRS` 塞文件名进去 —— 后者会把「豁免」变成常规操作，
   违背该门禁自己注释写的「让门禁只对 product 代码说话」初衷。
   （前提：先 grep 有无其他脚本 import 它，挪位置要同步改引用。）
2. `canvas_shot_vision.py` 等 3 处 `except OSError: pass` —— 按项目判定线补日志
   （判定线原文：「UI 绘制 `pass` 可接受；状态机/资源路径 `pass` 须 `logger.debug(..., exc_info=True)`」）。
   这 3 处在 `canvas_shot_vision` 里属「读取/解析失败后回退正则」路径 ⇒ 须补。
   ⚠️ 补日志用 `logger.debug(..., exc_info=True)`，**不能用 `except OSError: pass`** ——
   项目记忆明确记着「`except OSError: pass` 会被 stability_gate 拦 ⇒ 别 `--update` 洗掉」。
3. 修 2 个 tsc 错误（`storyNodes.tsx` / `infinite-compat.tsx`，都在非冻结文件，可直接改）。
4. 分线提交：视觉模型线一个 commit、e2e 脚本线一个 commit，各自带自己的 CHANGELOG 条目。

**验收**：`bash scripts/precommit_gates.sh` 14 道全绿（不再需要 `--no-verify`）。

**纪律红线**：
- **不得跑 `stability_gate.py --update` 洗基线**，不得放宽 tsc 基线 37。34 项逐条定性，不是「数字变小就行」。
- **门禁机制本身不动**（`SKIP_DIRS` / `_RULE_*` 一律不改）—— 改门禁比挪脚本风险大得多。
  若最终判定确需加豁免规则，必须：① 只按**目录/文件模式**加、不加具体文件名；
  ② 加 `--selfcheck` 反例验证（照抄 `check_canvas_selectors.py` 的自检范式）；
  ③ CHANGELOG + 提交消息双份登记理由。

## 三、Wave 1 — 母版层（P0，本规划主体）

### 借鉴 #1 四张表上下文引擎 ★ 最大项

**竞品做法**（Invideo，联网核实）：持有 `cast` / `locations` / `look` / `rules` 四张表，
**每次新生成前先与既定上下文比对**，脸错 / 细节破 / 光照不 match 都触发重生成。

**我们的现状核实**：
- `cast`表 **已有 80%**：`app/modules/lego/character_management_module.py` 的 `CharacterStore`
  已有 `face_params`（第 69 行 schema）/ `avatar_url` / `export` / `import_file`。
- `locations` / `look` / `rules`：**全缺**。grep `scene_library` / `StyleBible` / `look_table`
  在 `app/` 与画布侧**零命中**。
- 有零散素材但未成表：`aestheticPresets.ts`（审美预设）、`lightingPresets.ts`（24 灯位）。

**落地设计**：

| 表 | 关键字段 | 存储 | 状态 |
|---|---|---|---|
| `cast` | id / 名称 / `face_params` / `avatar_url` / 体型 / 声音 / **`identity_block`（固定身份块，逐字不改）** | 复用 `CharacterStore` | 已有，加字段 |
| `locations` | id / 名称 / 参考图集（3–5 张）/ 光照方向 / 色温 / 空间尺度 | **新建** `AssetStore` | 缺 |
| `look` | 调色板 / 镜头语言 / 颗粒感 / 光照约定 | **新建** | 缺 |
| `rules` | 禁生成清单（字幕/商标/法务声明标「图形」不走视频模型）/ 负面清单 / 命名规范 | **新建** | 缺 |

**落地要点**：
1. 新建 `app/modules/lego/asset_master_store.py`（**非冻结区**，三表 CRUD + 导入导出，
   照抄 `CharacterStore` 的形状）。
2. **新文件不塞进冻结区**：`store.ts` / `CanvasShell.tsx` 已顶体积红线
   （3251/3229 行、2526/2513 行），判定逻辑一律外置。
3. 比对闸门分两期：**P0 只做结构**（四张表 + 读写API + 面板入口），**P1 才做生成前比对**

4. `look` 表的审美值**需要拍板**（见文末待拍板项）。

### 借鉴 #2 Elements 元素抽象

**竞品做法**（LTX Studio）：角色 / 物体 / 地点抽成可复用元素，
**任何后续镜头引用它们时不再重新生成**。

**落地**：与 #1 同批做，因为共用 `AssetStore`。
在节点层引入 `element_id` 概念（挂到 `SourceData` / `ShotData` 上），
生成前先查元素命中⇒ 复用而非重新生成。

**红线**：这是**新增一条引用通道**，不是替换现有 `upstreamRefs`。
两条通道必须物理隔离（否则又是「同一语义两条链路」——V4.43.20刚清过这个坑）。

### 借鉴 #7 固定身份块（铁律，零成本）

**竞品做法**（pixmind 实操指南）：每条prompt 顶部贴**同一个**身份描述块，**逐字不改**
——因为同义词的分词结果不同，改写就漂。

**落地**：`cast.identity_block` 字段 + 生成时自动前置 + 面板上标「逐字不改，勿手改」。
成本极低（一个字段 + 一处拼接 + 一处提示），**但收益是所有一致性问题里最便宜的一环**。

---

### 借鉴 #8 漂移改源卡不重抽

**竞品做法**（invideo）：角色漂移时**修源角色卡而不是重抽该 panel**，改完存回上下文，
后续 panel 自动继承修复。

**落地**：依赖 #1。抽卡闭环的 `gen_critic` 检出坏区时，**先查是否命中元素/身份块漂移**，
命中则回写 `cast` 表而非直接抽卡。

**红线**：必须保留「直接重抽」路径（漂移不命中身份块时用），不许把两条路合成一条。

## 四、Wave 2 — 批次与护钱包

### 借鉴 #6 批次概念 + 一致性悬崖

**竞品做法**（creatortribune 专业流程）：**每批 8 条** + 每批之间查一致性悬崖 +
**末尾统一 harmonization**（DaVinci color match / CapCut 预设同步）。

**现状核实**：`app/core/ai/draw_book.py` 的 `DrawBookStore` 有
`record_draw` / `recommend` / `fingerprint` / `stats`，**但无 batch 维度**
（grep `batch` 仅命中 1 处，是内部的 batch 操作变量，不是业务概念）。

**落地**：
1. `DrawBookStore` 加 `batch_id` 维度 + `stats` 加「批内漂移度」。
2. 前端抽卡面板加「开一批 / 收一批」两个动作，批大小默认 8（可配）。
3. 批收尾钩子：建议接#11 的光流检测（未做前只报漂移度，不阻断）。

**红线**：`draw_book` 的 `fingerprint` 是抽卡去重与推荐的锚点，
**加batch 维度不得改动 fingerprint 的计算口径**（否则历史账本全部失效）。

### 借鉴 #5 生成幂等签名

**竞品做法**（Factory Agent）：**幂等签名**防「批准的动作被跑两次、扣两次钱」。

**现状核实**：`store.ts` 已有 `stage3dApplySeq` / `stage3dCastSeq` 这类 seq 消费范式，
**本质就是幂等签名的雏形**，但**生成类动作（生图 / 生视频 / 3D 渲染）没有这层保护**。

**落地**：
1. 新建 `app/core/ai/idempotency.py`（非冻结区）：`signature = sha256(action + nodeId + params + userApprovedAt)`。
2. 后端 `canvas_routes_post.py` 的生成类端点统一在入口查签名，命中则返回上次结果。
3. 与#6 的 `batch_id` 共用同一套批次上下文。

**红线**：签名**必须包含 params 全文**（不能只hash action + nodeId，
否则用户改了 quality 会被误判成重复请求而拒绝执行）。

### 借鉴 #3 确定性阶段列布局

**竞品做法**（Factory Agent）：节点按阶段分列
（上传素材→种子→分镜→参考→视频段→音频→合成→审→成片），
**所以 Agent 建的项目「从左往右读就是一条生产线」**。

**现状核实**：画布侧**无通用布局引擎**（grep `dagre` / `elkjs` 零命中），
只有磁吸系统自带的空间分析（`magnetic/SpatialAnalyzer.ts`、`FloatingToolbar.tsx` 里的
`autoLayout` / `autoPlace`）。

**落地**：新建 `src/stageColumns.ts` 纯函数（9 个阶段列 + 碰撞检查），
新建画布 / Agent 建项目时按阶段列落位。
**不改造磁吸落位**（磁吸有 40+ 条冻结不变量，动不得）——阶段列是**新建画布的初始布局**，
与磁吸是两层，落位后再交给磁吸接管。

### 借鉴 #9 嵌入相似度过滤

**竞品做法**：对参考图集算图像嵌入余弦相似度，低于阈值标「需人工复审」
（行业数据称可减 60%+ 人工复审量）。

**现状核实**：本机已有相关基础设施 —— `app/core/ai/aesthetic_analyzer.py`
（含 `analyze_frame` / `analyze_media` / `analyze_clip`）、
`content_classifier.py`、`local-vision-models` 端点。**但没有跨图嵌入比对**。

**落地**：
1. 用本机视觉模型出参考图嵌入 → 存`cast` 表。
2. 生成结果出嵌入 → 与 `cast` 算余弦相似度 → 低于阈值标红。
3. **门槛**：0.28 高度对齐 / 0.25–0.28 可用 / <0.25 淘汰是行业经验值，
   但**必须先用我们自己的素材实测校准**，不能直接照搬。

**红线**：**必须标注「仅为参考」**，且提供手动覆盖开关——
余弦相似度不是审美标准（竞品评测明确警告「配错颜色的图在 CLIP 上可能仍排很高」）。

### 借鉴 #10 Agent 自我清理

**竞品做法**（BLOCKLORE）：审计整张画布、删掉不在活跃流水线里的节点、重连剩余元素，
**并汇报删了什么、连了什么**。

**现状核实**：`app/core/canvas_routes_get.py` 有 `canvas-settings` 端点，
但**无「活跃流水线」的定义**——这正是本项的核心缺口。

**落地**（依赖 #4）：先定义「活跃」判据（有下游消费 / 被锁定 / 在批次内），
再做审计 + 清理 + 汇报三段。**汇报必须先于执行**（用户确认后才动）。

## 六、Wave 4 — 质检（最后做）

### 借鉴 #11 光流一致性检测

**竞品做法**：首尾帧光流场剧烈不连续跳变 = 模型中途放弃；
OpenCV 逐帧光流方差设阈值，可滤掉大部分崩坏片段。

**现状核实**：`aesthetic_analyzer.py` 已有 `analyze_frame` / `analyze_clip`，
但**无光流计算**。OpenCV 是否在依赖里**待核**（`.venv312` 需实测）。

**落地**：新建 `app/core/ai/optical_flow_qc.py`（非冻结区），
帧间光流方差 → 阈值判定崩坏 → 供 #6 的批收尾调用。

**为什么放最后**：① 需要 OpenCV（可能新增依赖）；② 它是**过滤器不是决策器**——
没有 #1 的四张表和 #6 的批次概念，光流检测出来的「崩坏」没有处置路径。
