# 拾光剪影 · 代码审查标准与流程（Code Review Standard & Process）

> 文档版本：V1.0 ｜ 制定：代码审查专家 ｜ 适用：所有自研 Python 代码（`app/modules/lego/`、`app/core/`、`ai_tools/` 等）
> 配套文件：`ruff.toml`、`.pre-commit-config.yaml`、`.github/workflows/quality-gate.yml`、`.github/PULL_REQUEST_TEMPLATE.md`

---

## 1. 为什么需要这套机制

我们**不是没有规范**——`docs/开发者文档.md` 早已写明 PEP 8、类型注解、"函数不超过 50 行"、提交规范、甚至"代码审查要点"。但规范停留在文档里，**没有任何工具或流程去执行它**，于是出现如下"规范与代码脱钩"的真实事故（均来自本项目）：

| 事故 | 现象 | 本应避免的方式 |
|---|---|---|
| 同名方法定义两遍 | `_cut_clip`/`_delete_clip` 各写两遍，Python 后者覆盖前者，导致一套带撤销栈的完整实现变成**死代码**，工具栏实际跑的是残缺版 | 静态检查 `F811`（重复定义）一行就能标红 |
| 撤销栈没接上 | 生效的剪切/删除/粘贴从不写历史栈，Ctrl+Z 永久失效 | 审查"关键路径是否记录可回滚"即可发现 |
| 剪切无边界校验 | 播放头停在片段最开头时切出"0 秒隐形空片段" | 审查"输入/位置是否校验边界"即可发现 |
| 单文件 7465 行 | 文档规定函数 ≤50 行，但 `editor_module.py` 一个方法就 130 行、整文件超 7000 行 | 增量拆分审查 + 体量告警 |

**结论**：质量参差的根因不是人，而是**机制缺位**——没有"提交前卡点 + 合并前门禁 + 标准化审查清单"。本文件与 4 个配套文件共同补全这套机制。

---

## 2. 机制架构（三层）

```
┌─────────────────────────────────────────────────────────┐
│ ① 制度层：本文件 + PR 审查清单（定义"什么算好代码"）      │
├─────────────────────────────────────────────────────────┤
│ ② 工具层：ruff.toml + .pre-commit-config.yaml             │
│          → 提交前本地自动拦截重复定义/未用导入/语法错       │
├─────────────────────────────────────────────────────────┤
│ ③ 门禁层：quality-gate.yml（CI）+ ci.yml（既有测试）      │
│          → 合并前自动跑静态检查 + 测试，不绿不准合         │
└─────────────────────────────────────────────────────────┘
```

**渐进式原则**：门禁只拦**新增代码**的致命/高价值问题；历史存量问题靠 `ruff.toml` 的 `per-file-ignores` 对巨型文件先放宽，随重构逐步收紧。**不要求一次性还清技术债**，避免团队因"几千条告警"而放弃机制。

---

## 3. 严重级别定义

每条审查意见必须标注级别，让作者一眼知道轻重：

| 级别 | 含义 | 合并策略 |
|---|---|---|
| 🔴 **阻断** | 正确性/安全/数据风险，或 CI 门禁直接标红 | **必须修复**，否则禁止合并 |
| 🟡 **建议** | 可维护性/性能/测试缺口，不立即出错但会腐烂 | 应尽量修复；争议时由 Reviewer 拍板 |
| 💭 **完善** | 风格/注释/可读性，纯主观收益 | 可选，鼓励但不强制 |

> 每条意见都要写清 **"为什么"** 与 **"建议改法"**，让被审者学到东西，而非只被挑错。

## 4. 分维度审查清单

Reviewer 按以下 5 个维度逐条过。每条都附**本项目真实反例**与**怎么查**。

### 4.1 正确性（Correctness） 🔴
- 是否真的做了它该做的事？边界条件是否覆盖？
- **反例**：剪切时播放头在片段端点 → 切出 0 秒空片段。✅ 应有 `if local <= 0 or local >= clip_dur: 提示并 return`。
- 怎么查：读核心逻辑分支；对"位置/索引/时间"类输入，确认有上下界校验。

### 4.2 安全性（Security） 🔴
- 用户输入是否校验/转义？路径拼接是否防穿越？有无凭据硬编码？
- **反例**：`eval()` 解析片段数据、`open(user_path)` 未校验 `..` 穿越。
- 怎么查：搜 `eval/exec/os.system/subprocess` 拼接；查 `open()`/`pathlib` 入参来源。

### 4.3 可维护性（Maintainability） 🔴/🟡
- 有无**重复定义导致覆盖**？（最致命的一类）
  - **反例**：`_cut_clip` 定义两遍 → 后者覆盖前者，前半套代码永不可达。✅ 提交前 `ruff` 的 `F811` 必拦。
- 命名是否自解释？有无"看起来像两回事其实重复"的方法？
- 单函数是否过长（文档规范 ≤50 行）？过长建议抽私有方法。
- 有无死代码 / 调试残留（`print()` 调试、`TODO` 无跟进）？
- 怎么查：跑 `ruff check`；对同名方法做全文检索确认唯一。

### 4.4 性能（Performance） 🟡
- 有无 N+1（循环内查库/查引擎）、重复全量扫描、频繁全量重建 UI？
- **反例**：每次操作都 `self._clips` 全量遍历 + 重建整个时间线控件。
- 怎么查：看循环体是否含重量级调用；UI 刷新是否可局部。

### 4.5 测试（Testing） 🟡
- 重要行为（剪切/删除/撤销、AI 分析入口）是否有测试？
- 怎么查：改了核心逻辑，对应 `tests/` 是否更新；无法单测的是否有集成验证说明。

## 5. 审查流程（五步）

```
① 开发者自审 ──→ ② 提交前 pre-commit 自动拦 ──→ ③ 开 PR + 填审查清单
        │                │                          │
        └────────────────┴──── 任一步失败都先修 ────┘
                                                ↓
                    ④ Reviewer 按本文件 5 维度 + PR 模板逐项审
                                                ↓
                    ⑤ CI 双门禁（quality-gate 静态检查 + ci.yml 测试）全绿 → 合并
```

| 步骤 | 动作 | 卡点 |
|---|---|---|
| ① 自审 | 作者按 §4 自查，确认无 🔴 | 人肉 |
| ② pre-commit | `git commit` 时 ruff 自动跑，修不了则**阻断提交** | 工具（本地） |
| ③ PR | 填 `.github/PULL_REQUEST_TEMPLATE.md` 清单 | 流程 |
| ④ Reviewer | 至少 1 人按清单审，意见标 🔴/🟡/💭 | 人肉 |
| ⑤ 门禁 | `quality-gate.yml`（静态）+ `ci.yml`（测试）必须全绿 | 工具（CI） |

**合并门禁**：任一 🔴 未解决、或 CI 任一门禁标红 → **禁止合并**。

## 6. 质量门禁与渐进策略

- **规则集**（`ruff.toml`）：先开 `E9`(语法) + `F`(Pyflakes，含 `F811` 重复定义/`F401` 未用导入) + `B`(bugbear) + `C4`/`PIE`(冗余写法) + `RUF100`。
- **巨型文件渐进豁免**：`editor_module.py`、`timeline_widget.py`、`video_editor/*` 暂仅保留 `E9`+`F`（致命），其余规则随重构逐步打开。
- **收紧节奏**：每个 Sprint 末，从某个文件的 `per-file-ignores` 移除 1–2 个规则，把它纳入严格检查。新文件/新目录一开始即严格。
- **格式**：先用 `ruff format --check` 仅报告（不阻断），待团队习惯后改为自动格式化。

---

## 7. 角色与节奏

- **Author**：对自己的代码先过 §4 自审。
- **Reviewer**：至少 1 名；关键模块（剪辑/AI 引擎/内核调度）建议第二人强制评审。个人主导项目可由"作者 + Agent 结对"完成。
- **节奏**：结合现有 Sprint 制度——每个 Sprint 有"代码评审会"统一过 🔴 存量；日常 PR 走 §5 轻量流程。

## 8. 工具安装与常用命令

```bash
# 本地静态检查（开发期自测，不等 CI）
pip install ruff
ruff check                        # 按 ruff.toml 扫描自研目录
ruff check --fix                  # 自动修可修项
ruff format                       # 格式化

# 提交前自动卡点（每个仓库装一次）
pip install pre-commit
pre-commit install

# CI 侧无需本地装，quality-gate.yml 用 ruff-action 自带环境
```

CI 失败时在 PR 行内会看到 `ruff` 的具体文件/行/规则号（如 `F811`），点开即定位。

## 9. 与现有项目约定的衔接

- **版本与变更日志**：凡功能/修复改动，**必须同步** `app/version.py` 与 `docs/CHANGELOG.md`（既有约定，已列入 PR 模板 🔴 项）。
- **Sprint 断点回归**：Sprint 2 规划的 `ai_clip_flow` / `smart_editing_engine` / `ai_integration` 三处"致命断点"，每次相关 PR 必须附带"已消费真实引擎输出"的验证，审查时重点核对。
- **开发者文档**：本文件是 `docs/开发者文档.md`"代码审查要点"的**可执行细化版**，二者冲突以本文件为准。

## 10. 附录：真实案例复盘（早有机制会怎样）

以本次修复的剪辑模块三处问题为例，说明机制如何拦住：

| 问题 | 机制拦截点 | 若没有机制 |
|---|---|---|
| 同名方法重复定义（死代码） | `ruff` `F811` + PR 模板 🔴 第一项 | 静默覆盖，功能悄悄失效数月 |
| 撤销栈未接入 | §4.3 可维护性 + §4.1 正确性审查 | 用户发现 Ctrl+Z 无效，无法回滚 |
| 剪切无边界校验 | §4.1 边界条件审查 | 切出 0 秒空片段，时间线错乱 |

**一句话总结**：规范写进文档只是第一步，**把它变成"提交时被工具拦、合并前被门禁卡、审查时有清单对照"**，质量才能稳定，而不是靠某次人工排查碰巧发现。
