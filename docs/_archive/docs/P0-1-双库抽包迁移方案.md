# P0-1 双库抽包迁移方案

> 目标：让「导演台画布」代码只存在一份（单一事实源），两个宿主（web / tauri）都引用它，从根上消灭"复制即技术债"。
> 作者身份：项目策划与决策人 · 本方案为决策文档，供人审查 + DeepSeek/Cursor 执行。
> 生成时间：2026-09-09 · 基于本次真机勘察（非记忆），所有事实均已验证。

---

## 0. 一句话结论

**导演台画布源码应抽成独立包 `@shiguang/libtv`，用 pnpm workspace 承载，两个宿主都以依赖方式引用；执行前必须先做「依赖对齐」和「分叉合并」两个前置，不能直接上 workspace，否则会在漂移的地基上再叠一层复杂度。**

我的判断（对决策负责）：**不采用** git submodule（对 AI 编辑器不友好）、**不采用**继续硬链接 + CI 守护（治标不治本、Windows alias bug 缠身）、**采用** pnpm workspace + 抽包（单一依赖、无需发布、业界标准、可逐步演进）。

---

## 1. 现状核实（本次真机验证，非记忆）

### 1.1 两套副本的关系

| 宿主 | 路径 | 定位 | 接入方式 |
|---|---|---|---|
| 主画布（web） | `vendor/shiguang-canvas/src` | Qt WebEngine 加载的自研导演台 | 整仓即这套源码 |
| 智能体画布（桌面） | `vendor/AI-Canvas-tauri/src/libtv` | Tauri 桌面里的「拾光导演台」视图 | `App.tsx` 里 `lazy(() => import('./libtv/App'))`，切换到 viewMode==='libtv' 时加载 |

- 两目录文件列表**完全一致**（`src` 与 `libtv` 名目同步）。
- **libtv 是活路径，不是孤儿**（已确认 `App.tsx` 接线）。

### 1.2 漂移已发生（这是 P0-1 最硬的证据）

本次用 MD5 逐文件对比，结果：**62 个文件一致，16 个文件已分叉**。

分叉清单（核心文件已加粗）：

> 结论：漂移不是"潜在风险"，是"已发生的事实"。继续靠同步运维，只会越漂越多、最终两个产品分裂。

### 1.3 依赖版本不一致（抽包的前置障碍）

| 依赖 | shiguang-canvas | AI-Canvas-tauri | 影响 |
|---|---:|---:|---|
| react | ^19.0.0 | ^19.2.6 | peer 范围冲突 |
| three | ^0.185.1 | ^0.184.0 | 3D API 可能不同 |
| zustand | ^5.0.3 | ^5.0.5 | 一般兼容 |
| @xyflow/react | 12.6.0 | 12.6.0 | 一致 ✓ |
| vite | 6.2 | 8.0 | 构建行为不同 |
| typescript | 5.7 | 6.0 | 类型检查不同 |

### 1.4 结构特征（决定抽包粒度）

- 两库均`无 path alias`（无 `@/`），全部**相对 import**，`src`/`libtv` 是自包含单元。
- `bridge.ts` 是**环境耦合点**：主画布连 Python 后端，tauri 侧连 Tauri API——抽包时必须抽象为可注入接口。
- AI-Canvas-tauri 另有 `src/store`（20 slice）、`src/components`、`src/services` 等**独有部分**，不在共享范围，勿动。
- 已知硬伤：**Rolldown-vite 在 Windows 的盘符 `is_absolute` 解析 bug**，导致 vite alias 指向共享源码会崩；历史上一度用硬链接 workaround。

## 2. 第一性原理：先回答"该不该抽、抽到哪"

抽包不是目的，"两个宿主共享同一套导演台"才是目的。动手前必须回答两个战略问题：

1. **这两套画布未来是否长期保持一致？**
   - 若主画布会往 Qt WebEngine 走、桌面画布会往 Tauri/原生走，两者注定分叉 → **只抽「无环境依赖的纯逻辑层」**（magnetic/store/riggedHumanoid/plugins），保留各自 App/UI 壳。
   - 若定位是"同一套导演台，两种外壳" → 抽**整个 src**（含 UI 骨架），宿主只留薄壳。

   我的建议：**先按"纯逻辑层 + UI 骨架上移、宿主壳下放"的折中抽法**——把环境耦合的 `bridge.ts`/`main.tsx`/入口 `App.tsx` 留在宿主，其余抽走。这是风险最低、又解决 90% 漂移的做法。

2. **真相源定谁？**
   - 主画布 `shiguang-canvas/src` 是 AGENTS.md 认定的"主路径"，定为**真源**。
   - 16 个分叉文件逐个 `git diff` 复核，少数（如 bridge.ts 的 tauri 侧改动）需要在抽包前先合并回真源。

## 4. 推荐方案：分四阶段（每阶段可独立验证、可回滚）

> 铁律：**每完成一阶段，两侧 `build` 必须通过，否则停在该阶段修，不进入下一阶段。** 不追求一次到位。

### Phase 0 — 分叉合并 + 依赖对齐（前置地基，最优先）

**目标**：先消除"已发生的 16 文件漂移"和"依赖版本分裂"，让两库回到一个干净一致的基线。

步骤：
1. 逐文件 `git diff` 16 个分叉文件，以 `shiguang-canvas/src` 为真源，把 tauri 侧特有的有效改动（尤其 `bridge.ts`）合入真源，其余回填。
2. 对齐 3 个 libtv 实际使用的核心依赖到同一版本：
   - react → `^19.2.x`（两侧统一）
   - three → `^0.185.x`（新，向后兼容 0.184 的 API）
   - zustand → `^5.0.5`
3. 同步根下 `package-lock.json`，两侧 `npm run build` 通过。

**验证**：两库 build 通过 + 两库 `src`/`libtv` 重新 `MD5` 一致性 100%。
**回滚点**：此阶段不改变任何 import 结构，`git checkout` 即可回滚。

### Phase 1 — 建 workspace + 抽独立包

**目标**：把共享代码物理抽成 `packages/libtv`。

步骤：
1. 在 `vendor/` 建 `pnpm-workspace.yaml`，声明 `packages/libtv`。
2. 新建 `vendor/packages/libtv/`，`package.json` 声明 `name: "@shiguang/libtv"`、`private: true`、`peerDependencies`（react/three/zustand/@xyflow/react 用宽范围）。
3. 把 `shiguang-canvas/src` 内容迁入 `packages/libtv/src/`（宿主专属 `main.tsx`、`index.html`、`vite-env.d.ts` 留壳）。

**验证**：包能独立 `tsc --noEmit` 通过。
**回滚点**：删除 workspace 与新目录，恢复两仓原路径即可。

### Phase 2 — 两侧接线（关键：bridge 抽象）

**目标**：两个宿主改为"引用包"，删掉 `libtv` 副本。

步骤：
1. **bridge 抽象**：包内 `bridge.ts` 改为接口 + 依赖注入；主画布注入"Python 桥"，tauri 侧注入"Tauri 桥"。
2. shiguang-canvas：壳内 `import ... from '@shiguang/libtv'`。
3. AI-Canvas-tauri：`App.tsx` 的 `lazy(() => import('./libtv/App'))` 改为 `lazy(() => import('@shiguang/libtv/App'))`，**删除 `src/libtv/` 整目录**。

**验证**：两侧 `build` 通过 + tauri 侧 `npm run typecheck` 通过 + 手动切到「拾光导演台」视图能加载。
**回滚点**：恢复 libtv 同步目录（Phase 0 已保证内容一致，回填成本为零）。

### Phase 3 — 加 CI 防漂卡点（收尾，从此不再漂移）

**目标**：把"永不漂移"变成机器强约束。

步骤：
1. 加 CI：Mach 'diff' 检查——两个宿主禁止再出现 `libtv` 源码副本（若检测到即 fail）。
2. 加 CI：`pnpm -r build` 全量构建门禁，任何一侧 break 即 fail。
3. 给 AI 编辑加规则：改导演台画布只能改 `packages/libtv`，禁止往宿主里复制源码（写入 `.cursor/rules` 或配到 `<zones>`）。

**验证**：模拟"在宿主里手改一份 libtv 源码"能触发 CI 报错。

## 5. 关键风险与规避

| 风险 | 等级 | 规避 |
|---|:---:|---|
| 16 文件分叉合并时判断错"真源/最新" | 高 | Phase 0 逐文件 diff，bridge 侧以 tauri 为主、其余以 shiguang 为主 |
| three 0.184→0.185、react 19.0→19.2 存在 breaking API | 中 | Phase 0 先统一版本并 build，有差异当场修，不进 Phase 1 |
| `bridge.ts` 环境耦合被抽错 | 高 | Phase 2 显式做"接口 + 注入"，禁用包内直接判定宿主环境 |
| Rolldown-vite Windows 盘符 alias bug | 中 | 本方案用 workspace 软链而非 vite alias，天然绕过 |
| workspace 与两仓原有独立 git 历史冲突 | 中 | 不合并 git 历史，仅在同一 vendor 目录内加 workspace，保持两仓各自 .git 独立 |
| 迁移期间两产品同时不能发布 | 中 | 分 4 阶段、每阶段保 build 绿，随时可停 |

---

## 6. 验证与回滚总则

- **每阶段硬门禁**：`shiguang-canvas` 与 `ai-canvas-tauri` 两仓 `build` 必须通过；Phase 2 起 tauri 须 `typecheck` 通过。
- **回滚原则**：Phase 0–1 用 `git checkout` / 删目录即可回到原状；Phase 2 的桥接改动用原 libtv 同步目录背书（Phase 0 已保证内容一致）。
- **兜底声明**：全程不触碰冻结区（本次不涉及 `frozen_zones.json` 任何符号），不触碰 tauri 侧 `src/store`(20 slice) 与 `src/services` 等独有部分。

---

## 7. 给 DeepSeek / Cursor 的执行清单

1. 只动下列范围：`vendor/packages/libtv`（新建）、`vendor/shiguang-canvas/src`、`vendor/AI-Canvas-tauri/src/libtv`、两仓 `package.json`、`pnpm-workspace.yaml`、`vite.config.ts`（如需）。
2. 禁止动：`vendor/AI-Canvas-tauri/src/store`、`src/services`、`src/components`、`src-tauri/`、以及两个仓库各自的 `.git`。
3. 每个 Phase 结束前，跑：`shiguang-canvas: npm run build`、`ai-canvas-tauri: npm run build && npm run typecheck`。
4. 抽包后，任何"导演台画布"改动只进 `packages/libtv`，宿主要拿到新代码只能改版本/依赖，不复制作业。
