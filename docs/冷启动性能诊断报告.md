## 二、逐层定位过程（证据链）

### 2.1 第一次测量：假象 11 秒

分阶段计时显示 `import editor_module` 耗时 **11.05s**（占全程 95%），一度被判定为瓶颈。

```
T5  +lego.main_window         0.60s
T6  +editor_module           11.05s   Δ=+10.45s   ← 疑似瓶颈
```

### 2.2 反向验证：`-X importtime` 只测出 0.78 秒

```
[venv312] IMPORT 0.78s
[累计峰值] 0.71s  (478 条记录)
TOP: app.modules.lego.editor_module  cum=0.708s
     cv2                            self=0.073s
     app.core.config_manager        self=0.068s
```

两个数字差 10 秒。矛盾必须解释。

### 2.3 归因实验：`os._exit(0)` 让 10 秒消失

| 脚本 | wall | 内部自测 import | 推算 shutdown |
|---|---|---|---|
| `import editor_module` 后正常退出 | 11.06s | 0.705s | **≈10.35s** |
| 同上，但结尾 `os._exit(0)` | **1.00s** | — | — |

**结论：那 10 秒是解释器退出清理（shutdown）开销，不是导入开销。**

归因于 `subprocess` 创建的管道句柄在 `wait` 期间被沙箱安全策略阻拦 —— 同时验证到：

```
直接调 wmic: PermissionError [WinError 5] 拒绝访问（elapsed=0.00s）
```

即 `wmic` 立即被拒，并非超时等待。10 秒纯粹是子进程拆解阶段。

> **教训：用 `subprocess.run` 测 Python 启动耗时时，wall 包含了 shutdown。必须用 `os._exit(0)` 或 `atexit` 打点分离，否则会得到 10 倍虚高的数字。**

### 2.4 真实瓶颈：`_setup_ui` 之后的那一跳

用 monkey-patch 对 `MainWindow.__init__` 内每个子步骤打点（脚本结尾同样 `os._exit`）：

```
MARK imports done                          0.10s
MARK QApplication()                        0.13s
MARK get_license_manager                   0.21s
MARK import MainWindow                     0.32s
  SUB _setup_ui                            0.13s
    LAZY HomeModule                        7.76s  OK     ← 真凶
  SUB _setup_default_modules               7.79s
  SUB _update_auth_status                  0.00s
  SUB _apply_initial_theme                 0.00s
  SUB _setup_lazy_loading                  0.00s
MARK MainWindow() TOTAL                    8.24s
```

### 2.5 根因：`_detect_whisper()` 的模块级副作用

`modules.py` 末尾（1518–1541 行）有一整块顶层 eager import：

```python
# modules.py:1523
from .editor_module import EditorModule      # ← 抵消了懒加载意图
from .copywriting_module import CopywritingModule
from .tasks_module import TasksModule
from .materials_module import MaterialsModule
from .plugins_module import PluginsModule
from .performance_module import PerformanceModule
from .model_management import ModelManagementModule
```

而 `MainWindow._setup_default_modules()` → `_lazy_import_widget_class()` → `importlib.import_module(".modules")` → 触发上述整块。

再往下追 torch：

```python
# app/modules/lego/drama_understanding_engine.py:22-46
WHISPER_AVAILABLE = False
_whisper_model_type = None

def _detect_whisper():
    """检测Whisper可用性，优先使用faster-whisper"""
    global WHISPER_AVAILABLE, _whisper_model_type
    try:
        import faster_whisper          # ← 模块级调用，实为 torch 全量加载
        _whisper_model_type = "faster_whisper"
        WHISPER_AVAILABLE = True
        return True
    except ImportError:
        try:
            import whisper
            ...

_detect_whisper()      # ← 第 46 行：模块导入即执行
_check_ollama()        # ← 第 79 行：模块导入即执行（还会连本地服务）
```

**实测代价：**

```
起点                  torch=- whisper=- faster_whisper=- cv2=-
IMPORT faster_whisper  6.97s OK   torch=LOADED    ← 真凶
IMPORT whisper         0.00s FAIL ModuleNotFoundError
IMPORT drama_understanding_engine  0.12s OK       ← 模块本身很轻
```

`faster_whisper` 把 `torch` 整个拖进来（`torch/cuda/__init__.py` 还去 `import pynvml`）。

**一句话：用户打开首页要等 7.76 秒，只因为一个「检测 Whisper 装没装」的函数真的把它导进来了。**

## 三、附带发现（真缺陷）

### 3.1 `_check_ollama()` 在导入时连本地服务

```python
def _check_ollama():
    try:
        import ollama
        client = ollama.Client()
        models = client.list()        # ← 网络/进程调用，发生在模块导入期
```

导入即发起 `client.list()`。Ollama 未运行时可能阻塞到超时。**检测型代码不该有外部副作用。**

### 3.2 `canvas_server.py` 循环导入

```
ImportError: cannot import name '_check_host_token'
from partially initialized module 'app.core.canvas_server'
(most likely due to a circular import)
```

独立 `import app.core.canvas_server` 直接失败。目前未暴露是因为真实路径下由别的模块先导入。

### 3.3 `_lazy_import_widget_class` 名不副实

```python
def _lazy_import_widget_class(self, mod_def: dict):
    """延迟导入：按需 import 模块类，避免启动时一次性加载所有 UI 代码。"""
```

注释声称「避免启动时一次性加载所有 UI 代码」，但该函数在 `_setup_default_modules()` 里**对每个启用模块都同步 `importlib.import_module()`**。真正的实现是「启动时一次性加载所有」。

## 四、优化方案（按收益/风险排序）

> **执行状态（2026-09-20）**：**P0 已落地**（V4.32.3），实测窗口可见耗时 **8.24s → 1.54s（-81%）**。
> 详细改动与验证见 `docs/CHANGELOG.md` 的 V4.32.3 章节。P1 / P2 / P3 仍为待办。

### P0 · 零风险高收益 —— 把「检测」改成真延迟 ✅ 已完成

**目标文件**：`app/modules/lego/drama_understanding_engine.py`
**预期收益**：**-7.7 秒（94%）** → **实测 8.24s → 1.54s（-81%）**

思路：模块级不导入，改成「首次真正用到时才探测 + 结果缓存」。

```python
# 现状（模块级副作用）
_detect_whisper()      # 第 46 行
_check_ollama()        # 第 79 行

# 改法：惰性探测 + 单次缓存
_whisper_probed = False

def _ensure_whisper_probed():
    global _whisper_probed
    if not _whisper_probed:
        _whisper_probed = True
        _detect_whisper()
    return WHISPER_AVAILABLE
```

调用点（转写/语音分析入口）改为先 `_ensure_whisper_probed()`。
`_check_ollama()` 同理。

**风险**：低。语义等价 —— 原先导入即探测，现在首次使用即探测；结果一致。

**执行时补充发现的关键点**：`_load_whisper()` 读全局 `_whisper_model_type` 做分支判断，
**若只删模块级调用而不在该方法内补探测，`if/elif` 两分支都不会命中（静默失效）**。
已在其开头补 `_ensure_whisper_probed()`。共 6 处消费方改用 `_ensure_*`。

### P1 · 拆掉 `modules.py` 末尾的 eager import 块（待办）

**目标文件**：`app/modules/lego/modules.py:1517-1547`
**预期收益**：**~-0.9 秒**（剩余 `HomeModule` 加载中约 0.9s 属此块）

`MODULE_CLASSES` 是唯一消费方。可改为按需填充或改用 `module_registry.py` 里已有的 `import_module`/`import_class` 声明（注册表**本来就为懒加载设计**）。

**风险**：中。需核对 `MODULE_CLASSES` 的所有外部引用（`from modules import MODULE_CLASSES` 式调用）。`modules.py` 存在循环导入隐患（`editor_module` 反向 import `modules`），改这块要小心。

### P2 · 落实 `_lazy_import_widget_class` 的真懒加载（待办）

**预期收益**：配合 P1，避免「导航栏要先注册所有类」这一前置约束

当前 `register_module()` 需要真实 `widget_class`。可改为注册「惰性描述符」，首次 `select_module` 时才 import。

## 六、测量方法学备忘（下次复用）

1. **`subprocess.run` 的 wall time 包含子进程 shutdown** —— 测 Python 启动必须用 `os._exit(0)`，否则虚高。
2. **`-X importtime` 只覆盖 import 阶段** —— 与 wall time 差异大时，差额就是 shutdown。
3. **三层递进**：`importtime` 看导入 → monkey-patch 打点看方法级 → 逐模块独立 import 看单跳。
4. **`grep '^\s*(import|from)'` 找不到的依赖** —— 藏在模块级函数调用里（如 `_detect_whisper()`），必须靠「 import 前后 `sys.modules` 差集」发现。

`app.core.voice_generator` / `ai_enhanced` / `ai_engine` / `test_base` / `ffmpeg_utils`

### 7.5b 本轮顺带发现的**存量崩溃缺陷**（与本改动无关，已 A/B 证明）

`import app.core.shortcut_manager` → **`0xC00000FD` 栈溢出（进程硬崩，Python 层无法捕获）**。

**最小复现（PyQt6 可 100% 复现）**：

```python
from PyQt6.QtCore import QObject

class Foo(QObject):
    _i = None
    def __new__(cls, *a, **k):          # ← 覆写 __new__ 返回缓存实例
        if cls._i is None:
            cls._i = super().__new__(cls)
            cls._i._init = False
        return cls._i
    def __init__(self):
        if getattr(self, '_init', False):
            return
        super().__init__()              # ← 与上面的 __new__ 组合即崩
        self._init = True

Foo()   # 0xC00000FD
```

**条件对照实验结果**：

| 变量 | 结果 |
|---|---|
| 覆写 `__new__` + `__init__` 内调 `super().__init__()` | **❌ 崩** |
| 覆写 `__new__`，但 `__init__` **不调** `super().__init__()` | ✅ 正常 |
| 覆写 `__new__`，且 `_init` 在 `super().__init__()` **之前**置位 | **❌ 仍崩** |
| 不覆写 `__new__`，只调 `super().__init__()` | ✅ 正常 |
| 有 / 无 `QApplication` 后再导入 | 都崩（无关） |

⇒ **根因不是「守卫置位太晚」**（提前置位仍崩），而是
**「QObject 子类覆写 `__new__` 返回缓存实例」×「`__init__` 内调用 `super().__init__()`」
这一组合在 PyQt6 上触发 C 层无限递归**。

**A/B 验证**（换回原版 eager `__init__.py` 重测）：

| `app/core/__init__.py` | `app.core.shortcut_manager` |
|---|---|
| 原版 eager | `0xC00000FD` |
| 新版惰性 | `0xC00000FD` |

**结论：完全一致，属存量缺陷，与本次惰性化改动无关。**

**影响面（已核实）**：`shortcut_manager` 仅被 `app/core/editing_capabilities.py:22` 引用；
而 `editing_capabilities` **在生产代码中零引用**（只有 `tests/unit/test_video_editing_e2e.py:520` 用它）
⇒ 该崩溃**不影响运行中的应用**，但会让那个测试硬崩。

另注：`app/logs/app.log` 显示 2026-04/05 时 `shortcut_manager.py:177 - 已加载快捷键配置`
是**正常打印**的，且当前文件行号已漂移 ⇒ 这是**后续某次编辑引入的回归**，非历史遗留。

**修复方向（待确认）**：`shortcut_manager` 本就是模块级单例（`shortcut_manager = ShortcutManager()`），
`__new__` 的单例包装属冗余 —— 去掉 `__new__` 即可绕开该 PyQt6 陷阱。

**同批发现的另 3 个存量导入失败**（A/B 同样证明与原版一致）：`ai_interpolation`
（`TypeError: bytes or ASCII string expected not '_GenericAlias'`）、`highlight_preview`（同左）、
`ai_tools`（`ImportError: cannot import name 'OUTPUT_PATH' from 'config'`，

### 7.7 本轮方法论教训（已写入技能 `python-coldstart-profiling`）

1. **归因前必须先核对解释器与依赖清单**。我在空解释器上追了 10+ 轮，全部结论作废。
2. **`-X importtime` 的 cumulative 会错位归因**。曾把 0.677s 记在一个实测 1.9ms 的模块头上。
3. **「同一包下多个子模块耗时高度一致」= 父包税的信号**，说明该数值属于 `__init__.py` 而非子模块。
4. **`sys.settrace` 逐文件活跃窗口**比 `importtime` 更可信：不依赖先序假设，还能暴露"无 app 代码执行"的空窗期。
5. **`sys.meta_path` spy + `traceback.extract_stack()`** 是抓「谁引入了这个库」的终极手段——
   直接给出从包入口到真凶的完整调用栈。
6. **clean-room 子进程测量优于同进程增量测量**（后者受缓存、GC、已导入状态影响）。
7. **改造前先证明「这块代码有消费方」**。本例的最大发现是：那 47 个 re-export 名**全库零消费**。
   若先做了这一步，P1-a 就不会被拖延两轮 —— 用 AST 扫 `from X import Y` 的聚合表
   比逐个 grep 快得多，且能顺带发现「哪些名字是死 API」。
8. **「模块级导入但全文件零使用」的死导入，可用 AST 批量扫出来**。
   判定：收集所有 `Name` 节点集合，再看模块级 `import` 绑定的名字是否在其中。
   本例扫 502 个文件命中 3 处，其中 1 处恰在启动链上（省 0.139s）。
9. **发现崩溃时，必须先做 A/B 隔离，再下结论**。本轮把 `app/core/__init__.py` 换回原版
   重测，才确证 `shortcut_manager` 栈溢出是存量缺陷。
   **没有 A/B 就说"这是存量问题"是不严谨的** —— 反之，没有 A/B 就急着去修，会白改一通。
10. **`0xC00000FD`（STATUS_STACK_OVERFLOW）无法被 Python 捕获**：`sys.setrecursionlimit`
    降到 200 也抓不到 `RecursionError`，因为递归在 C 层。
    唯一有效手段是 **`faulthandler.enable(file=...)`** —— 它会在崩溃瞬间把 Python 栈 dump 出来。
    且**必须每个可疑模块跑独立子进程**，否则第一个崩溃会带走后续所有测试。

### 8.7 顺带修复：`shortcut_manager` 栈溢出（存量崩溃）

§7.5b 记录的 `0xC00000FD` 已修。**改了两处（都要改，只改一处会换一种崩法）**：

| # | 改动 | 原因 |
|---|---|---|
| 1 | 删除 `__new__` 单例包装（及 `_instance` 字段） | 「覆写 `__new__` 返回缓存实例」×「`__init__` 内 `super().__init__()`」在 PyQt6 触发 C 层无限递归 |
| 2 | `super().__init__()` **上移到 `__init__` 第一行** | 原守卫 `getattr(self, '_initialized', False)` 在 `super().__init__()` **之前**读实例属性 → PyQt6 报 `RuntimeError: super-class __init__() of type ShortcutManager was never called`。原代码靠 `__new__` 预塞 `_initialized` 才"侥幸"绕过这一步，然后立刻撞上栈溢出 |

**为什么删 `__new__` 是安全的**：全库 grep 确认 `ShortcutManager(` **只有一处构造**
（`shortcut_manager = ShortcutManager()` 模块级），单例契约从未被依赖。

**修后验证**：import 正常 / 52 个快捷键绑定正常加载 / `pyqtSignal` 可连可发 /
`editing_capabilities`（此前被连带的崩溃受害者）恢复可导入。
